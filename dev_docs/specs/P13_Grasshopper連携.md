## 0. このフェーズについて

### 0.1 目的

Grasshopper（以下 GH）を Squid-n の**パラメトリック形状入力・最適化ループのフロントエンド**にする。

- **段階 A（形状入力）:** GH で骨組（節点・部材・スラブ・支点・荷重）をパラメトリックに定義し、
  開いている Squid-n GUI にリアルタイムに流し込む。細部設定・解析・帳票は GUI 側で行う。
- **段階 B（解析ループ）:** GH から一次設計一式（線形静的＋地震静的＋組合せ＋許容応力度検定＋重量集計）を
  実行し、結果を GH に返す。Galapagos / Wallacei 等による断面・形状最適化ループを成立させる。

想定ワークフロー: **GH でモデル生成 → Sync OFF にして GUI で細部設定（地震パラメータ等）→
再 Sync して GH で最適化実行**。

### 0.2 完了像（ゴール）

1. GH のスライダーを動かすと、開いている Squid-n GUI の 3D ビューが追従して更新される。
2. Sync OFF → GUI で設定変更 → 再 Sync しても、GUI 所有の設定（§1 の所有権境界）が保持される。
3. GH の `SqnAnalyze` から一次設計一式が実行され、部材ごとの検定比・変位・重量が
   GH 側のキーに対応付いて返る。
4. 上記 3 を目的関数・制約として Galapagos で断面最適化ループが完走する。
5. DTO スキーマの Rust↔C# 不整合が CI で機械的に検出される。

## 1. 設計決定記録（2026-08 壁打ちの結論）

本フェーズの方針は以下の決定に基づく。実装中に迷ったらこの表に立ち返ること。
D1〜D17 は当初の壁打ち、D18〜D26 は仕様レビュー（矛盾・未定義点の洗い出し）の結論。

| # | 論点 | 決定 | 主な理由 |
|---|---|---|---|
| D1 | 連携の目的 | 段階 A（形状入力）→ 段階 B（解析ループ）の段階実現 | A は低コストで価値が出る。B を見据えた通信設計を最初から採る |
| D2 | 接続方式 | プロセス間通信（HTTP）。FFI・ファイル渡しは不採用 | FFI は ABI 保守・panic 隔離・配布が過大。localhost HTTP の往復は解析時間に対し誤差 |
| D3 | サーバの居場所 | **GUI アプリに内蔵** + **Sync モード**（ON = GH が単一ライタ・GUI は閲覧のみ／OFF = 通常の GUI 編集） | 「開いている GUI と連携」の要件。単一ライタ原則をモード切替で守り、競合解決を作らない |
| D4 | 同期の単位 | **全量置換**（GH は毎回モデル全体を送る） | GH の再計算セマンティクスと一致。差分方式の ID 安定対応は本質的に解けない |
| D5 | ペイロード | **GH 専用 DTO（JSON）**。内部 `Model` にも ST-Bridge にも結合しない | 後方互換なし方針の内部モデルからプラグインを絶縁。変換知識は Rust 側に置く |
| D6 | プロトコル | **素の HTTP JSON API**。MCP は AI 向けに別物として存続 | C# は `HttpClient`+`System.Text.Json` だけで書ける。解析は同期レスポンスで足りる |
| D7 | 結果の対応付け | **クライアント発行キー**（全要素に GH 側が付けた文字列キー） | 順序非依存。エラーも「どの入力が悪いか」付きで返せる |
| D8 | v1 解析スコープ | **一次設計一式**（長期＋地震静的 X/Y＋組合せ＋検定比＋重量）。階は `story_gen` 自動生成 | 長期のみでは一次設計が成立しない。自動生成に乗れば DTO は地震スカラーだけで済む |
| D9 | 設定の所有権 | ジオメトリ依存＝GH 所有（毎回置換）／ジオメトリ非依存のルール・パラメータ＝GUI 所有（再 Sync を生存） | 最適化ループの不変条件（全イテレーションで同一設定）を構造的に保証 |
| D10 | 個別要素のモデル化条件 | 剛床解除等は**宣言的な入力属性に昇格**し DTO に含める（生成結果の手編集にしない） | 再 Sync・階再生成で消えない。GUI 単独運用の脆さも直る |
| D11 | 断面・材料 | 規格名／形状+寸法の**両対応** + **カタログ API**（規格表の単一情報源は Squid-n） | 断面最適化には候補列挙が必須。規格表の二重管理を避ける |
| D12 | 荷重 | **スラブを DTO に含める**（分配・重量集計は準備計算に委譲）。壁は線荷重で代替。既定組合せはサーバ側で自動構成 | スラブは剛床・地震用重量・CMQ の源泉。GH は床外形+用途を送るだけ |
| D13 | Sync 制御 | GUI 側トグル。OFF 中の push は 409 拒否。ON 時のみ未保存確認 1 回。ON 中は GUI 編集 UI 無効化（GUI 所有設定を除く） | 主導権をユーザーの明示操作に置く。ループ中は無確認で受ける |
| D14 | 単位系 | **DTO は mm・N 固定**（内部単位と一致）。換算は C# プラグインに一点集約。Z-up 右手系（変換不要） | 換算責務を「Rhino 単位を知る唯一の場所」に集中。単位事故の予防 |
| D15 | ターゲット | Rhino 8 以降 / GH1 / **.NET 8**。Rhino 7・net48・GH2 は対象外 | 後方互換なし方針と一貫。Mac は .NET 8 なら追加コスト小 |
| D16 | コンポーネント粒度 | Karamba 型・DTO 語彙と 1:1 の 9 コンポーネント | スキーマ変更時の追従箇所が明確。キー採番は `SqnAssemble` に集約 |
| D17 | リポジトリ・型同期 | **モノレポ**（`grasshopper/` フォルダ）。schemars → JSON Schema → C# DTO 自動生成 + CI ドリフト検査 | 「Rust 型が単一情報源、C# は生成物」を CI で強制 |
| D18 | 解析対象の同一性 | `/sync/model` がモデルリビジョン（単調増加整数）を返し、`SqnSync` の出力トークンを `SqnAnalyze` の必須入力にする。`/analyze` はリビジョン照合し不一致は 409 | GH は兄弟コンポーネントの実行順を保証しない。順序のデータフロー強制＋照合の二重で「前イテレーションのモデルを解析する」事故を防ぐ |
| D19 | 所有権表外の `Model` フィールド | §6.3 の表に無いフィールドは GH 所有（消える）が既定。建物一律のジオメトリ非依存設定は GUI 所有に明記。検定比に直結する横座屈補剛は宣言的属性として DTO に昇格 | 解釈の余地を残さない。lb 既定＝部材全長のままでは断面最適化が過大断面に収束する |
| D20 | 追加ケースの組合せ取り込み | `combine: none / long_term / short_term` の列挙。`short_term` は ±両符号の短期組合せを自動生成 | 風・雪の代替には短期組合せが必須。既存の組合せ自動構成機構に乗る最小拡張 |
| D21 | スラブ積載の指定 | `usage` はプリセット名／3 値 `{floor, frame, seismic}` の両対応。単一スカラーの上書きは持たない | 積載 3 値（令85条）を単一値から展開する規則は定義できない。コアの `SlabUsage::Custom` に 1:1 |
| D22 | サーバの並行制御 | 完全直列化。解析はバックグラウンド実行だが完了まで後続リクエストを取り出さない。実行前にキャンセル済みリクエストを破棄 | 最適化ループは本質的に逐次。「解析対象＝直近 sync」が構造的に常に成立する |
| D23 | undo への記録 | Sync 置換コマンドは OFF 遷移時に 1 件積む（push 無しなら積まない）。ON 中は undo/redo も無効化 | コマンド方式の undo/redo 対称性を保つ。ON 中の undo は単一ライタ原則違反の窓になる |
| D24 | 材料定義の生存 | 材料定義テーブルは GUI 所有（DTO 参照の有無に関わらず全量移植）。名前解決はカスタム→JIS プリセットの順 | 参照が外れたイテレーションで定義が消えると次の参照で 422 になりループが破綻する |
| D25 | 周期算定 | v1 は略算式固定（`t_method` フィールドを持たない） | 精算周期は固有値解析前提で v1 の同期実行では成立しない。選べるが必ず失敗する enum 値をスキーマに載せない |
| D26 | 層間変形角 | 一次設計一式に令82条の2 の確認を含める。制限分母は GUI 所有の設計条件（既定 200・緩和 120） | 最適化制約の主要指標。既存の二次設計指標実装を流用でき追加コストが小さい |

## 3. アーキテクチャ（T2）

### 3.1 構成

```
┌───────────── Rhino / Grasshopper (.NET 8) ─────────────┐
│ SqnSupport ─┐                                          │
│ SqnMember ──┤→ SqnAssemble → SqnSync ──── POST /sync/model ─┐
│ SqnSlab ────┤       │        SqnAnalyze ─ POST /analyze ────┤
│ SqnLoad ────┘       │        SqnSections ─ GET /catalog/… ──┤
└─────────────────────┼──────────────────────────────────────┘
                      │ キー採番・点マージ・単位換算（mm・N）    │ 127.0.0.1:8787
┌─────────────────────┼──────────────────────────────────────┐
│ squid-n-app (egui)  ▼                                      │
│  ┌─ HTTP サーバスレッド (tokio + axum, crates/squid-n-gh) ─┐ │
│  │  DTO 検証 → SyncRequest を mpsc チャネルへ →            │ │
│  │  oneshot で適用結果を受けて HTTP レスポンス              │ │
│  └────────────────────────────────────────────────────┘ │
│  UI スレッド: フレーム毎にチャネルを poll →                  │
│    Sync ON なら DTO→Model 変換・全量置換 → request_repaint  │
└────────────────────────────────────────────────────────────┘
```

- HTTP 層は `axum`（workspace 依存に追加）。tokio ランタイムは専用スレッドで起動し、
  GUI 起動中は常時 listen する（受理可否は Sync 状態で決める）。
- **モデルへの書込は必ず UI スレッド**で行う（単一ライタ原則）。サーバスレッドは
  リクエストをチャネルに積み、UI スレッドの適用結果（成功／キー付きエラー）を
  `oneshot` で受けてレスポンスを返す。
- **リクエスト処理は完全直列**（D22）: チャネルに届いた順に 1 件ずつ処理し、処理が
  完了するまで次を取り出さない。`/analyze` は対象の確定（リビジョン照合）を
  UI スレッドで行い、解析本体は既存の `AnalysisJob` 機構（バックグラウンドスレッド）で
  実行する。UI には進捗表示を出してよい（egui は解析中もイベントループを回す設計を維持）。
  各リクエストは実行前に `oneshot` の切断（クライアントのキャンセル）を検査し、
  切断済みなら**実行せず破棄**する（HTTP のキャンセルはサーバの計算を止めないため、
  検査なしではキャンセル済み解析が計算資源を浪費する）。
- 全量置換の適用に成功するたび、サーバは**モデルリビジョン**（単調増加整数）を発行して
  `/sync/model` レスポンスで返す（D18）。`/analyze` はリクエスト中のリビジョンと
  照合し、不一致は 409 で拒否する（§4.3）。
- 既定ポートは `8787`。起動時のコマンドライン引数で変更可（app に設定ファイルの
  永続化機構は現存しない。導入された場合はそちらへ移してよい）。バインドは
  `127.0.0.1` 固定とし、リモート接続・認証は将来課題（§13）。

### 3.2 クレート構成

`crates/squid-n-gh`（新規・ライブラリ）:

```
src/
  dto.rs        … DTO 型（serde + schemars 導出。§5）
  convert.rs    … DTO → Model 変換 + キー対応表（§6）
  results.rs    … 解析結果 → レスポンス DTO 整形（§7）
```

## 4. Sync モードと HTTP API（T2）

### 4.1 Sync モードの状態機械

| 状態 | GUI 編集 | `POST /sync/model` | `POST /analyze` | 遷移 |
|---|---|---|---|---|
| **OFF**（既定） | 可 | 409 拒否 | 409 拒否 | トグル ON 操作で → ON |
| **ON** | 不可（編集 UI をグレーアウト。閲覧・カメラ・結果表示は可） | 受理（全量置換） | 受理 | トグル OFF 操作で → OFF |

- **ON にする操作**: 未保存の変更がある場合のみ確認ダイアログを 1 回出す
  （「現在のモデルのジオメトリは GH から置き換えられます」）。以後 ON 中は無確認で受理。
- **undo との関係**（D23）: Sync 中の push は undo 履歴に**積まない**（毎秒単位の
  push で履歴が溢れるため）。代わりに **OFF 遷移時**に「Sync 置換」コマンドを 1 件
  だけ積む（逆方向 = ON 時点のモデルスナップショット、順方向 = OFF 時点の同期済み
  モデル。ON〜OFF 間に push が 1 回も無ければ積まない）。`UndoStack` はコマンド方式の
  ため、両方向のスナップショットが確定する OFF 時点で積むことで undo/redo の対称性を
  保つ — OFF 後の undo 1 回で Sync 開始前に戻り、redo で同期結果に戻る。
  **ON 中は undo/redo も編集 UI と同様に無効化**する（単一ライタ原則。
  undo 経由の書込の窓を作らない）。
- GUI 所有設定（§6.3）は Sync 状態に関わらず GUI から編集可とする
  （地震パラメータの調整をループ間で行う運用を妨げない）。

### 4.2 エンドポイント

| メソッド/パス | 概要 | Sync OFF 時 |
|---|---|---|
| `GET /status` | バージョン・Sync 状態・モデル概要（節点数等）・スキーマバージョン | 200 |
| `POST /sync/model` | 全量置換（§5 の `SyncModel`）。適用後の警告・自動生成された階の要約・モデルリビジョン（D18）を返す | 409 |
| `POST /analyze` | 一次設計一式を実行し結果を返す（§7）。直近に同期されたモデルが対象（リビジョン照合。D18） | 409 |
| `GET /catalog/sections?family=H` | 規格断面の列挙（§8） | 200 |
| `GET /catalog/materials` | 材料プリセットの列挙（§8） | 200 |

### 4.3 ステータスコードとエラー形式

| コード | 意味 |
|---|---|
| 200 | 成功（警告は body の `warnings` に含める） |
| 400 | JSON パース不能・スキーマ違反（フィールド欠落・型不一致） |
| 409 | Sync OFF 中の書込系・解析系リクエスト。`/analyze` のモデルリビジョン不一致（D18） |
| 422 | スキーマは正しいが意味的に不正（未知の断面名・存在しない節点キー参照・拘束不足等） |
| 500 | 内部エラー（panic は catch して 500 に変換。サーバは落とさない） |

422 / warnings は必ず**キー付き**で返す（D7）:

```json
{
  "errors": [
    { "key": "beam-0012", "field": "section",
      "message": "断面名 'H-400x200x8x13' がカタログにありません" }
  ],
  "warnings": [
    { "key": "node-0044", "message": "剛床解除節点が階 2FL に属します（水平力の負担なし）" }
  ]
}
```

`key` はリクエスト中のクライアント発行キー。モデル全体に関わるものは `key: null`。
C# プラグインはこれを該当コンポーネントの Error/Warning バルーンに表示する。

## 5. DTO スキーマ（T0）

### 5.1 原則

- **単位: 長さ mm・力 N・モーメント N·mm。座標系: Z-up 右手系**（Rhino と一致。変換不要）。
  スキーマの doc コメントに明記し、生成 JSON Schema にも載せる。
- 全要素が `key: String`（クライアント発行・リクエスト内で一意）を持つ。
- serde + schemars を導出し、`cargo xtask gh-schema` で JSON Schema を出力する（§11）。
- 後方互換は維持しない（プロジェクト方針）。スキーマに `schema_version`（整数）を持たせ、
  不一致は 400 で「プラグインと本体のバージョン不一致」を明示するのみとする。

### 5.2 `SyncModel`（`POST /sync/model` の body）

```jsonc
{
  "schema_version": 1,
  "nodes": [
    // 点のマージ（許容差内の同一視）は GH 側 SqnAssemble の責務。
    // Rust 側は座標の重複チェックをせず、キー参照のみ解決する。
    { "key": "n-0", "coord": [0, 0, 0],
      "restraint": "fixed",              // "free"(既定) | "pinned" | "fixed" | [bool;6]
      "support_spring": null,            // [f64;6] 並進 N/mm・回転 N·mm/rad。restraint が
                                         // 拘束していない自由度にのみ指定可（拘束済み
                                         // 自由度への指定は 422）
      "diaphragm": "auto" }              // "auto"(既定) | "exclude"  ← D10 の宣言的属性
  ],
  "members": [
    { "key": "beam-0012", "from": "n-0", "to": "n-1",
      "section": { "name": "H-400x200x8x13" },   // または { "shape": "H", "dims": {...} }
      "material": "SN400B",
      "end_release": ["rigid", "pin"],           // 材端条件 [i端, j端]
      "role": "girder",                          // "column" | "girder" | "beam" | "brace"
      "secondary": false,                        // true = 二次部材（小梁・間柱）
      "lateral_brace_count": null }              // 等間隔横補剛の本数（lb = L/(n+1)）。
                                                 // null(既定) = 補剛なし（lb = 部材全長）。
                                                 // 検定比に直結するため宣言的属性として
                                                 // DTO に含める（D19）
  ],
  "slabs": [
    { "key": "s-01", "boundary": ["n-0", "n-1", "n-5", "n-4"],
      "kind": "interior",                        // "interior" | "cantilever" | "corner"
      // usage はプリセット名 or 3 値の任意入力の両対応（D21。SlabUsage::Custom に 1:1）:
      //   "usage": { "floor": 2.9e-3, "frame": 1.8e-3, "seismic": 0.8e-3 }  [N/mm²]
      "usage": "office",
      "dead_load": 1.2e-3 }                      // スラブ自重を含む固定荷重の面荷重 [N/mm²]。
                                                 // 自重の自動算定は行わない（GUI と同じ流儀）
  ],
  "loads": {
    "cases": [ { "key": "lc-add", "kind": "other", "name": "機器荷重",
                 "combine": "long_term" } ],  // "none" | "long_term"(既定) | "short_term"（D20）
    "nodal":  [ { "key": "pl-1", "case": "lc-add", "node": "n-3",
                  "force": [0, 0, -5000], "moment": [0, 0, 0] } ],
    "member": [ { "key": "wl-1", "case": "lc-add", "member": "beam-0012",
                  "kind": "uniform", "value": -10.0, "axis": "global_z" } ]  // N/mm
  }
}
```

補足:

- **自重・床荷重・地震荷重は DTO に含めない**。自重と床分配は準備計算、地震は
  `story_gen` + Ai 分布が担う（D8/D12）。DTO の荷重は「それ以外の追加荷重」のみ。
  床荷重の分配方法は `TriTrapezoid`（三角形・台形分配）固定とし、`docs/` に既定として
  明記する。
- 既定の荷重ケース（DL: 固定＋自重、LL: 積載）と一次設計の既定組合せ
  （DL+LL、DL+LL±EX、DL+LL±EY。組合せ名は既存実装の標準命名に従う）は
  **サーバ側で自動構成**する。追加ケースは `loads.cases` で定義し、組合せへの
  取り込みは `combine` で指定する（D20）:
  - `"none"`: 解析のみ行い、どの組合せにも入れない
  - `"long_term"`（既定）: 長期組合せに加算（DL+LL+C）
  - `"short_term"`: ±両符号の短期組合せ（DL+LL±C）を自動生成する。
    風・積雪の代替はこの指定で行う（詳細な組合せ編集は将来。§13）
- 断面 `section` は規格名（カタログ解決）または形状+寸法の両対応（D11）。
  材料は名前解決のみ。解決順は「モデル内のカスタム材料（GUI 所有。D24）→
  JIS プリセット」とし、最初に一致した定義を採用する（解決順は `docs/` に明記）。
- `diaphragm: "exclude"`・`end_release`・`secondary`・`lateral_brace_count` は
  D10 の宣言的属性。同種の属性を将来追加する場合も「生成結果の手編集」ではなく
  必ずここに載せる。

### 5.3 `AnalyzeRequest` / `AnalyzeResponse`（§7 で詳述）

```jsonc
// POST /analyze  body
{
  "schema_version": 1,
  "model_revision": 42,                // 直近の /sync/model が返したリビジョン（D18。必須）
  "preset": "primary_design",          // v1 はこれのみ。将来 "eigen" 等を追加
  "seismic": {                          // 省略時は GUI 所有の設定値を使う（§6.3）
    "z": 1.0, "ground_type": 2, "c0": 0.2
  }
}
```

`seismic` を省略すると GUI で設定した値が使われる。**送った場合は GUI 所有設定を
上書きせず、このリクエスト限りで適用**する（最適化で C0 を振る等の用途。
恒久設定は GUI で行う、という所有権境界 D9 を崩さない）。

一次設計用の周期 T は**略算式固定**（D25）。精算周期は固有値解析の実行が前提であり
v1 の同期実行では成立しないため、スキーマに選択肢を設けず、長時間解析の GH 公開
（§13）と合わせて将来対応とする。

## 6. DTO → Model 変換と所有権境界（T0, T2）

### 6.1 変換（`convert.rs`）

1. DTO 検証（キー重複・参照解決・値域）。失敗は 422 のキー付きエラー（§4.3）に集約。
2. 材料名・断面名をカタログ解決し、`Model` の材料・断面テーブルを構築。
3. 節点・部材・スラブ・支点・荷重を `Model` に構築。**キー ↔ 内部 ID の対応表**
   （`KeyMap: HashMap<String, EntityId>` 両方向）を作り、以後の結果整形・エラー整形で使う。
4. 宣言的属性（`diaphragm: exclude` 等）を適用。
5. 準備計算＋`story_gen` を実行（GUI 所有の生成パラメータを使用。§6.3）。
   生成された階の要約（階名・レベル・地震用重量・剛床構成）をレスポンスに含め、
   GH 側で妥当性を確認できるようにする。

### 6.2 全量置換の適用

UI スレッドで `ReplaceSyncedModel` 相当の適用処理を行う:

- 現在モデルの **GUI 所有部分（§6.3）を退避**し、変換結果の新モデルに移植して差し替える。
- 解析結果・選択状態・stale フラグは既存の `App::load_model` と同じ規約でリセットする。
- undo は §4.1 の規約（Sync 中は積まない）。

### 6.3 所有権境界（D9）の実装

| 区分 | 内容 | 再 Sync 時 |
|---|---|---|
| **GH 所有** | 節点・部材・スラブ・支点・支点ばね・追加荷重・断面割当・材料割当・宣言的属性（剛床解除・材端・二次部材・横座屈補剛） | **毎回置換** |
| **GUI 所有** | 地震パラメータ（Z・地盤種別・C0）、階生成パラメータ（クラスタリング許容差等）、質量方式（`mass_method`）、**材料定義テーブル**（カスタム材料を含む全定義。D24）、**建物一律のモデル化設定**（`slab_thickness`・`load_cfg`・`multi_opening_mode` 等。D19）、設計条件（層間変形角の制限分母〔既定 200・緩和 120〕を含む。D26）、表示設定 | **退避→移植で生存** |

GUI 所有フィールドの集合はコード上で 1 箇所（`convert.rs` の移植関数）に集約し、
`Model` にフィールドを足すときに移植漏れが起きないよう、網羅テスト
（新旧モデルの GUI 所有フィールド全一致を assert）を置く。

**上表に無い `Model` フィールドは GH 所有（全量置換で消える）を既定とする**（D19）。
要素紐付きの設計属性（`steel_design_attrs` の欠損率等・`wall_attrs`・`misc_walls` など）も
同様に消える。GUI で設定済みの属性が置換で失われる場合は warning で通知する。
移植関数は `Model` の全フィールドを destructuring で列挙する実装とし、フィールド追加時に
GH 所有／GUI 所有の分類判断がコンパイルエラーで強制されるようにする。

**v1 の割り切り:** GUI で定義した追加の荷重組合せは再 Sync で保持**しない**
（GH 所有の荷重ケース名を参照するため、キー再結合問題が再燃する。§13 参照）。

## 7. 一次設計一式の実行と結果返却（T3）

### 7.1 実行内容（`preset: "primary_design"`）

1. 準備計算（自重・床分配・地震用重量）※ /sync/model 時に実施済みの結果を再利用
2. 線形静的解析: DL+LL（長期）
3. 地震静的解析: EX・EY（Ai 分布。T は略算式固定。D25）
4. 既定組合せ（DL+LL、DL+LL±EX、DL+LL±EY ＋ `combine` 指定の追加組合せ）の断面力算定
5. 許容応力度検定（一次設計）: 部材ごとの最大検定比と支配組合せ
6. 重量集計: 鋼材重量（材料別）・コンクリート体積
7. 層間変形角の確認（令82条の2。D26）: 地震時弾性変位から階・方向ごとに算定
   （その階の柱の層間変形角の最大値・斜め柱除外という既存実装の扱いに従う）。
   制限値は GUI 所有の制限分母（既定 200・緩和時 120）から算出する

実行は同期レスポンス（D6）。目安として中規模モデルで数秒以内。タイムアウトは設けず、
GH 側 `SqnAnalyze` は応答待ちをキャンセル可能にする（HttpClient の CancellationToken）。
サーバ側はリクエストを完全直列で処理し、実行前にキャンセル済みリクエストを破棄する
（D22。§3.1）。

### 7.2 `AnalyzeResponse`

```jsonc
{
  "schema_version": 1,
  "model_revision": 42,   // 解析対象のモデルリビジョン（D18）
  "stories": [   // story_gen の生成結果（確認用）
    { "name": "2FL", "level": 4000.0, "seismic_weight": 1.23e6, "ai": 1.32, "ci": 0.26 }
  ],
  "nodes": [
    { "key": "n-3",
      "displacement": { "DL+LL": [0.1, 0.0, -2.3, 0, 0, 0], "DL+LL+EX": [12.3, ...] },
      "reaction": null }   // 支点のみ Some
  ],
  "members": [
    { "key": "beam-0012",
      "forces": { "DL+LL": { "n_i": -1.2e4, "m_i": 3.4e7, "q_i": 5.6e4, /* j端同様 */ } },
      "check": { "ratio": 0.84, "governing": "DL+LL+EX", "kind": "bending" } }
  ],
  "drift": [ { "story": "2FL", "direction": "X",
               "value": 0.0042, "limit": 0.005 } ],  // limit = 1/制限分母（GUI 所有。D26）
  "totals": { "steel_weight_n": 4.56e5, "concrete_volume_mm3": 1.2e10,
              "steel_by_material": { "SN400B": 3.1e5 } },
  "warnings": [ ... ]   // §4.3 と同形式
}
```

- キーは GH 側発行のものをそのまま返す（D7）。内部 ID は露出させない。
- 組合せ名は既存実装の標準命名（`DL+LL`・`DL+LL+EX` 等）をそのまま用いる
  （§12.1 の「GUI 経路との数値一致」検証で名前の対応表を不要にするため）。
- 変位・断面力は組合せ名をキーにしたマップ。最適化で使う代表値
  （`check.ratio`・`totals`・`drift`）はトップレベルで取り出しやすくする。
- 解析エラー（拘束不足・特異行列等）は既存の precheck / 診断メッセージを 422 の
  キー付きエラーに変換して返す（原因部材・節点が特定できる場合はそのキーを付す）。

## 9. コアモデル拡張: 宣言的モデル化属性（T1）

D10 の方針に基づき、以下を**入力属性**としてコアモデルに追加する。

## 10. C# GH プラグイン（T6）

### 10.1 配置とプロジェクト構成

```
grasshopper/
  SquidN.Grasshopper.sln
  src/
    SquidN.Grasshopper/          … コンポーネント本体（Grasshopper NuGet 参照）
    SquidN.Grasshopper.Dto/      … 生成 DTO（§11 の生成物のみ。手書きコード禁止）
    SquidN.Grasshopper.Client/   … HttpClient ラッパ（接続・エラー→バルーン変換）
  tests/
    SquidN.Grasshopper.Tests/    … DTO 往復・Assemble ロジックの単体テスト（Rhino 不要）
  schema/                        … xtask が出力する JSON Schema（コミットする）
```

- TFM は `net8.0`。`Grasshopper` は NuGet 参照（ビルドに Rhino 不要 → CI は ubuntu で可）。
- 配布は Yak パッケージ（`yak build`）。手順は CONTRIBUTING.md に追記する。

### 10.2 コンポーネント（D16。プレフィックス `Sqn`）

| コンポーネント | 入力 → 出力 | 備考 |
|---|---|---|
| `SqnSupport` | 点, 拘束条件（プリセット/6bool）, ばね → Support |  |
| `SqnMember` | 線, 断面, 材料, 材端, role, 二次部材, 横補剛本数 → Member | 断面は `SqnSections` 出力 or 名前文字列 |
| `SqnSlab` | 境界点列, kind, 用途, 仕上げ荷重 → Slab |  |
| `SqnNodeAttr` | 点, 剛床解除フラグ → NodeAttr | 宣言的属性（D10） |
| `SqnLoad` | ケース, 対象（点/線）, 値 → Load |  |
| `SqnAssemble` | Support/Member/Slab/NodeAttr/Load 群 → Model | **点マージ（許容差=ドキュメント許容差）とキー採番を一手に担う**。単位換算（ドキュメント単位→mm）もここ |
| `SqnSync` | Model, 有効化 bool → 接続状態, 同期トークン | `POST /sync/model`。サーバ発行のモデルリビジョンを同期トークンとして出力する（D18）。409 は「Squid-n 側で Sync が OFF です」と表示 |
| `SqnAnalyze` | 同期トークン（`SqnSync` 出力。**必須**）, 地震パラメータ(任意) → 検定比/変位/断面力/重量/変形角/階要約 | トークン入力により `SqnSync` 実行後にのみ動くことをデータフローで強制し、リビジョンを `/analyze` に添えて照合する（D18）。結果は入力キー順のデータツリーで出力 |
| `SqnSections` | family, フィルタ → 断面候補リスト | `GET /catalog/sections` |

キー採番規則: `SqnAssemble` が入力のデータツリーパス＋インデックスから決定論的に生成する
（例 `member/0;2/5`）。同一定義・同一入力なら再計算でも同じキーになり、
イテレーション間で結果の対応が安定する。ユーザーはキーを意識しない。

### 10.3 接続設定

- 既定 `http://127.0.0.1:8787`。`SqnSync` の右クリックメニューでポート変更可。
- `GET /status` の `schema_version` 不一致は「プラグインと Squid-n のバージョン不一致」
  としてエラー表示（400 の受け身ではなくプラグイン側で先に検知する）。

## 11. スキーマ生成と CI（T5）

1. **`cargo xtask gh-schema`**: `squid-n-gh::dto` の各ルート型（`SyncModel` /
   `AnalyzeRequest` / `AnalyzeResponse` / カタログ応答）の JSON Schema を
   `grasshopper/schema/*.json` に出力する。
2. **C# DTO 生成**: quicktype（`npx quicktype`）で `SquidN.Grasshopper.Dto` に
   C# record を生成しコミットする。生成コマンドは `grasshopper/generate.sh` に固定。
   生成物には手を入れない（ロジックは `Client`/本体側に置く）。
3. **CI（GitHub Actions・ubuntu）に追加するジョブ**:
   - スキーマ鮮度: `cargo xtask gh-schema` 実行後に `git diff --exit-code grasshopper/schema`
   - 生成物鮮度: `generate.sh` 実行後に `git diff --exit-code`（quicktype のバージョンは固定）
   - `dotnet build` + `dotnet test`（DTO のシリアライズ往復・Assemble 単体テスト）
4. Rust 側にも **JSON 例のスナップショットテスト**（insta）を置き、
