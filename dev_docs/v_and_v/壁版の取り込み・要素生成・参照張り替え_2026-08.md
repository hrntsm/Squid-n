# 壁版の取り込み・要素生成・参照張り替え（2026-08, Step 7+8 本体）

**対象**: 壁版（`WallPlate`）の ST-Bridge 取り込み・壁の解析要素（`ElementKind::Wall`）の
生成（D5）・自重算定/保有水平耐力/ST-Bridge出力/GUI診断の参照張り替え
**区分**: データモデルの型移行（`WallAttr` 直接入力 → `WallPlate`／壁展開モデル経由）
**判定**: ☑ 実装済み。壁入りフィクスチャの代表スカラは型移行前後で完全一致（後述）。
残るのは GUI の断面力表示・壁属性編集タブ・3Dビューアの壁対応（Step 9）と、
取り付き壁版・T字取り付き境界の一般化（申し送り §5.14 の残課題参照）

## 対象

申し送り [床領域・壁領域の再設計](../handoff/床領域・壁領域の再設計_申し送り.md) §5.14。
着手前に dig（利用者との対話）で7問を確定した（同 §5.14 参照）。核心は D5「壁の解析要素は
準備計算からの生成物であり、入力の正である `Model` には残さない」を実装へ落とし込むこと。

## 実装の要旨

- `squid_n_load::wall_expand::expand_wall_elements(&Model) -> (Model, WallExpansionIndex,
  WallExpansionReport)` を新設。`WallRegion.wall_plate_ids` を辿り、`Enclosed` 形・
  `section` 割当あり・境界4節点の `WallPlate` から `ElementKind::Wall` を決定的に生成する
  （既存要素の最大 `ElemId` より後ろへ採番）。生成した要素ごとに、由来する `WallPlate` の
  開口・三方スリットを写した `WallAttr` を壁展開モデルへ合成して積む（既存の壁消費者
  ―自重算定・開口低減剛性・偏心率の雑壁剛性・数量拾い等―を無改修で動かすための橋渡し）。
- ST-Bridge 取り込み（`assemble.rs::build_walls`）を `ElementKind::Wall` 直接生成から
  `WallPlate` 生成へ切り替えた。直後の `rebuild_wall_regions`（結線済み）が壁領域へ帰属させる。
- ST-Bridge 出力（`export_stbridge`）・GUI診断（`run_diagnostics`）・解析各種
  （`squid_n_job::compute` の全公開関数、および `squid-n-app` 側の独自実装
  `compute_static_all`/`compute_combination`/`summary.rs` の主軸角計算）の直前で
  壁展開モデルを組み立てるよう変更した。

## 実装中に見つけた既存の想定違い

1. **`squid-n-app` の一括解析・荷重組合せが `squid_n_job::compute` を経由しない独自実装を
   持っていた。** `run_static_all`/`run_combination` は `Analysis::prepare` を直接呼ぶ
   重複実装（`app::actions::linear_static::{compute_static_all, compute_combination}`）で、
   `squid_n_job::compute` にだけ壁展開を足した最初の実装では、これらの経路から壁が
   欠落した（`snapshot_wall_bay_scalars` の member_forces 探索失敗で発覚）。両方に
   個別に壁展開を追加して解消した。根本的な重複実装の解消は別課題として残す。
2. **`Analysis<'m>` が `&'m Model`（借用）を保持するため、`Analysis::prepare` 自身の内部で
   壁展開を完結させることはできない。** 壁展開はモデルを複製する操作のため、
   `prepare(model: &'m Model) -> Self`（`Self` も `&'m Model` を保持）の内部でローカルに
   複製を作って `&'m` として返すことは借用チェッカーが許さない。単一の choke point には
   集約できず、`Analysis::prepare` を呼ぶ全箇所（`squid_n_job::compute`・`squid-n-app`
   独自実装2箇所・`summary.rs`）で個別に展開する設計にした。
3. **T字取り付き境界（5節点以上）をそのまま1要素にすると幾何が壊れる。** `wall_element_geometry`
   （`squid_n_element`）が `data.nodes.iter().take(4)` と先頭4節点しか使わない実装のため、
   5節点境界（実測: 実フィクスチャ55件中2件、3.6%）の頂点を1つ落として壁を組み立てて
   しまう。dig Q6 の当初案（「保守側フォールバック」）を利用者からの直接の疑問を受けて
   再検証し、実際には壊れた幾何を作る不具合だと訂正した。最終的に、4節点でない境界を
   持つ壁版は要素そのものを生成しない（Q6=C）。

## 検証: 壁入りフィクスチャの代表スカラが型移行前後で完全一致

`crates/squid-n-app/tests/wall_model.rs::wall_bay_model` を、生の `ElementData`＋`WallAttr`
（旧経路）から `WallPlate`＋`rebuild_wall_regions` 呼び出し（新経路）へ移行した
（`crates/squid-n-load/src/story_gen/tests.rs::wall_model` も同様に移行）。これにより
既存の回帰テストが「取り込み→壁版→壁領域帰属→壁展開→要素生成→解析」という新しい経路
全体を実際に通るようになった。

- `snapshot_wall_bay_scalars`（総重量・固有周期・壁材端力・柱頭変位）
- `snapshot_wall_ds_group_and_holding_capacity`（Qu・Ds・Qun・部材ランク）

**両スナップショットとも既存の固定値（`insta` の保存済みスナップショット）と完全一致した
（差分なし。`git status` でスナップショットファイルの変更なしを確認）。** これは dig Q5
「型移行で計算根拠を変えない」ことの直接の裏付けである。値が変わっていれば、どこかに
計算根拠の変化（バグ）が入り込んだことを意味していた。

実 ST-Bridge フィクスチャ（`crates/squid-n-app/tests/fixtures/model.stb`）の
`full_model.rs::snapshot_key_scalars` も無変化（同フィクスチャは壁版を1枚も持たないため、
壁展開自体は素通りする経路だが、他の全経路への副作用がないことの確認になる）。

## 検証: dig Q7 の新規回帰テスト3種

- **壁ラウンドトリップ**: `squid-n-io::stbridge::tests::test_wall_roundtrip_export_import`
  （`WallPlate`＋`WallRegion` を入力に ST-Bridge 出力→再取り込みし、`wall_plates` を照合）
- **断面力の `ElemId` 逆引き**: `snapshot_wall_bay_scalars` が
  `WallExpansionIndex::generated_elem_ids()` で生成 `ElemId` を動的に解決してから
  `member_forces` を引く（旧来のハードコード `ElemId(12)` を廃止。パネルゾーン生成が
  ID を消費するため実際の値は 16 だが、テストはこれをハードコードせず毎回解決する）
- **GUI診断反映**: `crates/squid-n-app/tests/wall_model.rs::
  test_wall_frame_mismatch_appears_in_gui_diagnostics`（新設）。側柱の断面材料を
  意図的に鋼へ差し替えた壁入りモデルで `App::run_diagnostics` を呼び、耐震壁と
  周辺架構の構造種別食い違いが診断へ現れることを確認する。壁展開を経由しない
  （＝旧来の `self.model` をそのまま `model_issues` へ渡す）実装に後退すると、
  `model.elements` の壁要素が 0 件のためこの検知が一切働かなくなり、この回帰
  テストがそれを検出する。
