# 壁展開モデルを見ていなかった4箇所の是正（2026-08、敵対的レビュー起点）

**対象**: D5（壁の解析要素はモデルに残さない生成物）の実装後、「壁展開モデルを
見るべき箇所が生モデルを見ている」という同じ不具合パターンが4箇所に残っていた
ことが敵対的レビューで発覚し、いずれも是正した。
1. `squid_n_job::prepare::apply_rigid_zones_and_panels`（剛域自動算定。
   `rigid_zone_consider_walls` が壁版経由の壁で恒久的に無効化されていた）
2. `App::run_design_check` → `joint_wiring::wall::check_walls`（耐震壁のせん断
   断面検定が常にスキップされていた）
3. `squid_n_design_jp::quantity::compute_quantity_takeoff`（壁の数量が積算から
   欠落していた）
4. `App::compute_holding_capacity` の部材ランク自動判定（耐震壁が告示「耐力壁の
   種別」表による判定を受けられていなかった）

**区分**: [壁版の取り込み・要素生成・参照張り替え_2026-08.md](壁版の取り込み・要素生成・参照張り替え_2026-08.md)
（申し送り §5.14）の実装レビューで発覚した回帰の是正（新機能ではない）。
**判定**: ☑ 4件とも是正済み。いずれも是正前のコードで新規回帰テストが実際に
失敗することを確認済み（偶然通るテストではない）。

---

## 発端

§5.14 の実装完了後、利用者の指示でレビュースキルを使わない敵対的レビューを行い、
以下を発見した。

- `squid_n_job::prepare::apply_rigid_zones_and_panels`（本番の呼び出し元は
  GUI の `App::apply_rigid_zones_for_analysis` と job/MCP の
  `prepare_model_for_analysis` の2箇所のみ）は、**壁展開前の生モデル**
  （D5 により `ElementKind::Wall` を1件も持たない）に対して
  `squid_n_element::beam::apply_auto_rigid_zones` を直接呼んでいた。
- 内部の `collect_rigid_zone_walls`（`squid_n_element::wall::misc_wall`）は
  `model.elements` を `ElementKind::Wall` で走査するだけなので、常に空を返す。
- 算定結果（`ElementData::rigid_zone`）はモデルへ直接書き込まれる永続フィールド
  で、`Analysis::prepare` はこれを再計算せずそのまま読む。壁展開は既存要素を
  そのまま複製するだけで `rigid_zone` を再算定しない。

結果として、`rigid_zone_consider_walls`（技術基準「柱には袖壁、梁には腰壁・
垂壁を含めた寸法で算定する」既定 true）が、壁版経由で壁が入るモデル全てで
恒久的に無効化されていた。剛域長は柱・梁の剛性そのものに効くため、全解析
（線形静解析・固有値・地震・増分解析・時刻歴）の結果を静かに誤らせる。

## 実測

全断面材料を RC に統一した検証モデル（1バイの全周RC架構＋Y=0面の耐震壁1枚。
`all_rc_src_at`——節点に集まる柱・大梁が全て RC/SRC であること。1本でも S 系が
あれば剛域そのものを設けない規則——が成立する構成）で
`squid_n_element::beam::apply_auto_rigid_zones` を直接比較した。

| | 壁要素なしで算定（是正前の実際の経路） | 壁要素ありで算定（あるべき姿） |
|---|---|---|
| 側柱 `length_i` | 125.0mm | 0.0mm |
| 側柱 `length_j` | 125.0mm | 1262.5mm |
| 壁頂部大梁 `length_i`/`length_j` | 100.0mm / 100.0mm | 1500.0mm / 1500.0mm |

壁の有無で剛域長が桁違いに変わることを直接確認した。

**既存の `wall_bay_model` 回帰網（§5.14）がこれを検知できなかった理由**:
同フィクスチャは「耐震壁と周辺架構の構造種別食い違い」検定用に周囲の柱・梁を
意図的に RC/鋼混在にしており、各節点が必ず1本は鋼部材と接する。`all_rc_src_at`
が全節点で false になるため、壁の有無に関わらず剛域長が常に 0 になり、この
不具合を偶然素通りしていた。**「回帰検知網が新しい経路を実際に通っている」
ことの確認は、通過そのものだけでなく検知対象の値が実際に動きうる構成かどうかも
見る必要がある**、という教訓（§5.14 の V&V は経路の通過は確認していたが、
値が動く構成かどうかまでは検証していなかった）。

副次的に、`crates/squid-n-app/src/app/preparation.rs`
（`build_prep_member_stiffness` の `has_wall_element` ゲート）も同じ理由で
「準備計算」タブの壁上下大梁剛性割増し確認表が機能しなくなっていた。ただし実害は
表示のみで、実際の解析（`construct.rs` が壁展開済みモデルに対して
`stiffness_breakdown` を呼ぶ）は正しく壁上下大梁の剛性割増しを適用していた
（`factory/mod.rs` の要素構築は常に壁展開済みモデルを受け取るため）。

## 是正方針（dig で確定）

- `apply_rigid_zones_and_panels` 自身が内部で壁展開し、算定した `RigidZone` を
  既存要素のインデックス対応で非展開モデルへ書き戻す（仕口パネルは壁に依存
  しないため従来どおり非展開モデルへ算定する）。
- `squid-n-element` への `squid-n-load` 依存追加（自重算定と同じ「クレート内で
  完結」パターン）は採らない。`squid-n-element` は `squid-n-load` に依存して
  おらず、新しい依存辺を作ると将来の循環依存リスクになる。`squid-n-job` は
  両方に依存済みのため、`apply_rigid_zones_and_panels`（本番の唯一の呼び出し元）
  を直すだけで GUI・job/MCP の両方が無改修で恩恵を受ける単一チョークポイントで
  ある。
- `has_wall_element`（準備計算タブの確認表）も同じ波で是正する。
  `build_prep_member_stiffness` も内部で壁展開モデルを都度組み立てて判定する
  （`App` にキャッシュは持たせない。§5.14 の「都度計算」方針を踏襲）。
- 回帰テストは `squid-n-job` 層に全周 RC の新規最小フィクスチャを追加する
  （既存 `wall_bay_model` は RC/鋼混在の構造種別食い違い検定用のため手を
  入れない）。

## 実装

- `squid_n_job::prepare::apply_rigid_zones_and_panels`（`crates/squid-n-job/src/prepare.rs`）
  を、壁展開モデルで `apply_auto_rigid_zones` を実行し、結果の `RigidZone` を
  先頭 `model.elements.len()` 件（壁展開は既存要素の末尾へ追記するだけなので
  展開前後で 1:1 対応する）だけ非展開モデルへ書き戻す実装へ変更した。
- `crates/squid-n-app/src/app/preparation.rs::build_prep_member_stiffness` が
  `self.model` の代わりに都度組み立てた壁展開モデルを走査するよう変更した。
- 回帰テスト `apply_rigid_zones_considers_wall_plates`
  （`crates/squid-n-job/src/prepare.rs`）を新設した。全周RCの1バイ架構＋壁1枚を
  直接構築し、`apply_rigid_zones_and_panels` を壁あり/なしそれぞれに適用して
  剛域長が異なることをアサートする。
- **性能ガード（advisorのレビューで指摘）**: 上記2箇所は解析エントリの都度
  （`ensure_preparation` 経由で）呼ばれるため、無条件に `expand_wall_elements`
  （`model.clone()`。要素数比例のコスト）を呼ぶと、壁を1枚も持たないモデル
  （実 ST-Bridge フィクスチャは現状すべて該当する）でも常に複製を払うことになる。
  `squid_n_load::wall_expand::model_has_wall_plates_to_expand` を新設し、
  壁を持たないモデルでは複製を経ずに従来どおり非展開モデルへ直接算定する。

  `apply_rigid_zones_considers_wall_plates` を実行し、
  `assertion left != right failed: ... left: 125.0 right: 125.0` で実際に

- `cargo clippy --workspace --all-targets --locked -- -D warnings`: 0 警告
- `cargo clippy -p squid-n-app --all-targets --features gui --locked -- -D warnings`: 0 警告
- `cargo clippy -p squid-n-mcp --all-targets --features mcp --locked -- -D warnings`: 0 警告
- `cargo fmt --check`: 差分なし
- `wall_bay_model` の既存スナップショット（`snapshot_wall_bay_scalars`・
  `snapshot_wall_ds_group_and_holding_capacity`）は無変化（`git status` で
  スナップショットファイルの変更なしを確認）。同フィクスチャは
  `all_rc_src_at` が常に false のため、この是正の影響を受けない構成である

## 追加で発覚し是正した3件（剛域の是正後のレビューで発覚）

剛域の是正を終えた後のadvisorレビューで、同じ「生モデルを渡し壁展開モデルを
見ていない」パターンが他に3箇所見つかった。いずれも実際に実行して不具合を
再現した上で是正し、回帰テストを追加した（是正前のコードで実際にテストが
失敗することを確認済み）。

### ① `App::run_design_check` → `check_walls`（耐震壁のせん断断面検定）

`run_design_check`（`crates/squid-n-app/src/app/actions/design/check.rs`）は
`&self.model`（生モデル）を渡していたが、渡す `results.member_forces` は壁展開
済みモデルで解いた結果のため壁の `ElemId` を含む。`check_walls` はこの `ElemId`
を `model.element(*eid)` で引き直すため、生モデルには存在しない壁の `ElemId` に
対して毎回 `None` となり `continue` していた——**耐震壁のせん断断面検定が
常にスキップされていた**（安全性に直結する検定が実行されないまま「検定結果」
として GUI・MCP へ返っていた）。

**実測**: `test_wall_shear_check_appears_after_run_design_check`
（`wall_model.rs`）を是正前のコードで実行すると、`joint_checks` のラベルが
`["接合部(RC)", "接合部終局(RC)", ..., "パネルゾーン(S)", ...]` のみで
"耐震壁" を含む行が一切現れないことを確認した。

**是正**: `run_design_check` の冒頭で壁を持つモデルなら壁展開モデルを組み立て、
`run_member_design_checks` へ渡すよう変更した。MCP側の同等経路
（`crates/squid-n-mcp/src/job/design_check.rs::compute_design_check_job`）も
同じ理由（`work`＝壁展開前の準備済みモデルをそのまま渡していた）で同様に
是正した。回帰テスト `test_wall_shear_check_appears_after_run_design_check` で
`joint_checks` に "耐震壁" ラベルの検定結果が現れることを固定した。

### ② `squid_n_design_jp::quantity::compute_quantity_takeoff`（数量拾い）

GUI（`quantity_view.rs`）・レポートCSV（`summary.rs::build_quantity_csv`）・
MCP（`squid-n-mcp/src/query.rs::quantity_takeoff_json`）のいずれも生モデルを
渡しており、壁の数量（コンクリート体積・型枠面積等）が積算から静かに欠落して
いた。

**実測**: `test_wall_quantity_via_wall_plate_is_included`
（`squid-n-design-jp::quantity::tests`）を是正前のコードで実行すると、
`MemberCategory::Wall` の品目が一切現れず（`[Column, Column, Girder,
FoundationGirder]` のみ）失敗することを確認した。

**是正**: `compute_quantity_takeoff` 自身が内部で壁展開するよう変更した
（自重算定 `enumerate_self_weight` と同じパターン。単一のチョークポイントで
直せるため、GUI・レポートCSV・MCP の3つの呼び出し元は無改修）。回帰テスト
`test_wall_quantity_via_wall_plate_is_included` を新設した。

### ③ `App::compute_holding_capacity` の部材ランク自動判定

自動判定（`design_rank_auto == true` のときのみ経路に入る）が
`self.model.elements`（生モデル）を走査していたため、壁が `ElementKind::Wall`
として分類されず、告示「耐力壁の種別」表（τu/Fc）による耐力壁のランク判定が
一度も実行されなかった。`design_frame == FrameType::RcWall`（耐力壁付き）を
宣言していても、耐力壁が層内に1枚もない扱いになり、βu を使わない簡易 Ds 表へ
フォールバックしていた（`ds_beta_u_unavailable = true`）。

既存の `snapshot_wall_ds_group_and_holding_capacity` は `design_rank_auto` の
既定値 `false` のままこの分岐を一度も通っておらず検知できなかった（剛域の
不具合が `all_rc_src_at` 常時 false で検知できなかったのと同じ「回帰網が
経路自体を通っていない」パターン）。

**実測**: `test_holding_capacity_auto_rank_detects_wall`（`wall_model.rs`）を
是正前のコードで実行すると `ds_beta_u_unavailable` が `true` のままで失敗する
ことを確認した。

**是正**: `compute_holding_capacity` の部材ランク自動判定ループが、都度組み立てた
壁展開モデルを走査するよう変更した。回帰テスト
`test_holding_capacity_auto_rank_detects_wall` を新設し、
`design_rank_auto=true` で `ds_beta_u_unavailable` が `false` になる（＝耐震壁が
検出される）ことを固定した。

## 追加確認（③是正の波及範囲）

`compute_holding_capacity` の是正では、ループの反復元（`for elem in &model.elements`）
だけでなく、ループ本体内の 17 箇所の `self.model` 参照も併せて壁展開モデル
（`model`）へ張り替えた（一括置換）。反復元以外の張り替えが安全かを個別に
確認した: 本体が読むのは `model.sections.get(sid.index())`（`elem.section` 経由）
と `model.nodes.get(nid.index())`（節点 ID 経由）の 2 箇所のみで、いずれも
ID/インデックスをキーにした参照であり、`elements` を位置参照する箇所は無い
（壁展開が追記するのは `elements` と `wall_attrs` のみで、`sections`/`nodes` は
展開前後で同一）。したがって非壁要素側の判定（断面・材料・部材長・鋼断面
判定など）は壁展開モデルを経由しても値が変わらないことを確認済み。

## 追加確認（perf_probe.rs の測定範囲）

`crates/squid-n-app/tests/perf_probe.rs` のステージ 4 は
`squid_n_element::beam::apply_auto_rigid_zones` を直接呼んでおり、
`apply_rigid_zones_and_panels` の壁展開ガード（`model_has_wall_plates_to_expand`）
を経由しない。同ファイルの合成モデルは壁を持たないためガードは常に
「壁展開なし」分岐を取り、この測定値は今回の是正と挙動上一致するが、
壁入りモデルでの壁展開分岐のコストはこの測定の対象外である（未測定）。
詳細は perf_probe.rs 冒頭のモジュール doc コメントに追記した。
