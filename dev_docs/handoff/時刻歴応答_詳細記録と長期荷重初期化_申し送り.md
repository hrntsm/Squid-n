# 時刻歴応答解析: 詳細記録（ThRecording）と長期荷重初期化 — 申し送り

## 実装範囲

`crates/squid-n-solver/src/dynamic/timehistory/` を対象に、以下を実装した。

1. **詳細記録 `ThRecording`**（`result.rs`）を新設し、線形（Newmark-β、`linear.rs`）・
   線形（HHT-α、`hht.rs`）・非線形（`nonlinear.rs`）の 3 経路すべてで記録するようにした。
   - `ResponseResult::recording: Option<ThRecording>` を `#[serde(default)]` で追加（.scz 後方互換）。
   - 記録の組立ロジックは新モジュール `recording.rs`（`ThRecorder`）に集約し、3 経路で共有している。
2. **非線形時刻歴の長期荷重初期化**（`nonlinear.rs`）。
   - `NonlinearThCfg { max_iter, tol, use_kg, apply_long_term, record_every }` を新設し、
     `nonlinear_time_history_analysis` の末尾引数（旧: `use_kg, max_iter, tol` の 3 引数）を
     このフィールドを持つ 1 構造体に置き換えた（破壊的変更。呼び出し元は本モジュールの
     `tests.rs` のみ）。
   - `apply_long_term=true`（既定）で、プッシュオーバーの長期載荷フェーズ（`pushover::driver.rs`）
     と同じ経路・同じ漸増規約（5 分割＋収束失敗時の増分半減）で長期荷重を静的 Newton 反復で
     載荷し、要素状態を commit してから時刻歴を開始する。長期荷重ベクトル `f0` は時刻歴を
     通じて一定の外力として毎ステップ加算する（プッシュオーバーの `f0+λ·q` と同じ扱い）。
   - `initial_disp`/`initial_vel` は「長期解からの増分」として扱う。時刻歴の初期変位 `u0` は
     長期解の変位＋`initial_disp` であり、以降の応答（`peak_disp`・`recording` の全量）は
     この全変位を含む。
3. **バグ修正**: 非線形時刻歴の初期剛性組立（Rayleigh/初期剛性比例減衰の参照剛性）が
   `use_kg` を無視していた（`let _ = use_kg;`）。`crate::pushover::assemble_k`
   （Newton 反復内で使う関数と同一）に置き換え、`use_kg` を反映するようにした。
   あわせて、この初期剛性の組立を長期荷重載荷**後**（かつ動的初期変位 `initial_disp`
   反映**前**）に行うよう順序を変更した。減衰行列の参照剛性は「長期荷重下の構造」を
   基準とするのが物理的に妥当なため。

## `ThRecording` の最終形と設計判断

```rust
pub struct ThRecording {
    pub record_every: usize,
    pub frame_time: Vec<f64>,
    pub node_disp: Vec<Vec<[f64; 6]>>,      // [frame][node_idx]
    pub story_x: StoryResponse,
    pub story_y: StoryResponse,
    pub member_forces: Vec<Vec<Option<squid_n_element::beam::MemberForces>>>, // [frame][elem_idx]
    pub peak_member_forces: Vec<Option<squid_n_element::beam::MemberForces>>, // [elem_idx]
}

pub struct StoryResponse {
    pub stories: Vec<squid_n_core::ids::StoryId>,
    pub story_weight: Vec<f64>,
    pub story_shear: Vec<Vec<f64>>,   // [frame][story]
    pub floor_accel: Vec<Vec<f64>>,
    pub floor_vel: Vec<Vec<f64>>,
    pub floor_disp: Vec<Vec<f64>>,
    pub peak_shear_coeff: Vec<f64>,
}
```

- **方向の扱い**: 加振方向（X/Y）を自動選択せず、`story_x`/`story_y` として**常に両方向**を
  記録する設計にした（`ResponseHistory` の記録方向自動選択とは独立）。UI が方向別に
  階応答グラフを描けるようにするための判断。加振されていない方向（例: `accel_y` 未入力）
  でも、その方向の自由度に生じる応答（ねじれ・偏心による連成等）をそのまま記録する。
- **階の並び**: `model.stories` と同じ並び（下層→上層）をそのまま採用した。既存の
  `update_story_drift`/`pushover::response::compute_story_shear` も同じ前提（`model.stories`
  は既に下→上に整列済み）に依っており、独自の再整列はしていない。
- **階の重量 `story_weight`**: `Story::seismic_weight`（設計用地震用重量）をそのまま使う。
  慣性力ベースの層せん断力係数 `Ci = max|Qi| / Σ(j≧i) Wj` の分母に使う値として、
  プッシュオーバー等の他解析と定義を揃えるため。ノード質量から再計算する方式は採らなかった。
- **階の応答（floor_accel/vel/disp）**: 階に属する節点（`Story::node_ids`）の質量加重平均
  （`Node::mass` の当該方向成分を重みとする）。質量が全節点ゼロの階は単純平均にフォールバック。
- **層せん断力**: 慣性力ベース（内力ベースの `pushover::compute_story_shear` とは別実装）。
  `Σ_(dof∈階) M·r[dof]·(相対加速度+地動加速度)` の符号反転で、既存 `history::record_history_step`
  のベースシア算定の層別版になっている（1 層のみのモデルでは両者が厳密に一致することを
  テストで確認済み、`test_story_shear_matches_base_shear`）。
- **記録の間引き**: `record_every` ステップごとに 1 フレーム。既定は自動決定
  （`(n_steps/1000).max(1)`、`recording.rs::auto_record_every`）。線形（Newmark-β）・
  HHT-α の 2 経路は間引き量を指定する公開 API を追加しておらず、常に自動決定のみを使う
  （呼び出し元を増やさないための判断）。非線形経路のみ `NonlinearThCfg::record_every` で
  明示指定できる。**UI 側で間引き量を選ばせたい場合は、線形/HHT-α にも同様のオプション
  引数を追加する必要がある**（既存呼び出し元は `statics::analysis::Model::time_history`/
  `time_history_hht`（`statics/analysis/mod.rs`）の 2 箇所のみで、影響範囲は小さい）。
- **`peak_disp`・`peak_member_forces`・`peak_shear_coeff`**: 全ステップで更新し、間引かない
  （メモリを圧迫する時系列本体だけを間引く方針）。
- **部材内力 `member_forces`**: 線形経路は `ElementBehavior::recover_forces`（弾性 behavior を
  ループ前に 1 回構築し使い回す）、非線形経路は `ElementBehavior::state_member_forces`
  （現在の committed 状態から復元）。内力分布を持たない要素は `None`。

## 未対応・申し送り事項（UI 配線担当エージェント向け）

- **app / mcp クレートの UI 配線は未着手**（本タスクのスコープ外）。`SavedResults`
  経由の .scz 保存では `recording` フィールドは自動的に保存・復元されるが（`#[serde(default)]`）、
  ビューア側（3D アニメーション・層応答グラフ・部材履歴パネル）は `result.recording` を
  まだ一切参照していない。
- 線形（Newmark-β）・HHT-α 経路には `record_every` を指定する公開引数が無い
  （常に自動決定）。UI 側で間引き量を選択させたい場合は、上記 2 関数にも
  `record_every: Option<usize>` を追加する対応が必要。
- `ThRecording::member_forces`/`peak_member_forces` の要素順は `model.elements` の添字順
  （`node_disp` も `model.nodes` の添字順）。UI 側でモデルと突き合わせる際はこの前提に従うこと。
