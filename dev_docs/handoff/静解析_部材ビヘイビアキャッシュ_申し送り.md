# 静解析: `Analysis` 部材ビヘイビアキャッシュ 申し送り

作成日: 2026-07-29
対象コード:
`crates/squid-n-element/src/common/behavior.rs`（`ElementBehavior` トレイト定義）、
`crates/squid-n-solver/src/statics/{mod.rs,analysis/mod.rs,linear/mod.rs}`

前提: `解析高速化_第3波_申し送り.md` の残課題5「`Analysis` の部材ビヘイビアキャッシュ」
（`ElementBehavior` に `Send + Sync` 境界が無く `run_batch` の rayon 並列（`&self`
共有）でキャッシュを共有できないためトレイト変更を伴い見送り）に対応した。

## 1. 実施内容

### 1.1 `ElementBehavior: Send + Sync` supertrait 化

`crates/squid-n-element/src/common/behavior.rs` の `pub trait ElementBehavior` に
`Send + Sync` を追加した。

- 全実装型（`BeamElement` / `FiberBeam` / `ConcentratedSpringBeam` / `TrussElement` /
  `NodalSpringElement` / `IsolatorElement` / `MaxwellDamperElement` /
  `HystereticDamperElement` / `PanelZone` / `ShellElement` / `WallPanelElement` /
  `InPlaneReleasedColumn` / `MultiSpringElement` 等、`grep -rln "impl ElementBehavior for"`
  で全列挙）を確認したところ、いずれも内部に `Rc`/`RefCell`/`Cell` 等の非スレッド安全な
  型を持たず、`Box<dyn UniaxialMaterial>`（既に `Send + Sync` 境界つき）等のみで構成
  されているため、追加のフィールド変更なしに全実装型が自動的に境界を満たした。
- `Box<dyn ElementBehavior>` を使う既存箇所（`squid-n-solver` 全体、`squid-n-io` の
  チェックポイント）に `+ Send + Sync` の明示は元々なく、トレイト定義側の変更のみで
  ワークスペース全体がそのままビルドできた（`cargo build --workspace` で確認）。

### 1.2 `Analysis` の部材ビヘイビアキャッシュ（本命）

`Analysis::recover_member_forces`（`statics/analysis/mod.rs`）は、荷重ケース・組合せ
ごとに全要素で `build_behavior(elem, model)` を呼び直していた。`build_behavior` は
局所座標変換・断面/材料 clone・SRC/CFT 合成断面換算など荷重ケースに依存しない処理
のため、`prepare`/`from_parts` 時に1回だけ構築してキャッシュする方式に変更した。

- `Analysis` に `behavior_cache: Vec<BehaviorEntry>`
  （`BehaviorEntry = (Box<dyn ElementBehavior>, SmallVec<[usize; 24]>)`、
  `statics::BehaviorEntry` として `analysis`・`linear` で共有）を追加。
  `build_behavior_cache(model, dofmap)` で `model.elements` 全件ぶん
  `(behavior, behavior.global_dofs(dofmap))` を1回だけ構築する。
- `recover_member_forces` は `self.model.elements.iter().zip(self.behavior_cache.iter())`
  で参照するだけになり、ケースごとの `build_behavior` 再構築を排除した。
- `f_free_cache`（既存の荷重ベクトルメモ化）と同じ方針で扱いを揃えた:
  - `prepare`: 通常どおり構築（有効自由度0の早期リターン分岐は空 `Vec`）。
  - `prepare_load_case_gen`（求解を行わない軽量準備、K 組立・分解を省く契約）:
    `f_free_cache` と同様に構築を省き空 `Vec`（求解系を呼ばない契約のため
    `recover_member_forces` 自体が呼ばれない）。
  - `from_parts`: 荷重ケース内容だけを変えた新モデル参照に対して呼ばれる想定のため、
    `f_free_cache` と同じく新モデルで作り直す（要素・断面/材料の割当は `from_parts`
    の契約上不変のはずだが、安全側で再構築する既存方針にあえて合わせた）。
- 静解析経路の `build_behavior`（`build_nonlinear_behavior` ではない方）は常に弾性
  要素を返す（履歴状態を持たない）ため、`recover_forces` は `&self` の純関数であり、
  複数ケース・複数スレッドから安全に共有参照できることを実装から確認した。

### 1.3 `statics::linear::solve_once_inner` の同様の整理（余力対応、任意項目）

`linear_static_once`（内部は `solve_once_inner`）も、K 組立時（旧: `assemble_global_k`
内部）と内力回収ループの計2回 `build_behavior` を呼んでいた。`assemble_global_k`
自体は `common/assemble.rs`（本タスクの変更対象外）にあるため、`solve_once_inner`
内で K 組立を「要素ごとの behavior・global_dofs・局所剛性を1回だけ構築し、
`to_triplets` → `add_support_spring_diag`（既存の `pub` ヘルパを呼ぶだけ、
`common/assemble.rs` は変更していない）→ `assemble_csc`」という、
`assemble_global_k` と完全に同じ演算順の処理へインライン化し、その場で構築した
behavior を内力回収ループでも再利用するよう書き換えた。演算列は従来の
`assemble_global_k` と同一（要素 ID 順→支点ばね対角）のため結果はビット一致する。

なお、既存の `BraceIterAssembly`（引張専用ブレースの active-set 反復、第3波で導入）
は元々この最適化が適用済みだった（`behavior_active`/`behavior_disabled` を反復外で
1回だけ構築）。今回変更したのは通常経路の `solve_once_inner` のみ。

## 2. 実装上の注意点

- `Box<dyn ElementBehavior>` の型が長いため、`Vec<(Box<dyn ElementBehavior>,
  SmallVec<[usize; 24]>)>` を直接書くと clippy `type_complexity` に抵触する。
  `crate::statics::BehaviorEntry` という型エイリアスを `statics/mod.rs` に追加し、
  `analysis`・`linear` の両方から共有する形で解消した。
- `Box<dyn ElementBehavior>` の値（静的型が `dyn ElementBehavior` と確定している値）
  に対するトレイトメソッド呼び出し（`.global_dofs()`/`.recover_forces()` 等）は、
  `ElementBehavior` トレイトを `use` でスコープに入れていなくても呼び出せる
  （トレイトオブジェクトの vtable がメソッド集合を直接持つため、ジェネリック境界
  経由の通常のトレイトメソッド解決とは扱いが異なる）。このため
  `statics/analysis/mod.rs` では `use squid_n_element::behavior::ElementBehavior;`
  が最終的に不要になり削除した（clippy `unused_imports` で検出）。

## 4. ベンチ結果（`parallel_bench`、同一環境・同一コード内での前後比較）

作業ブランチ上で本変更のみを一時的に取り除いた状態（`git stash` で対象3ファイルのみ
退避）と適用後とを、同一実行環境（コア数4、他プロセスの負荷変動あり）で交互に
実行して比較した。

| 実行 | 並列（Auto）組合せ16件一括 |
| --- | --- |
| 変更前（本タスク分のみ除去） | 6.493 s |
| 変更後 | 0.419〜1.235 s（実行毎の外部負荷変動あり、複数回の実測値） |

「成功 16」「成功 2」は変更前後とも維持。負荷変動はあるが、**荷重組合せバッチの
支配コストだった `build_behavior` の再構築をケースごとに排除したことで、
おおむね5〜15倍の高速化**を確認した（第3波申し送りが記録した参考値「並列16件
約4.4秒」からも大幅な改善）。`prepare`（K組立+分解、本変更の対象外）の所要時間は
変更前後で誤差範囲内（本変更はここに影響しない）。
