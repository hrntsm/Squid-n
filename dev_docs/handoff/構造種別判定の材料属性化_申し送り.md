# 構造種別の判定を材料の属性へ移す 申し送り

関連文書: [仕口パネル_対象接合部とオフセットの見直し_申し送り.md](仕口パネル_対象接合部とオフセットの見直し_申し送り.md)

前回の申し送り §4「残課題」のうち、接合部トポロジの照会先の分散と `is_steel`（材料名の
前方一致）の残存に着手した。着手後に利用者から判定方式そのものの変更方針が示され、
「材料に鋼・コンクリートの属性を必ず持たせ、それで判定する」形へ設計を変えている。

## 1. 何が問題だったか

### 1.1 構造種別の判定が 5 箇所に分散し、規則が食い違っていた

| 箇所 | 判定方法 |
|---|---|
| `squid_n_core::structure_kind`（旧 2 値） | 断面形状 → 材料の `fc`/`fy` → 既定 RcSrc |
| `joint_wiring/common.rs::is_steel` | 材料名の前方一致（`SS`/`SN`/`SM`/`STK`/`ST`/`SA`/`BC`） |
| `StoryStructure::of_section_shape` | 断面形状のみ |
| `quantity::structure_kind` | 断面形状優先、形状がないときだけ材料名 |
| `stbridge/export.rs::kind_structure` | 断面形状優先、形状がないときは `Fc` 前方一致 |

材料名の前方一致は独自名の鋼材を取りこぼす。断面形状主体の判定は、H 形のコンクリート
部材や矩形断面の鋼部材を表現できない。

### 1.2 断面形状の列挙漏れが黙って RC へ落ちていた

`pushover/hinge.rs` の `is_steel_shape` は `SteelBuiltH`・`SteelFlatBar`・`SteelRoundBar`・
`SteelLipChannel` を列挙しておらず、これらの断面が鋼の全塑性モーメントではなく
`σy·Ze` のフォールバックで評価されていた。

## 2. どう直したか

### 2.1 `MaterialCategory` を `Material` の必須フィールドにした

`Steel` / `Rebar` / `Concrete` の 3 値。プリセット追加は選んだ分類がそのまま入り、
直接入力は E・ν・ρ と同じく必須の入力項目。材料一覧に「区分」列を置き、後から
確認・変更できるようにした（`SetMaterialCategory` コマンド）。

**SRC・CFT は材料ではなく断面側で判定する。**これらは 1 つの材料では表せない複合断面で、
`SrcRect` は内蔵鉄骨のグレードを断面に持ち、CFT は材料の `Fc` を充填コンクリートの
強度として使うため。利用者の判断による。

### 2.2 判定順を `squid_n_core::structure_kind` に一元化した

1. 断面形状が複合断面（`SrcRect` → SRC、`CftBox`/`CftPipe` → CFT）
2. それ以外は材料の区分（`Steel` → S、`Concrete`/`Rebar` → RC）
3. 材料が解決できない場合だけ断面形状の系統で補う（`shape_default_kind`）
4. 断面形状もなければ RC

手順 3 はレビューで見つけた退行への対処。部材テーブルから追加した部材は
`material: None` で作られるため、材料未割当の純鉄骨ラーメンが一律 RC になり、
`apply_auto_rigid_zones` が RC の剛域長（柱 λ=200mm 等）を入れて架構が硬くなっていた。

`shape_composite_kind` と `shape_default_kind` はどちらも網羅 `match` で、
`SectionShape` にバリアントが増えたときの追随漏れはコンパイルエラーになる。

### 2.3 判定を使う側をすべてこの 1 箇所へ寄せた

| 用途 | 畳み込み |
|---|---|
| 剛域長の算定式・仕口パネルの対象 | `StructureKind::is_steel_like()`（S・CFT） |
| 略算周期の構造種別 | `StoryStructure::of_structure_kind`（CFT → SRC） |
| 断面検定の式の選択 | `squid_n_design_jp::checker_for`（4 種別） |
| 数量積算・ST-Bridge 書き出し | `StructureKind::label()`（4 種別） |

`is_steel`（材料名の前方一致）は 5 箇所すべて削除した。検定器の 4 分岐 `match` が
3 ファイルに重複していたのも `checker_for` へ集約した。

### 2.4 ヒンジ式だけは配筋を持つ形状を優先する

`hinge.rs` の分岐は `(&sec.shape, kind)` のタプル `match` だが、第 1 アームの条件は
`(Some(RcRect | RcCircle), _)` とし、材料の区分に依らず RC の式を使う。

`plastic_modulus_strong(RcRect)` は `None` を返すため `Zp = 1.12·Ze` に落ち、
700 角の RC 柱で `My ≒ 16,500 kN·m`（真値の 20 倍以上）になる。増分解析で曲げヒンジが
一切発生せず保有水平耐力を過大評価するため、ここだけは形状を優先させる。

### 2.5 `NodeAdjacency` を core へ置いた

「節点 → 接続する線材要素の添字」を 1 回だけ構築する。剛域算定・パネル生成・
座屈長さ係数 K の剛度比 G の 3 箇所が共有する。`buckling.rs` の `BeamNodeIndex` は
`NodeAdjacency` の空ラッパーになったので廃止した。

## 3. 既存挙動への影響

### 3.1 スキーマ版は 1 のまま据え置いた

`Material` に必須フィールドを追加したため、本変更前に保存した `.scz` は
`rmp_serde` のデコードエラーになる。利用者の判断で後方互換は取らない方針であり、
`CURRENT_SCHEMA_VERSION` も 1 のまま置いている。`migrate` が意図する
`UnsupportedVersion` の明示エラーではなく、原因の分かりにくいデコードエラーとして
出る点は把握したうえでの選択。

### 3.2 ST-Bridge 取込の区分は名前 → 物性の順で決まる

`category_of_grade` がグレード名から決め、決まらない場合は `Fc` を持つものを
コンクリート、`Fy` だけを持つものを鋼材、どちらもないものをコンクリートとする。
**判断がつかない場合にコンクリートへ寄せるのは意図的**で、RC 部材を誤って鋼材にすると
`SteelDesign` が素の断面積で許容応力度を評価し、検定比がほぼ 0 で通ってしまうため。
推定した材料名は `ImportReport::notes` で通知する。

### 3.3 CFT 部材が幅厚比表・部材ランク判定に必ず入るようになった

`elem_is_steel` が `is_steel_like()`（S ∪ CFT）になったため、材料名に依らず CFT が
鋼側の分岐に入る。旧実装では CFT 柱の材料名を「Fc36（充填）」等にしていると
その柱にランクが付かなかった。今後は `max_width_thickness(CftBox)` で FA〜FD が付き、
**既存モデルの Ds が変わることがある**（充填効果の緩和なしで安全側方向）。

### 3.4 階の構造種別が材料主導になった

`StoryStructure` は断面形状のみで判定していたが、部材の構造種別からの畳み込みへ
変えた。H 形の断面にコンクリート材料を割り当てた部材は、その階を RC 側に数える。
また、断面も材料も未割当の部材は集計から除く（旧実装は断面形状がない部材を除いていた）。

### 3.5 非線形解析の入力チェックが 2 つ増えた

- 配筋を持つ断面（RC 矩形・RC 円形）に鋼材区分の材料
- 線材の材料に鉄筋区分

いずれも既存モデルで該当があれば増分解析・時刻歴が停止する。形鋼の断面に
コンクリート材料を割り当てるのは**誤りとしない**（H 形のコンクリート部材は成立する
入力であり、本変更が対応したかったもの）。

## 4. 残課題

- **`SteelBuiltH`・`SteelFlatBar`・`SteelRoundBar`・`SteelLipChannel` の `Zp` が未実装**。
  列挙漏れの修正でこれらが鋼のアームへ入るようになったが、
  `plastic_modulus_strong` が未対応のため `Zp = 1.12·Ze` に落ちる。平鋼の真の形状係数は
  1.5、中実丸鋼は 1.698 なので `Mp` を 25〜34% 過小評価する（この用途では安全側）。
  非対称組立 H は `plastic_modulus_strong` を実装すれば正確に出せる
- **`panel_gen` 以外に `resolve_panel_joint` の全要素走査が残る**。
  `springs/panel.rs::resolve` が `&model.elements` を渡しており、パネル数 × 要素数。
  要素生成 API に隣接マップを通す必要があるため見送った
- **閾値 0.8/0.2（|ez| による柱・梁・斜材の判定）が 6 ファイル・10 箇所に直書きされている**。
  `panel_zone.rs`（`COLUMN_EZ`）のほか `joint_wiring/common.rs`、`app::member_kind_of`、
  `app/viewer/th_detail.rs`、`design-jp::ultimate::geometry`、`design-jp::steel::buckling`、
  `mcp::job::design_check`。`NodeAdjacency` を「分類済み」に拡張すれば同時に解ける
- **`rigid_zone_with_adjacency` は j 端に `nodes[nodes.len()-1]` を使う**が、
  `NodeAdjacency::build` は `nodes.iter().take(2)` で両端しか見ない。現状 3 節点以上の
  `Beam` 要素は生成箇所が 1 つもないので影響しないが、導入すると j 端の直交せいが
  0 になる
- **`SectionField::PanelThickness` は f64 の 0 を「未入力」の番兵に使う**。
  `SetMaterialField` の `Option<f64>` と流儀が揃っていない
- **区分と断面形状の矛盾を線形解析でも通知したい**。今の入力チェックは非線形解析の
  入口にしかなく、断面検定・数量積算だけを回す場合は素通りする
