# 要素の振る舞いの定型集約とクレート階層の整理 — 申し送り

作成日: 2026-09-03
対象コード: `crates/squid-n-element/`、`crates/squid-n-solver/`

この申し送りでは、`ElementBehavior` の実装に集中していた定型の重複を集約した経緯と、
その過程で見つかった表示の欠落、あわせて実施した 2 クレートの階層整理を記録します。

## 背景

着手にあたり、テストコードを除いた本体を機械的にクローン検出しました。
その結果、重複は `squid-n-element` の `ElementBehavior` 実装 14 個に集中していることがわかりました。

塊は 3 つあります。

| 塊 | 規模 |
| --- | --- |
| `global_dofs` の節点自由度収集 | 10 個が手書き。`if let Some/else` 版・`map_or` 版・`map().unwrap_or()` 版の 3 通りに書き方が割れていた |
| committed / trial 変位の状態機械（6 メソッド） | 節点バネ・トラス・弾性梁・シェルの 4 個がバイト一致 |
| 委譲ラッパの手書き転送 | 3 個が `self.inner.<同名>()` を 10〜18 メソッド分書いていた |

**この形の重複はすでに 2 回実害を出しています。**
1 回目は記録済みで、`IsolatorElement` と `HystereticDamperElement` に
`serialize_checkpoint` / `deserialize_checkpoint` の実装が漏れ、レジューム時に履歴が
初期化されていました（[実装レビューと重複統合](実装レビューと重複統合_申し送り.md) §1.6）。

2 回目は今回見つけたもので、まだ直っていませんでした。次節に記します。

## 見つかった欠落 — MS 要素のファイバー断面の塑性化マップ

`MultiSpringElement` が `fiber_section_states` の委譲を書き忘れていました。

このメソッドはトレイト側に既定値（`None`）があるため、書き忘れてもコンパイルは通ります。
`MultiSpringElement` の内側は `FiberBeam` で状態を持っているのに、既定の `None` が返り、
増分解析の結果を組み立てる `pushover::driver` がこの要素から状態を収集できませんでした。
その結果、ヒンジ詳細ウィンドウの「ファイバー断面の塑性化マップ」が MS 要素でだけ空になっていました。

意図的な省略ではありません。根拠は 3 つあります。

- MS 要素の実体は `FiberBeam::build_plastic_zone` で、`Fiber` 要素と同一の定式化である
  （端部断面の分割数だけが粗い）
- ヒンジ詳細の対象判定 `is_axial_bending_member` は MS を明示的に列挙しており、
  塑性率（`ductility_probe`）は委譲されている
- 同じ立場の `PanelOffsetMember` は当初から `fiber_section_states` を委譲している

## 決めたこと

着手前に dig で 9 問を確認し、次の形に決めました。

| 問い | 決定 |
| --- | --- |
| 委譲の転送漏れ防止 | `macro_rules!` の転送マクロ。`delegate` クレートは例外指定ができず目的を果たさない |
| 弾性 4 要素の状態機械 | マクロで 6 メソッドを生成。フィールドは各型に残す |
| 見つかった欠落の是正 | 移設コミットでは一時的に据え置き、次のコミットで是正する |
| 再エクスポート整理の同梱 | 同じブランチに含める（コミットは分ける） |
| 再エクスポートの到達点 | グロブ・モジュール別・`mod` の非公開宣言をすべて廃し、階層パスへ全面移行 |
| element の `common` | 解体してクレート直下へ出す |
| solver の範囲 | 逆依存の解消と再エクスポート整理まで |
| 上書きを持つラッパの扱い | 全メソッドの `forward` / `custom` を列挙させ、漏れをコンパイルエラーにする |
| solver の `common` | 残す |

element の `common` を解体して solver の `common` を残すのは、一見すると不揃いに見えます。
ですが適用している基準は同じで、**そのくくりに説明力があるか**の一点です。
element の `common` は中身が `behavior` と `transform` の 2 つだけで、しかも `behavior` は
クレート全体の契約そのものですから、部分集合をくくる名前として成り立ちません。
一方 solver の `common` は 6 モジュール 1812 行が「どの解析種別にも属さない共有機構」という
一貫した性格を持ち、そこへ今回 `tangent` を引き上げるので、くくりはむしろ強くなります。

## 変更内容

### 節点自由度の収集を共通ヘルパへ

`behavior::node_global_dofs` を新設し、手書きの 10 個を置き換えました。
`FiberBeam` だけは `beam_global_dofs` という固有メソッドに切り出したうえで `6` を直書きして
おり、他の 9 個と揃っていませんでした。これも同じヘルパへ寄せています。
追加自由度を持つ要素向けに、末尾へ足す `push_node_global_dofs` と
`push_panel_global_dofs` も用意しています。仕口パネル側にあった `0..2` の直書きは
`PANEL_DOF_PER_NODE` 経由になりました。

挙動は変えていません。3 通りの書き方（`map_or` 版・`if let Some/else` 版・
`map().unwrap_or()` 版）は元から同じ結果を返しており、番兵の値・並び順・欠番の扱いは
いずれも従来と同一です。

### 弾性要素の定型を `elastic_disp_behavior!` へ

節点バネ・トラス・弾性梁・シェルの 4 要素は、要素の状態が「全体系の committed / trial 変位」
だけで表せる点で共通しています。`internal_force` と状態管理 6 メソッドを 1 つのマクロにまとめました。

材料履歴やばねの状態を併せ持つ要素は対象外です。
`FiberBeam`・`WallElement`・`PanelZone` などは commit / revert が変位以外にも及ぶため、
個別実装が正しい形になります。`ElementBehavior` の実装 14 個のうち、commit / revert が
変位だけで閉じるのはこの 4 個だけでした。

あわせて `internal_force` が `tangent_stiffness` を呼ぶようにしました。
従来は 4 要素とも接線剛性と同一の K の組み立て式を内力側にも書いており、片方だけ直すと
両者が静かに食い違う状態でした。シェルは自分のコメントで「接線剛性と同一の K を使う」ことを
要求していましたが、その保証は実装の対応だけに委ねられていました。

数値は変わりません。4 要素とも内力側の K の式は自分の `tangent_stiffness` と完全に同一で、
演算順序も変わらないためビット一致が保たれます。

シェルの `update_state` にあった `24.min(du.data.len())` は落とし、他の 3 要素と同じ添字
アクセスへ揃えました。この防御は到達しません。ソルバ（`elem_loop::apply_du_trial`）は
`global_dofs` の長さで `du` を作り、この 4 要素はいずれも節点数が固定長配列
（シェルは `[NodeId; 4]`、残り 3 つは `[NodeId; 2]`）なので、長さは常に `n_dof` に一致します。

食い違った場合に短い方へ黙って合わせると、変位の一部が欠けたまま解析が続行して誤った内力を
返します。panic させる方が `downcast_snapshot` と同じ方針に沿うと判断しました。

### 委譲を `forward_element_behavior!` へ

全 19 メソッドについて `forward`（内側へ委譲）か `custom`（自前で実装）かの明示を要求し、
マクロのパターンが全記載に一致することを条件にしています。
この形にすることで、次の 2 つがコンパイルエラーになります。

- `ElementBehavior` へメソッドを追加してマクロを更新すると、呼び出し側 3 箇所が
  パターンに一致しなくなる。ラッパでの扱いを決めるまでビルドが通らない
- `custom` の本体を書いたのに `forward` と記すと、同名メソッドの重複定義になる

列挙は冗長ですが、その冗長さが保証の実体です。
副次的な効果として、呼び出し側を見れば「このラッパは何を自前で持つか」が一覧で読めるようになりました。

両方の保証が実際に働くことは、着手時に確認しています。
トレイトへダミーのメソッドを足してマクロを更新すると呼び出し側 3 箇所すべてが
`no rules expected` で落ち、`custom` を `forward` へ書き換えると `E0201`（重複定義）で落ちました。

マクロ自体の置き場所は `behavior.rs`、つまり `ElementBehavior` の定義の隣です。
トレイトへメソッドを足した人が、更新すべきマクロを同じ画面で見つけられるようにするためです。
`#[macro_export]` はマクロをクレート根へ置く仕様なので、階層のパスでも参照できるよう
`behavior` モジュール内で再エクスポートし、呼び出し側は
`crate::behavior::forward_element_behavior!` と階層パスで書いています。

なお内側の呼び出しは、UFCS ではなくメソッド呼び出し構文にしています。
`PanelOffsetMember` の `inner` は `Box<dyn ElementBehavior>` で、UFCS の引数位置では
`&Box<dyn _>` から `&dyn _` への解決が効かないためです。
トレイトが呼び出し側で import されていなくても動くよう、生成する各メソッドの本体で
`use ... as _;` を行っています。

### MS 要素の欠落の是正

`fiber_section_states` を委譲へ戻しました。回帰テストを追加し、委譲を外すと落ちることも確認しています。

移設コミットでは `custom` で `None` を返して従来の挙動を据え置き、次のコミットで是正しています。
転送マクロを入れると何もしなくても直ってしまうため、意識して分けないとリファクタと挙動変更が
同じ差分に同居するためです。

このほかに手書き実装が流していなかったメソッドも新たに転送されますが、いずれも内側の型が
実装しておらず既定値のままです。`InPlaneReleasedColumn` の内側は `BeamElement`、
`PanelOffsetMember` の内側は `BeamElement` / `FiberBeam` / `ConcentratedSpringBeam` で、
`panel_moments_from` を実装するのは `PanelZone` のみだからです。

### `squid-n-element` の階層整理

`lib.rs` は自分のコメントで「階層化前の平坦なモジュールパスは従来どおり利用できる」と書いており、
AGENTS.md の「後方互換性は維持しない」と正面から矛盾していました。
加えて `pub use behavior::*;` と `pub use factory::*;` のグロブが 17 個の名前をクレート根へ漏らし、
`common` / `frame` / `springs` / `wall` の階層を実質無効化していました。

再エクスポートを 1 行も残さず、モジュールパスが階層をそのまま辿る形へ移行しました。
`common` は解体し、`behavior.rs` と `transform.rs` をクレート直下へ移しています。

旧パスとの対応は次のとおりです。書き換えたのはクレート外から 105 箇所・クレート内から 162 箇所です。

| 旧 | 新 |
| --- | --- |
| `behavior` / `transform` | 変わらず（`common` の解体により従来のパスが正になった） |
| `beam` / `concentrated` / `fiber` / `member_load` / `multi_spring` / `panel_offset` / `rigid_arm` / `truss` | `frame::` を前置 |
| `damper` / `isolator` / `panel` / `panel_gen` / `spring` | `springs::` を前置 |
| `misc_wall` / `side_column` / `wall_element` | `wall::` を前置 |

`common` を解体したことで、外部から最頻の `behavior::`（40 箇所）と
`transform::`（16 箇所）は書き換えが不要になりました。

### `squid-n-solver` の逆依存の解消

`dynamic/timehistory/nonlinear.rs` が
`crate::pushover::{assemble_k, assemble_k_cached_ref, compute_f_int, add_support_spring_f_int}`
を参照していました。時刻歴が増分解析の内部モジュールを覗く形です。

`pushover/mod.rs` はこの 4 関数を「dynamic/timehistory が参照するため」とコメントを添えて
再エクスポートしており、`assembly.rs` のモジュール doc も同じ事情を書いていました。
両者とも問題を自認したうえで維持していたことになります。

4 関数の中身は要素の現在の状態から接線剛性と内力を組み立てるもので、増分解析に固有の要素は
ありません。`common/tangent.rs` へ移し、`pushover` 側の再エクスポートを削除しました。
Newton 反復を回す解析はすべてここを通ります（増分解析・弧長法・非線形時刻歴）。

`nonlinear.rs` のコメントは「Newton 反復内の接線剛性（`assemble_k`）と不整合だった」と、
両者が同じ足場を共有すべきことを述べています。
この不整合は一度顕在化した記録であり、逆依存を放置する危険がそこに出ています。

### `squid-n-solver` の階層整理

element と同型の問題があり、`lib.rs` のコメントも同じ文言でした。
同じ到達点まで移行しています。書き換えたのはクレート外から 267 箇所・クレート内から 104 箇所です。

| 旧 | 新 |
| --- | --- |
| `assemble` / `constraint` / `newton` / `transaction` | `common::` を前置 |
| `damping` / `eigen` / `lumped_mass` / `phase_diff` / `timehistory` | `dynamic::` を前置 |
| `arc_length` / `pushover` | `nonlinear::` を前置 |
| `analysis` / `linear` | `statics::` を前置 |

solver の `common` は残しました。理由は「決めたこと」に記したとおりです。

## ドキュメントの更新

`docs/` と `dev_docs/specs/` には現在の仕様を書くので、パスの記述を新しい階層へ更新しました。
この過程で、**以前の階層化のときに更新し漏れていた記述**も見つかっています。
`dev_docs/specs/` の 4 ファイルが `squid-n-solver/src/analysis.rs` のように、
すでに存在しないファイルを指していました。あわせて是正しています。

`dev_docs/v_and_v/` と `dev_docs/handoff/` の既存ファイルは更新していません。
これらはその日付の時点の記録であり、書き換えると記録としての意味が薄れるためです。
古いパスに当たった人が解決できるよう、対応表を本書に載せてあります。

利用者向けの `docs/` は 1 箇所だけ内容を書き換えました。
「ファイバー断面の塑性化マップ」の節が対象を「ファイバー要素」とだけ書いており、MS 要素の
欠落を是正した結果と食い違うためです。ファイバー定式化の部材（ファイバー梁・マルチスプリング梁）
が対象であることを明記しました。

計算根拠そのものは変えていません。計算の内容と既定値は変わっていないためです。

## 意図的にやらないこと（残課題）

- **委譲マクロは、トレイトへのメソッド追加そのものは検出できません。** 検出できるのは
  「マクロを更新したのに呼び出し側を更新していない」状態です。マクロを更新せずに
  トレイトだけへ既定値付きのメソッドを足すと、ラッパは静かに既定値へ落ちます。
  トレイトとマクロの一覧を単一の情報源から生成すればここも塞げますが、
  `macro_rules!` の入れ子定義が必要になり、19 個の異なるシグネチャを表現するコストに
  見合わないと判断しました。`ElementBehavior` の doc に「メソッドを追加したらマクロにも
  追加すること」を明記して運用で補います
- **`custom` と記して本体を書き忘れた場合**は、既定値を持つメソッドなら静かに既定へ落ちます
  （必須メソッドならコンパイルエラーになります）。`forward` / `custom` の対応は
  呼び出し側を読めば一覧で確認できるので、これ以上の機構は入れていません
- **`squid-n-element` の残り 10 個の `ElementBehavior` 実装**は個別実装のままです。
  材料履歴やばねの状態を持つため、定型に乗せる意味がありません
