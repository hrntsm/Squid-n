# 荷重ツリーの高度化と荷重モデルの拡張 申し送り

## 1. 背景と方針

ナビゲータ（左パネル）の「荷重ケース」は、ケース名を `selectable_label` で並べるだけでした。
荷重の追加は下ドックの「荷重」タブにある追加フォームだけが導線で、荷重ケースの中身が
どうなっているのかをツリーからは追えませんでした。

この申し送りは、次の 4 つの変更をまとめたものです。

1. 節点荷重を 1 節点につき複数持てるようにし、荷重に名称と生成元を持たせた
2. ブレースの部材荷重を、材端モーメントの出ない静定分配へ変えた
3. 風荷重機能を削除した
4. ナビゲータの荷重ツリーを 3 階層にし、右クリックから荷重を追加・編集・削除できるようにした

## 2. 荷重モデルの拡張

### 2.1 節点荷重の複数化

変更前の `SetNodalLoad` は「同じ節点のエントリがあれば値を差し替え、なければ push」という
upsert でした。このため 1 荷重ケース内で 1 節点につき節点荷重は 1 件しか持てず、同じ節点へ
別々の荷重（機器荷重と吊り荷重など）を分けて定義できませんでした。

`AddNodalLoad` を追加し、変更・削除を添字指定へ組み替えています。

| コマンド | 変更前 | 変更後 |
|---|---|---|
| 追加 | （`SetNodalLoad` の副作用） | `AddNodalLoad { lc, load }` |
| 変更 | `SetNodalLoad { lc, node, values }` | `SetNodalLoad { lc, index, load }` |
| 削除 | `DeleteNodalLoad { lc, node }` | `DeleteNodalLoad { lc, index }` |
| 挿入（undo 用） | — | `InsertNodalLoad { lc, index, load }` |

添字で対象を指すのは、部材荷重（`DeleteMemberLoad { lc, index }`）と同じ規約です。
このコードベースは **ID ＝ 配列インデックス**を不変条件としており（`squid_n_core::ids`、
削除時は後続 ID を繰り上げる）、荷重にだけ安定 ID を導入するのは方式が揃いません。

求解側（`assemble_global_f`）は元から `f[active] += ...` で全件を加算しており、準備計算・
階重量の集計も全件走査のため、**複数化にともなうソルバ・集計側の変更はありません**。

### 2.2 名称と生成元

`NodalLoad`・`MemberLoad` に次の 2 つのフィールドを追加しました。

- `name: String` — 利用者が付ける名称。未入力可
- `source: LoadSource` — `Manual`（利用者入力）か `Auto`（準備計算が生成）か

`source` の導入により、準備計算の同期（`SyncSlabLoadsToCase`）は自動生成分だけを入れ替え、
同じ荷重ケースへ手入力した荷重を残せるようになりました。

変更前は `lc.nodal = self.nodal.clone()` のベクタ丸ごと差し替えだったため、DL・EX などの
自動生成ケースへ荷重を足しても次の解析実行で無言で消えていました。

入れ替えは `LoadCase::replace_auto_loads` が担い、**渡された荷重の `source` を `Auto` へ
揃えます**。手入力扱いのまま積むと次回の入れ替えで残ってしまい、同期のたびに荷重が
増え続けるためです。新規ケースを作る経路も同じ関数を通しています
（`test_sync_slab_loads_marks_content_as_auto` がこの不変条件を守っています）。

同期の要否判定（`sync_one_auto_case`）も `LoadCase::auto_loads_match` による自動生成分どうしの
比較に変えました。手入力を足しただけで同期が走ると、undo 履歴が無意味に伸びます。

### 2.3 生成元の割り当て

| 生成箇所 | `source` |
|---|---|
| 自重（`self_weight_case_content`） | `Auto` |
| 床荷重の分配（`slab_load_case_content`） | `Auto` |
| Ai 分布の水平力（`build_seismic_load_case_from_model`） | `Auto` |
| 二次部材の CMQ 変換（`resolve_nodal_to_primary`） | 変換元を引き継ぐ |
| ST-Bridge 取込（`build_load_cases`） | `Manual` |
| UI からの入力 | `Manual` |

ST-Bridge の取込荷重を `Manual` にしているのは、これが利用者の入力であり、準備計算が
作り直す対象ではないためです。`StbNodalLoad` に名称属性はないため名称は空になります。

## 3. ブレースの部材荷重

`TrussElement` は軸剛性のみを持ち、曲げ・せん断・ねじり剛性がゼロです。
にもかかわらず `consistent_load_local` は Hermite 形状関数で材端モーメントを生成しており、
ブレース自身が負担できないモーメントが外力として節点へ撒かれていました。

**この誤りは自重で既に発生していました。**
`enumerate_self_weight` は `ElementKind::Brace` を梁と同じ `Line` として扱い、
`self_weight_case_content` が鉛直下向きの等分布荷重をブレースへ与えています。

`SpanLoadTransfer` を導入し、要素種別で配り方を切り替えます。

| 方式 | 対象 | 材軸直交成分の扱い |
|---|---|---|
| `Consistent` | 梁・柱・ファイバー梁・マルチスプリング梁 | Hermite 形状関数（材端モーメントを含む） |
| `StaticallyEquivalent` | ブレース | 単純梁反力と同じ静定分配（材端モーメントなし） |

軸方向成分は形状関数が線形で静定分配と一致するため、方式によらず同じ処理を通します。
合力と作用位置の 1 次モーメントがともに保存されるので、**建物総重量・支点反力は方式を
変えても変わりません**（`brace_udl_has_no_end_moment_and_preserves_resultant` で確認）。

内力回復側（`fixed_internal_local`）も同じ方式を受け取り、ブレースでは軸力以外の固定端内力を
返しません。材軸直交成分は荷重ベクトル側で両端へ流し切っているためです。

### 3.1 残した既知の割り切り

ブレースへ載せた材軸直交成分の荷重は、**部材の設計用応力に現れません**。
トラス要素は軸力しか回復しないため、たとえば外壁の仕上げ荷重をブレースへ載せた場合、
その荷重による曲げは設計上どこにも計上されません。実部材としてのブレースが局部曲げを
受けるモデル化が必要になった場合は、ブレースを梁要素へ置き換える必要があります。

## 4. 風荷重機能の削除

風圧力の算定・WX/WY 荷重ケースの自動同期・風荷重静的解析・準備計算タブの風圧力表示を
すべて削除しました。利用者からの「直近では使わない」という判断によるものです。

### 4.1 削除したもの

| 対象 | パス |
|---|---|
| 風圧力の算定 | `crates/squid-n-load/src/wind.rs` |
| 風荷重静的解析 | `crates/squid-n-solver/src/statics/analysis/wind.rs` |
| 静的解析の設定型 | `WindStaticCfg`（`analysis/config.rs`） |
| 結果キー | `StaticCaseKey::Wind` |
| 標準ケース名 | `WX_CASE_NAME`・`WY_CASE_NAME` |
| 同期アクション | `sync_wind_load_cases_action` |
| 実行導線 | `run_wind`・`compute_wind`・`start_wind_job` |
| 算定諸元 | `AnalysisSettings` の `v0`・`roughness`・`parapet_mm` と右パネルの入力欄 |
| 準備計算の結果 | `PrepWind`・`PrepWindRow`・`build_prep_wind` と表示・CSV 出力 |
| 利用者ドキュメント | `docs/calc_basis/01_荷重/02_風圧力.md`・`docs/preparation/03_風圧力.md` |

`docs/calc_basis/01_荷重/` は節番号が連番だったため、02 を削除したあと 03 以降を繰り上げ、
本文の見出し番号と全ページの参照リンクを合わせました。

### 4.2 残したもの

**`LoadCaseKind::Wind` と多雪区域の積雪低減係数 δ2（暴風時）は残しています。**

これらを消すと、利用者が手入力した風荷重ケースの種別が `Other` になります。
`LoadCaseKind::is_long_term` は `Other` を真として扱うため、風荷重が長期応力解析へ
混入することになり、明確な誤りです。δ2 も、多雪区域の暴風時組合せ
\\( G + P + \delta_2 S \pm W \\)（令86条・82条）を手で組む際に必要になります。

`squid_n_load::combo` の `ComboInput::wind_x`・`wind_y` と `standard_combinations` の暴風
組合せ生成もそのまま残しています。組合せの算定自体は風圧力の算定とは独立です。

### 4.3 組合せ自動生成の劣化

「種別から自動生成」（`auto_generate_combinations_action`）は、方向を持つ地震・風について
標準ケース名（EX/EY・WX/WY）で方向を判別していました。WX/WY がなくなったため、風は
**種別 Wind の先頭 1 件を X 方向として扱う**フォールバック経路のみになります。

これは変更前からあった経路（標準名の風ケースが 1 つもないモデル向け）をそのまま残した
ものです。2 方向の風荷重ケースを定義しても Y 方向の暴風組合せは生成されません。
風荷重を本格的に扱う段階になったら、方向を判別する手立て（荷重ケースへの方向属性、
あるいは標準ケース名の復活）を検討してください。

## 5. ナビゲータの荷重ツリー

### 5.1 構成

「荷重ケース → 種別グループ（節点荷重／部材荷重）→ 個別の荷重」の 3 階層です。
実装は `crates/squid-n-app/src/app/nav_loads.rs` に切り出しました。

右クリックのメニューは次のとおりです。

| ノード | メニュー |
|---|---|
| セクション見出し | 荷重ケースを追加 |
| 荷重ケース | 節点荷重を追加 / 部材荷重を追加 / この荷重ケースを削除 |
| 種別グループ | 同種の荷重を追加 |
| 個別の荷重 | 値を編集 / この荷重を削除 |

メニューのクロージャ内では `self` を可変借用できないため、要求された操作を
`LoadTreeAction` へ退避し、クロージャの外で `apply_load_tree_action` が適用します。

### 5.2 自動生成荷重を表示しない判断

ツリーに並べるのは**手入力の荷重だけ**です（`LoadCase::manual_nodal`・`manual_member`）。
床荷重を分配した部材荷重は数百件に達することもあり、編集できない行の中に手入力の荷重が
埋もれるためです。

表示の切り分けは次のように決めました。

| 画面 | 自動生成荷重 |
|---|---|
| ナビゲータの荷重ツリー | 表示しない |
| 下ドック「荷重」タブ | 表示する（読み取り専用） |
| 準備計算タブの荷重集計 | 合算に含める |

下ドックに残しているのは、この画面が準備計算の結果を確認する場でもあるためです。
準備計算タブの荷重集計から自動生成分を除くと、EX の合力が 0 と表示され、ベースシアの
確認という表の目的そのものが失われます。

コマンド層でも自動生成荷重の編集・削除を Noop で弾いています（`test_auto_loads_reject_edit_and_delete`）。
UI でメニューを出さないだけでは、`.scz` の直接編集や将来の別経路から不正な操作が入ります。

## 6. 荷重の追加・編集モーダル

実装は `crates/squid-n-app/src/load_editor.rs` です。

### 6.1 対象選択を 3D ピックにした理由

対象の節点・部材は、実務規模のモデルでは数百を超えます。ID を並べた ComboBox では選べません。
また 3D の通常モードは部材しかピックせず、`selection.nodes` は空のままでした（節点は
作成モード中しか拾えませんでした）。このため 3D へ節点ピックと節点の選択ハイライト描画を
追加しています。

### 6.2 モーダルとピック待ちの往復

モーダル（`egui::Modal`）は対象選択の間だけ閉じます。

1. 「3D で選択」を押すと、入力内容を保ったまま `LoadEditor::picking` を立ててモーダルを閉じる
2. 3D クリックで仮選択（何度でも選び直せる）
3. Enter で確定してモーダルへ戻る。Esc は `pick_backup` から元の対象を復元して戻る

モードレスなウィンドウを 3D の上に浮かせる案は採りませんでした。窓が視点操作の邪魔になり、
窓の裏をクリックしたつもりの操作が拾えないためです。往復させるほうが状態がはっきりします。

ピック待ちは Enter / Esc でしか抜けない明示モードとし、既存の作成モード
（`beam_draw_mode` 等）と排他にしています。この間もアプリ全体を操作できるため、確定時に
次の 2 つを検証します。

- 対象の節点・部材が存在するか
- 編集の場合、対象がモーダルを開いた時点の内容（`snapshot`）と一致するか

2 つ目は、ピック待ちの間に他の荷重が削除されて添字がずれた場合に、別の荷重を書き換えて
しまうのを防ぐためです。

作用方向は、下書きが持つ選択肢番号ではなく**対象部材から決めます**（`is_brace` で判定）。
下書き側の番号を信じると、ブレースを選んでから Esc で取り消した場合に「対象は梁なのに
方向だけ材軸方向」という状態が残り、選択肢の範囲外を引きます。
取り消し時に方向も一緒に戻すよう `PickBackup` に方向を持たせたうえで、確定側でも対象から
決め直す二重の守りにしています。

### 6.3 タブの切り替え

3D ビューが出るのは `Tab::Model` / `Tab::Loads` / `Tab::Analysis` の 3 タブだけです。
ナビゲータは左ドックに常時表示されるため、`Results` / `Design` / `Report` からも荷重の追加を
選べてしまいます。この場合は `Tab::Model` へ切り替えてからモーダルを開きます。

## 7. 残課題

- **等分布荷重の区間は節点の移動に追従しない**（変更前からある挙動）。等分布は追加・更新の
  時点で `b = 材長` を焼き込むため、あとから `SetNodeCoord` で節点を動かしても区間は元の
  ままです。モーダルで対象を選び直したときは選択中の部材から材長を取り直すので、対象の
  変更には追従します。なおこの状態の荷重を編集で開くと、`b` が現在の材長と一致しないため
  台形として開きます（区間を焼き込んでいる事実がそのまま見える扱いです）。
- **ナビゲータの他セクションは手つかず**。部材グループ・部材一覧・結果ケース・階/レベルは
  従来どおりの羅列です。荷重ケースだけが 3 階層になり、粒度が揃っていません。
- **荷重組合せを手で組む UI がない**。組合せは「標準組合せを生成」「種別から自動生成」の
  2 つの自動生成しか作る手段がありません。風の 2 方向を扱いたい場合（§4.3）に効いてきます。
