# CMQ 図を荷重ケースの全荷重へ揃える

- 作成日: 2026-08-27
- 残課題: —

## 現状（改修前）

CMQ 図（`ViewMode::Cmq`）の描画ソースは、選択中の荷重ケースではなく、床荷重分配の
`BeamLoad` 列だった。

1. `App::refresh_beam_loads` / `sync_gravity_load_cases_action` が
   `compute_dl_beam_loads` の結果を `app.beam_loads` に書く
2. `App::cmq_display_member_loads` がそれを `slab_load_case_content` で
   `MemberLoad` へ変換する
3. `viewer/cmq.rs` が大梁ごとに C/M/Q を描く

`compute_dl_beam_loads` に入るのは、スラブ固定荷重の分配と、自立壁
（床領域アンカー）の等価面荷重（床分配へ上乗せ）だけだった。解析の「DL」ケースへは
別経路で、梁・柱・囲まれた壁の自重（`self_weight_case_content`）と、取り付く壁版の
線アンカー分布（`attached_wall_beam_loads`）が加算される。そのため、取り付く壁版の
分布荷重は応力解析の DL には載るが、CMQ 図には出ない、という不整合があった。

## 改修内容（2026-08-27、dig による設計確定）

利用者との dig で、単に「ソースを付け替える」だけでなく、応力図と同じ「軸」の
区別を CMQ 図にも持たせる設計へ広げた（下記 Q3 参照）。

### ソースの付け替え

CMQ 図のソースを `app.beam_loads`（DL 専用の中間表現）から、**表示中荷重ケースの
`member`（`LoadCase.member`）そのもの**へ付け替えた。

- 表示中ケースは `nav.focus_load_case`（荷重タブ・ナビゲータの荷重ケース一覧が
  既に持っている選択状態）をそのまま使う。応力図の `nav.focus_result` は使わない
  ── これは `app.results`（解析実行結果）からしか作られず解析未実行時は空になるが、
  CMQ 図は解析未実行でも使える診断図という現状の性質を保つため
  （`App::cmq_display_load_case`）
- 未選択時は静解析の対象決定（`resolved_analysis_target`）と同じ規約で先頭の
  荷重ケースへフォールバックする
- CMQ 図の画面には新しいケース選択 UI を追加しない。ナビゲータの荷重ケース一覧が
  既にその役目を果たしているため（現在のケース名は案内ラベルとして表示する）
- `LoadCase.member` は既に `sync_gravity_load_cases_action` が床分配・自重・取り付く
  壁版の線アンカー・（自動同期対象外の）手入力荷重をすべて合成した内容を持つため、
  ソースをそのまま読むだけで「あるべき姿」（床分配・梁自重・取り付く壁版の線アンカー・
  手入力の部材荷重を同じ図に重ねる）を満たす

### 軸（強軸 ey・弱軸 ez）の追加

**当初案（CMQ 図は強軸曲げのみを表示する）は、利用者からの指摘で撤回した。**
部材の局所軸は必ずしも「ey が鉛直・ez が水平」ではない（斜め柱、ひねりのある
断面の柱など）。この場合、鉛直下向きの荷重でも局所 ey 面・ez 面の両方に投影成分が
生じ、これは近似の誤差ではなく物理的に正しい現象である。強軸のみに絞ると、
そうしたモデルで弱軸側の荷重伝達が CMQ 図から欠落する。

そこで応力図（`ForceComponent::plane`）と同じ「面」の区別を CMQ 図にも導入した。

- `MemberLoad.dir`（世界座標の作用方向）を、要素の局所軸（`LocalFrame::from_nodes`
  が返す `rot[1]`=ey・`rot[2]`=ez。ビューアの `diagram_offset_dir` と同じ計算）へ
  投影してから C/M/Q を計算する（`project_load`）
- 「軸:」チェックボックスで強軸・弱軸を独立にON/OFFできる。既定は強軸のみ
  （直交グリッド・ひねりのない部材が大半で、弱軸はほぼ0になるモデルが多いため）
- 両軸を同時表示するときは同一スケールで重ねて描く（応力図の同単位成分の
  共有スケールと同じ規約）

### 死コードの一掃

CMQ 図の描画ソース付け替えにより、`app.beam_loads`／`refresh_beam_loads`／
`cmq_display_member_loads`／`AutoLoadComputeResult.dl_beam_loads` は他に消費者が
なくなったため削除した（`compute_dl_beam_loads` 関数自体は `compute_gravity_auto_load_cases`
の内部処理として存続）。対応する既存テスト
（`test_refresh_beam_loads_*`・`test_sync_gravity_invalidates_beam_loads_hash`）も削除した。

### 敵対的レビューで発覚した符号反転の是正（2026-08-28）

実装をレビュースキルを使わない敵対的レビュー（利用者の指示）で検証したところ、
`project_load` が `s = dot(dir, axis)` を使っていたため、**標準的な水平梁
（`ref_vector=[0,0,1]` → 局所 ey は世界 +Z）に鉛直荷重（`dir=[0,0,-1]`）が
作用する既定ケース（強軸のみ表示）で `dot(dir,ey) = -1` となり、全ての梁の
C/M/Q が符号反転していた**（サギング/ホギングが入れ替わり、この改修より前の
（検証済みの）描画と逆側に描かれる）ことが判明した。`ref_vector=[0,0,1]` は
ST-Bridge 取込・`squid-n-edit` の梁作成のいずれもが使う既定値であり、ほぼ全
モデルの既定表示（強軸のみ）に影響する高深刻度の回帰だった。

`squid_n_load::floor::fem` の固定端モーメント・単純梁公式は「正の強度・
集中荷重＝`axis` の負方向へ作用する」という教科書的規約（この改修前の CMQ 図は
`dir` を一切見ず、常にこの符号で `w` をそのまま渡していた）のため、
`s = -dot(dir, axis)` が正しい。既定ケースでは `s=+1` となり、この改修より前の
符号を保ったまま、傾いた部材・弱軸成分へ一般化できる。修正前に失敗する回帰
テスト（既定ケースで投影後の符号・大きさが変わらないことを確認するもの）を
書いて確認してから是正した。

ez（弱軸）側に符号のズレがないことも、`LocalFrame::from_nodes` の実際の右手系
（`ez = ex × ey`）を使って手計算で検証した（水平梁の ref_vector を [0,0,1]→[0,1,0]
に変え、鉛直荷重の投影先を ey→ez に入れ替えても、同一の物理荷重に対し `s` の値・
描画オフセット方向とも完全に一致することを確認）。応力図の `My` に対する
`plot_sign=-1`（`Qy=dMz/dx`・`Qz=-dMy/dx` という右手系の差分関係に由来）とは異なり、
CMQ図の C/M/Q は面ごとに独立した単純梁公式の再計算であって、実測 6 自由度の
内力ベクトルから導く量ではないため、その非対称性を持ち込む必要がない。

### 利用者の指示による2度目の敵対的レビュー（2026-08-28）で発覚した2件の是正

1回目のレビューで発見・是正した符号反転とは別に、以下2件を発見・是正した。

**準備計算未実行時に空表示になる（メッセージを改善）**: DL・LL(架構用)・
LL(地震用) の `member` は `sync_gravity_load_cases_action`（準備計算の入口
`ensure_preparation` からしか呼ばれない）が書き込む。旧 `app.beam_loads`
（`compute_dl_beam_loads` を直接呼ぶ設計）はモデルの `floor_regions`/`slabs`
から都度再計算するため準備計算を必要としなかったが、`LoadCase.member` を
直接読む新設計では、モデル読込直後・スラブ編集直後で準備計算を一度も
実行していないと空表示になる。これは「ケースの内容をそのまま描く」という
設計上不可避のトレードオフであり、`sync_auto_load_cases_action` を毎フレーム
自動で呼んで解消する案は却下した（`sync_one_auto_case` は差分があれば
undo 履歴・`unsaved_changes`（未保存マーカー）を書き換えるため、CMQ 図を
**見るだけ**でモデルが「編集済み」扱いになってしまう）。かわりに、空表示の
案内メッセージに「準備計算タブで実行すると更新される」旨を追記した
（`is_gravity_auto_case_name`。EX/EY は水平力が常に `NodalLoad` のみで
`member` を持たないため対象外）。`docs/result_view/README.md` にも明記した。

**`MemberLoad.dir` を正規化せずに使っていた**: `MemberLoad` 構造体のドキュメントは
「dir は内部で正規化」と説明するが、`MemberLoad::manual`/`auto` のコンストラクタ
自体は正規化しない。実解析側 `squid_n_element::frame::member_load::resolve` は
この前提に頼らず明示的に正規化してから内積を取っており、`project_load` も
同じ流儀へ揃えた（現状 GUI・MCP のいずれにも `dir` を編集する経路がなく、
実在するモデルの `dir` は常に単位ベクトル定数のため実害はないが、将来
手入力の方向付き部材荷重が入る余地に備えた防御的な修正）。退化した向き
（長さ ≈0）は寄与 0 として扱う（パニック・NaN を出さない）。

### 利用者の指示による3度目の敵対的レビュー（2026-08-28）で発覚した3件の是正

**軸を選択しても何も描かれず、無言で空白になる**: `max_c`/`max_q`/`max_m` が
全て 0 のときの早期 return にメッセージがなかった（1・2回目のレビュー時点でも
見落としていた）。直交グリッド・ひねりのない部材が大半のモデルで「弱軸(ez)のみ」
を選ぶと、荷重（大半は鉛直）が局所 ez 面へほぼ投影されず、これは日常的に
起こりうる。物理的に正しい結果（不具合ではない）だが、無言で何も描かないと
「表示が壊れた」と区別が付かないため、案内を追加した。

**その案内メッセージ自体に矛盾があった**: 追加した直後の版は「強軸(ey)を追加
してください」と固定文言だったため、**既に強軸のみを選択していて強軸側が
0 だった場合に、選択済みの軸を追加するよう勧める矛盾したメッセージ**になって
いた。選択中の軸をそのままメッセージへ含める `selected_axis_label`（凡例とも
共有）に直して解消した。

**2D 構面表示で強軸・弱軸のトレースが同一直線上に重なり判別できない**:
`in_plane_offset_dir`（構面表示での張り出し方向の平面内への倒し込み）は
材軸と構面法線だけから向きを決め、投影元の面（ey/ez）を見ない。そのため
2D 構面表示で強軸・弱軸を同時表示すると、張り出し方向が完全に同一直線上
（符号違いのみ）に重なる。応力図の強軸 Mz・弱軸 My も同じ制約を持つが、
成分ごとに色そのものが違う（Mz=紫・My=赤）ため重なっても判別できる。CMQ図は
成分（C/M/Q）で色が決まり軸では変えていなかったため、両軸同時表示時に
弱軸側が強軸側に完全に埋もれて見えなくなっていた。弱軸(ez)を半透明（塗り・
輪郭とも不透明度50%）で描く `plane_alpha_scale` を追加し、3D表示でも同じ
規則で統一した（3Dでは方向自体が分かれるため実害はないが、軸ごとに描き分け
規則を変えると挙動が複雑になるため）。凡例にも「弱軸は半透明」と付記した。
