# 断面の同一性キー（符号＋階）と属性 fail-loud の申し送り

## 背景

下ドックの断面テーブルで、同じ名前・同じ断面性能の断面が ID 違いで何行も並ぶという報告があった。
調査した結果、原因は取り込み側の不具合ではなくデータモデルの表現力不足だった。

ST-Bridge は断面の一意キーが `guid` で、**同じ符号の断面を階ごとに別定義として持つ**。
検証に使った実ファイル（3 階建て S 造 + PH）では、断面定義 30 件に対して実体は 13 種類だった。

```
 4 C1  floor=1   □-400x400x16x56      18 GX1 floor=2   SH-500x250x9x16x13
 5 C1  floor=2   □-400x400x16x56      19 GX1 floor=3   SH-500x250x9x16x13
 6 C1  floor=3   □-400x400x16x56      20 GX1 floor=R   SH-500x250x9x16x13
 1 C2  floor=1   □-300x300x12x42      21 GX1 floor=PHR SH-500x250x9x16x13
 ...                                  22 b3  floor=-   H-300x150x6.5x9x13
 7 C2  floor=PH1 □-300x300x12x42      28 b3  floor=-   H-300x150x6.5x9x13
 8 C3  floor=PH1 □-300x300x12x42      29 b3  floor=-   H-300x150x6.5x9x13
```

旧実装は `StbSec*` 要素 1 個につき `Section` 1 件を作るだけで、`floor` 属性は読み捨てていた。
そのため階の情報が失われ、断面テーブルには `C1` が 3 行並ぶだけの状態になっていた。

## 決めたこと

### 断面の同一性キーは符号＋階

`Section` に `floor: Option<String>` を追加し、`(name, floor)` を同一性キーとした。

- 断面性能が同じ断面が別の符号＋階で存在するのは許す（`C2` と `C3` が同じ角形鋼管でもよい）
- 符号＋階の重複は許さない

`floor` は文字列のまま保持し、`Story` へは紐付けない。
ST-Bridge の `floor` は自由文字列で階への id 参照を持たず、実ファイルでも断面の階名（`1`・`R`・`PHR`）と
`StbStory` の名称（`1FL`・`RFL`・`PHRFL`）が食い違い、`PH1` のように対応する階が存在しない値もあったため。

### 取り込み時の衝突解決

`build_sections`（`squid-n-io/src/stbridge/import/assemble.rs`）で解決する。

- 断面性能・断面形状が完全一致 → 1 件へ統合し `notes` で件数を通知
- 食い違う → 符号へ連番（`b3` → `b3#2`）を付けて別断面として残し `warnings` で通知

食い違う定義を捨てないのは、利用者が書いた断面定義を無言で消さないため。
連番を付けた時点でキーは一意になるので不変条件と矛盾しない。

`check_unique_ids`（`assemble.rs`）は節点・階・材料にのみ掛かっており断面には掛かっていないため、
統合で「要素数 > index 数」の誤検知は起きない。

### アプリ内では重複キーを作れない

`squid-n-edit` のコマンド側で拒否し、GUI 側でも事前にボタンを無効化して理由を出す。
コマンド側だけだと「押しても何も起きない」に見え、GUI 側だけだと `squid-n-mcp` などの
他の呼び出し元で不変条件が守れないため両方に置いた。

| 経路 | コマンド | 扱い |
|---|---|---|
| 断面作成パネル「+ 追加」 | `AddSectionShape` | 衝突なら `Noop`。GUI はボタンを無効化 |
| 断面カタログ「+ 追加」 | `AddCatalogSection`（新設） | 同上 |
| 符号・階の変更 | `SetSectionName`（`floor` を追加） | 同上。自分自身は衝突判定から外す |
| 部材断面複製 | `DuplicateSectionForMember` | `(複製)`・`(複製2)`… と自動採番して一意化 |

`AddSection` は `DeleteSection` の逆操作（undo 専用）なので衝突判定を持たせていない。
新規追加でこれを使うと不変条件を迂回できてしまうため、カタログ経路は `AddCatalogSection` へ移した。

### 属性の扱いを全件報告する

要素の単位では fail-loud だったが、属性の単位は素通りだった。
検証ファイルで無言で捨てていた属性は 30 種類あり、`offset_*`（部材端の偏心）のように
解析結果へ直接効くものが含まれていた。

`Attrs`（`import/xml.rs`）を「参照されたキーを記録する型」に変え、要素の処理直後に
「出現した属性 − 参照された属性」を要素タグ別に集計する。
**無視リストは持たない。**`guid` も未取り込みとして報告する。
リストを持たないことで、取り込みの実装を足せば報告も自動で追随し、一覧の更新漏れが起きない。

報告は `ImportReport::attributes`（`Vec<AttrDisposition>`）に載せ、`warnings` には入れない。
`warnings` へ入れると `is_clean()` が実ファイルで常に偽になり判定として死ぬためと、
要素×属性×件数の表を `Vec<String>` に混ぜると集計も絞り込みもできなくなるため。

GUI は下ドックの「ログ」タブへ全量を出し、読込直後のトーストには要約 1 行だけを出す。

## 残課題

### 部材端の偏心（`offset_*`）の取り込み

`StbColumn`・`StbGirder` の `offset_start_X`・`offset_end_Z` などは**依然として取り込んでいない**。
今回入れた属性の報告により未取り込みであることは利用者に見える状態になったが、取り込み自体は未実装。

偏心を入れると剛域長・可とう長・部材長・応力の全体へ波及するため、断面表示の改修とは分けた。
着手するときは次を確認すること。

- `LocalAxis`／剛域（`RigidZone`）と偏心の関係。剛体アーム長の算定に偏心を含めるのか別枠にするのか
- 偏心を持つ部材の自重・スラブ荷重の載荷位置
- 書き出し側（`export.rs` の `members_body`）での往復

### `AddSectionShape` の `new_id` は呼び出し側任せのまま

`AddSectionShape` は `new_id` をそのまま断面の id にし、逆操作も `DeleteSection { id: new_id }` を返す。
呼び出し側が `sections.len()` 以外を渡すと「配列添字 == id.index()」の不変条件が壊れる。
現在の呼び出し側はいずれも正しい値を渡しており、今回の変更で悪化してはいないが、
コマンド側で実際の追加位置から id を決める形（`AddCatalogSection` と同じ）へそろえる余地がある。

### 属性報告の精度

`get_f64_any` のように候補キーを順に試す取得では、先に一致したキーで打ち切るため、
後続の候補キーが要素に存在すると「未参照」として残る。
方言吸収のための候補列なので実害は小さいが、報告上は「読んだのに未取り込みと出る」ように見える
ケースがありうる。気になるようなら候補列を全件マークする方式へ変える余地がある。

### 断面の階と `Story` の突き合わせ

いまは文字列のラベルとして持つだけで、`Story` とは無関係。
階ごとの断面リスト出力や、階別の断面集計をやる段階になったら突き合わせの規則が要る。
その際も「対応する `Story` がない階名がある」ことを前提に設計すること。
