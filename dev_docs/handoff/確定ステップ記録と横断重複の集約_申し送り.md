# 確定ステップ記録と横断重複の集約 — 申し送り

作成日: 2026-09-03
対象コード: `crates/squid-n-solver/`・`crates/squid-n-core/`・`crates/squid-n-element/`・`crates/squid-n-app/`・`crates/squid-n-io/`・`crates/squid-n-design-jp/`・`crates/squid-n-job/`

この申し送りでは、ワークスペース全体（約 22 万行）をクローン検出で走査して見つかった重複を集約した経緯と、その過程で見つかった 1 件の抜けを是正した内容を記録します。

## 背景 — 今回の走査で何が残っていたか

重複の集約は [クレート横断の重複統合](クレート横断の重複統合_申し送り.md)・[実装レビューと重複統合](実装レビューと重複統合_申し送り.md)・[要素振る舞いの定型集約とクレート階層の整理](要素振る舞いの定型集約とクレート階層の整理_申し送り.md)・[要素の定式化の重複集約](要素の定式化の重複集約_申し送り.md) で繰り返し行ってきました。
そこで今回は、対象をどれか 1 つのクレートに絞らず、**ワークスペース全体を横断して**もう一度走査をかけました。

走査で残っていた重複は、性格が 2 つに分かれていました。

1 つは、**同じ処理が 1 つの関数の中でフェーズごとに複製されている**ものです。
これは増分解析の司令塔（`pushover/driver.rs`）に集中していました。

もう 1 つは、**すでに集約先があるのに呼び出し側がそれを使っていない**ものです。
`Model::node` / `Model::element` があるのに線形探索が書かれている箇所、`plate_thickness` があるのに同じ `match` が別クレートに写っている箇所などです。

前者と後者では危険度が違います。
後者は「遠回りをしている」だけで、結果は一致します。
ですが前者は、**追跡する項目を増やしたときに 1 か所だけ更新が漏れる**という形で、解析結果を静かに壊します。

そして `driver.rs` では、それが実際に一度起きていました。

## 実害の記録 — 弧長法フェーズだけ追跡が抜けていた

`driver.rs` には次のようなコメントが残っていました。

> ヒンジ・せん断降伏の追跡は荷重制御・変位制御と同じ扱いで継続する（従来は弧長法フェーズだけ追跡が抜けており、耐力ピーク以降に形成されるヒンジが機構判定・詳細図から欠落していた）

増分解析は長期載荷・荷重制御・変位制御・弧長法の 4 フェーズを順に通ります。
ステップが確定したときに残す記録は、どのフェーズでも同一です。
それが 4 か所へ複製されていたため、ヒンジ追跡を足したときに 1 か所（弧長法）だけ書き忘れ、崩壊機構の判定とヒンジ詳細図からヒンジが落ちていました。

つまりこの重複は、すでに 1 度実害を出しています。
そして今回調べたところ、**同じ場所に同じ形の抜けがもう 1 件残っていました**（後述の §是正した挙動）。

## 決めたこと

着手前に dig で 5 問を確認し、次の形に決めました。

| 問い | 決定 |
|------|------|
| 何を本丸に据えるか | `driver.rs` の 4 重複。前科のある重複を残したまま他を整えるのは目的から外れる |
| 適用範囲 | 見つかった 10 件すべて。GUI・ベンチ例題も含める |
| 弧長法の目標判定漏れ | リファクタリングと分けて是正する。集約のビット一致を先に確認できる形を保つ |
| 長期載荷ステップ（λ=0）を目標判定に含めるか | 含めない。水平力に対する応答ではないため |
| ベンチ例題の共通化の深さ | 節点格子と要素構築の定型だけ。質量・階・断面の差異は各例題に残す |

長期載荷を目標判定から外したのは、意味論が合わないことに加えて、**含めると無意味な経路を新設してしまう**ためです。
`PushoverTarget::reached` は `max_disp` か `max_drift_angle` のいずれかを超えたら真を返します。
長期荷重だけの応答で目標に達したと判定すると、水平力を 1 ステップも載荷しないまま「目標到達」で終了し、`Qu` がほぼ 0 になります。
解析が成立していないのに成立した顔で結果が返るため、これは作ってはならない経路です。

ベンチ例題の共通化を格子と要素構築にとどめたのは、**4 本のベンチが何を測っているかを字面に残すため**です。
質量の有無や階の割当をオプション引数へ畳み込むと、`spec.mass = false` の意味を読むために共通モジュールを開くことになります。
重複は消えても、理解のコストが移動するだけです。

## 集約したもの

### 増分解析の確定ステップ記録 → `pushover/step_record.rs`（新設）

4 フェーズに複製されていた記録（性能曲線・ステップ列・塑性率の更新・ヒンジ追跡・せん断降伏追跡・部材応答履歴の 6 つ）を `StepRecorder` へ集約しました。
記録の中身は `StepRecorder::record` だけが知る形にし、呼び出し側が渡すのは荷重係数 `load_factor` の 1 つだけです。

フェーズごとに違うのは、この荷重係数の求め方だけでした。
長期載荷は 0、荷重制御は `current_lambda`、変位制御は変位拘束から解いた λ、弧長法は `arc_lambda` です。

終了目標の判定は**呼び出し側に残しました**。
長期載荷は判定の対象にならないため、4 フェーズで扱いが揃わないからです。
判定に要る頂部変位と最大層間変形角は `RecordedStep` で返し、判定するフェーズだけがそれを見ます。

`driver.rs` は 1171 行から 1008 行へ減り、集約先の `step_record.rs` が 208 行です。

### 時刻歴の地動加速度取得と最大変位展開 → `timehistory/common.rs`

線形と非線形の時刻歴が、地動加速度の取り出し（`accel_xy_at` / `accel_dir_at`）と最大応答変位の全節点展開（`expand_peak_disp`）を持ち直していました。
いずれも引数が 2〜3 個で済む純関数なので、`common.rs` へ移しました。

**その前後にある「縮約空間から自由 DOF 空間へ展開して最大値を更新する」ブロックは、あえて共有していません。**
共有するには可変バッファを 13 個ほど渡す関数が要るうえ、中身は `update_story_drift`・`mass_accel_free_into` という**すでに共有済みのヘルパを順に呼ぶだけ**です。
引数の束を作って隠す価値はないと判断しました。

### ID から実体を引く線形探索 → `Model` のアクセサ

`Model::node` / `Model::element` は [クレート横断の重複統合](クレート横断の重複統合_申し送り.md) で集約済みでしたが、そこを通らない線形探索が app・design-jp・job に残っていました。
断面については、そもそもアクセサ自体がありませんでした。

`Model::section` を新設し、`node` / `element` と同じ規約（添字で引き、不変条件が崩れた場合のみ線形探索へ落とす）に揃えました。
`sections[i].id == SectionId(i)` は `Model::validate` が要素・二次部材からの参照ごとに検証しており、`Model::element_section` もすでに添字で引いています。

要素から断面を引く箇所は `Model::element_section` へ寄せました。
`element_material` の doc が「材料が要る箇所は常にこのヘルパーを情報源とし、断面と材料の対応を呼び出し側へ散らさない」と定めているのと同じ規約です。

置き換えたのは 14 ファイル・17 か所です。
うち 3 か所（`eccentricity_analysis.rs`・`eccentricity/model_extract.rs`・`lumped_mass.rs`）は**柱ごとのループの中**にあり、部材数に対して O(n²) を払っていました。

### 物性ゼロの断面 → `Section::zero`（`squid-n-core`）

物性がすべて 0・形状も材料も持たない `Section` の構築リテラルが、`squid-n-element` の `section_lookup` と `squid-n-io` の `zero_section` に同一で存在していました。
[実装レビューと重複統合](実装レビューと重複統合_申し送り.md) の残課題が「統合には `Section` の既定値を `squid-n-core` へ持ち上げるクレート横断の判断が要る」としていた箇所です。

`Section::zero(id, name)` を core へ置き、両方から呼ぶ形にしました。
`impl Default` にはしていません。
断面の既定値は「もっともらしい値で埋めてはならない」という方針が doc に明記されており、`Default::default()` で暗黙に湧く形にすると、その方針が読めなくなるためです。

ST-Bridge の壁厚断面（物性ゼロ＋板厚のみ）も、`..Section::zero(sid, name)` を土台にする形へ寄せました。

### F 値の板厚区分判定 → `material_strength::plate_thickness`

鋼断面形状から最大板厚を求める `match`（`SectionShape` の全分岐、約 45 行）が、`squid-n-app` の `steel_max_thickness` と `squid-n-design-jp` の `plate_thickness` に複製されていました。
app は design-jp の上位層にあるため、app 側を削除して一本化しました。

2 つは板厚を解決できなかったときのフォールバックが違いました（app は 0.0、design-jp は `Section::thickness` か 40.0）。
調べたところ、**この差は実到達範囲では結果を変えません**。
根拠は 2 つあります。

1 つは `Section::thickness` が入る断面が限られていることです。
このフィールドを埋めるのは ST-Bridge のスラブ・壁 RC 断面の取り込みだけで、鋼断面には入りません。
`thickness` が `None` なら design-jp 側は 40.0 を返し、`bucket2` / `bucket3` はどちらも `t <= 40.0` の区分なので、app 側の 0.0 と同じ F 値になります。

もう 1 つは、呼び出し箇所が鋼部材に限られていることです。
`holding.rs` のこの分岐は `is_brace_elem && elem_steel` で守られており、`elem_is_steel` はコンクリート系材料の部材を弾きます。
そのため仮に壁 RC 断面（`thickness` が 200mm 等）をブレース要素へ割り当てても、この経路には入りません。

なお、この 2 つの守りが将来外れて 40mm を超える `thickness` を持つ鋼断面が現れた場合も、design-jp 側の解決は F 値が下がる（＝耐力を過小に見る）**安全側**です。

### ファイバー梁のガウス点構築 → `build_gauss_fiber_pair`

`build_gauss_fibers` は呼ぶたびに独立した断面と材料インスタンスを返します。
各ガウス点が自分の履歴状態（塑性ひずみ・除荷点）を持つため、1 組を複製したり共有したりはできず、**必ず同じ引数で 2 回呼ぶ**必要があります。

この定型と、その前段にある材料文脈の解決（形状・fc・降伏諸元・材料強度割増・除荷則）が `fiber/mod.rs` 内の 2 か所に複製されていました。
[要素の定式化の重複集約](要素の定式化の重複集約_申し送り.md) が「同一ファイル内の重複が残る（ガウス点まわり）」として残課題にしていた箇所です。

引数は `data`・`model`・`basis`・`kind`・格子寸法の 4 つに絞りました。
断面・材料・ヤング率は `data` と `model` から内部で解決できるため、呼び出し側から渡す必要がありません。

### 弾性要素の局所材端力 → `LocalFrame::local_end_forces`

節点バネ（`springs/spring.rs`）とトラス（`frame/truss.rs`）の `recover_forces` が、局所材端力 `f_local = K_local·(R·u)` を組み立てる前半を持ち直していました。
[要素の定式化の重複集約](要素の定式化の重複集約_申し送り.md) の残課題です。

共有できるのはここまでです。
返す断面力の形が要素で違う（バネは 6 成分すべて・トラスは軸力のみ）ため、符号規約の適用は各要素に残しました。

### ビューアのカメラ操作入力 → `CameraState::apply_pointer_input`

ドラッグ・スクロール・ピンチをカメラへ反映する処理が、ビューア（`viewer/input.rs`）・M-N 相関図（`mn_view.rs`）・ヒンジ詳細（`viewer/hinge.rs`）の 3 か所に複製されていました。
ズームの感度 0.01 とクランプ範囲 0.5〜10.0 まで写っていました。

3 か所の違いは、ビューアの「構面表示中は左ドラッグをパンに割り当てる」だけでした。
これを `allow_rotate` の 1 引数で表し、感度とクランプは `CameraState` の定数（`ZOOM_SENS`・`ZOOM_MIN`・`ZOOM_MAX`）へ寄せました。
同じ 3D をどのパネルで触っても同じ操作感になることが利用者から見た要件であり、感度がパネルごとに割れてはならないためです。

なお `mn_view.rs` には「viewer と異なり同一画面に 2D プロットや操作パネルが並ぶため、ズームは 3D 領域にポインタがあるときのみ反応させる」というコメントがありました。
これは**事実に反する古い記述**でした。
`viewer/input.rs` も同じく `response.hovered()` で囲っており、違いはありません。
集約に合わせてこの記述も落としました。

### 鋼材設計属性のドラフト書き写し → `SteelAttrDraft::sync_from`

モデルの `SteelDesignAttr` から入力バッファへ 11 項目を書き写す処理が、表の「編集」ボタンと対象部材の切替時の再同期の 2 か所に複製されていました。
`SteelAttrDraft` のメソッドへ移し、表示桁の規約（欠損率は 0.1% 刻み・長さは整数・横座屈修正係数 C は 0.01 刻み）も 1 か所に集めました。

### ベンチ例題の骨組生成 → `examples/common/mod.rs`（新設）

4 本のベンチ（`eigen_bench`・`parallel_bench`・`pushover_bench`・`th_bench`）が、150〜216 行の `make_frame` をそれぞれ持っていました。
節点格子の採番・座標・支持条件と梁要素の構築は同一で、`ElementData` や `Node` にフィールドが増えるたび 4 本すべてを直す必要がありました。

`FrameGrid` を新設し、格子点の採番（`node_id`）・節点生成（`build_nodes`）・柱と大梁の生成（`push_frame_members`）を共有しました。
節点質量と階の割当は `build_nodes` のクロージャへ、長期荷重の載荷対象となる大梁 ID の収集は `push_frame_members` のクロージャへ委ねています。

例題の共有モジュールは `#[path = "common/mod.rs"] mod common;` で取り込みます。
`examples/` 直下の `.rs` はモジュール探索先が自分の名前のディレクトリになるため、`mod common;` だけでは解決できません。

## 是正した挙動 — 弧長法フェーズが終了目標を判定していなかった

4 ブロックを並べて精査したところ、**弧長法フェーズだけが `target.reached()` を評価していませんでした**。
`drift_angle_now` すら算定していませんでした。

さらに、フェーズの入口も食い違っていました。
変位制御フェーズは `target.is_enabled() && !target_reached` で守られているのに、弧長法フェーズには `!target_reached` の守りがありませんでした。

その結果、次のことが起きます。

- 荷重制御・変位制御で終了目標に達して打ち切ったあとも、弧長法が最大 20 ステップを追加で回す
- 追加分が `capacity_curve` に積まれ、`Qu`（性能曲線上の最大ベースシア）の算定対象に入る
- 弧長法の途中で目標に達しても、そこで止まらない

これは §実害の記録 で引用したコメントと**同じ場所・同じ原因の、まだ塞がれていない残り**です。
前回はヒンジ追跡が抜けていて、今回は目標判定が抜けていました。

安全側か危険側かは自明ではありません。
単調載荷では耐力ピーク後にベースシアが下るため、追加ステップが `Qu` の最大値を押し上げることは通常ありません。
一方で弧長法は下り勾配の追跡を目的とするため、「目標到達後も追跡を続ける」ことが意図的な設計である可能性もありました。
そのため dig でユーザーへ確認し、**水平力を載荷する 3 フェーズで判定を揃える**方針を得て是正しました。

是正の内容は 2 つです。

- 弧長法フェーズの入口へ `!target_reached` の守りを追加した
- 弧長法フェーズの記録後に `target.reached()` を評価し、達していれば `target_reached` を立てて打ち切るようにした

長期載荷ステップ（λ=0）は判定の対象に含めていません（§決めたこと の理由）。

この是正が結果を変えるのは、**弧長法を有効にし、かつ終了目標が有効で、かつ目標に達した**場合だけです。
そのとき性能曲線は短くなり、`Qu` は従来以下になります。
`PushoverTarget::reached` は目標が両方 `None` のとき常に偽を返すため、目標を設定しない解析には影響しません。

**現時点で GUI・MCP の結果は変わりません。**
`squid-n-job` の `compute_pushover` が `use_arc_length` に `false` を直書きしており、`AnalysisSettings` にも対応する項目がないため、アプリからは弧長法フェーズへ入れないためです。
影響を受けるのはソルバ API を直に呼ぶ経路（`pushover_bench`・V&V テスト）に限られます。
逆に言えばこの是正は、**弧長法を UI へ結線したときに欠陥が表面化することを未然に防ぐ**ものです。

## 検証

リファクタリングと挙動の是正をコミットで分け、リファクタリング側が**代表スカラのスナップショットに差分を出さないこと**を先に確認しました。
集約のミスと意図した是正を、スナップショットの差分から切り分けられる状態を保つためです。

実行した確認は次のとおりです。

- `cargo build --workspace --all-targets`（`gui`・`mcp` フラグ付きを含む）
- `cargo test --workspace --locked`
- `cargo test -p squid-n-app --features gui`・`cargo test -p squid-n-mcp --features mcp`
- `cargo clippy --workspace --all-targets --locked -- -D warnings`（`gui`・`mcp` フラグ付きを含む）
- `cargo fmt --all -- --check`
- `full_model.rs`・`wall_model.rs` の代表スカラのスナップショット

`pushover/tests.rs` の既存 107 テストは、荷重制御・LoadOnly・弧長法をそれぞれ個別に通します。
`StepRecorder` への集約が記録の順序と通し番号を保っていることは、これらが検出します。

弧長法の是正には回帰テストを 2 本追加しました。

- `test_pushover_arc_length_respects_termination_target` — 小さな終了目標を与え、目標到達後に弧長法が性能曲線へ追加ステップを積まないこと（弧長法の有無で `capacity_curve` の長さと `Qu` が一致すること）
- `test_pushover_arc_length_runs_when_target_disabled` — 目標を無効にした場合は従来どおり弧長法が走ること（追加した `!target_reached` の守りが、目標なしの解析まで止めていないこと）

2 本目を置いたのは、`!target_reached` の守りが行き過ぎて**弧長法そのものを無効化する**方向の誤りが、1 本目のテストだけでは検出できないためです。

GUI のカメラ操作には自動テストがありません。
`CameraState::apply_pointer_input` は 3 か所の実装が逐語一致していたものを 1 つにまとめただけで、感度・クランプ・ボタン割り当てをすべてそのまま持ち込んでいますが、**目視確認に頼っている点は残ります**。

## 残課題

- `viewer/input.rs`・`mn_view.rs`・`viewer/hinge.rs` のカメラ操作には自動テストがない。`apply_pointer_input` は `egui::Ui` と `egui::Response` を要求するため、`egui` のテストハーネスなしには単体テストが書けない。感度・クランプの回帰は目視でしか気づけない
- 時刻歴の線形・非線形に残した「縮約空間から自由 DOF 空間へ展開して最大値を更新する」ブロックは、なお 2 か所にある（§集約したもの の理由で意図的に残した）。共有するなら、可変バッファを束ねる型を先に設計する必要がある
- `core/frame.rs` の `stories.iter().find(|s| s.id == id)` は線形探索のまま残した。`stories[i].id == StoryId(i)` の不変条件が `Model::validate` で検証されていないため、`Model::section` と同じ規約を当てられない。階の追加・削除で `squid-n-edit` が添字と ID を揃えているかを先に確認する必要がある
- 今回の走査では `core/region_rebuild.rs` と `core/wall_region_rebuild.rs` の「旧領域を重心で照合して名前を継承する」ループ（約 25 行）も同型だった。ジェネリクスとクロージャで括れる形だが、`FloorRegion` / `WallRegion` の型と ID が違うため、括ると読みにくくなる可能性がある。今回の対象からは外した
- `app/tables/wall_plates.rs` と `app/tables/slabs.rs` にも同型の表描画（約 15 行）が残っている。同様に今回の対象からは外した
- 弧長法フェーズは `docs/` に「オプション、既定は無効」と書かれているが、**アプリからは選べない**。`squid-n-job` の `compute_pushover` が `use_arc_length` に `false` を直書きし、`AnalysisSettings` にも項目がないためで、今回の是正で見つけた既存のずれ。UI へ結線するか、`docs/` の書きぶりを実態へ揃えるかは未判断（今回の範囲外のため手を付けていない）
