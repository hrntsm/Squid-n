# 表フォーマットの統一 申し送り

作成日: 2026-08-06
対象コード: `crates/squid-n-app/src/table_util.rs`（全面改修）、
`tables/*.rs`、`prep_view.rs`、`design_view.rs`、`ultimate_view.rs`、
`quantity_view.rs`、`app/panels.rs`、`app/mod.rs`、`dev_docs/handoff/TONMANUAL.md`

## 1. 何を直したか

GUI の表の見た目が表ごとに割れていた。利用者から挙がった指摘は次の 3 点である。

- 断面の表には縦線が入って読みやすいが、ほかの表には入っていない
- 部材の表で ID が 3 桁になると「10 / 0」と不自然に折り返す
- 材料の表は列がそろっていない

3 点はいずれも同じ原因から出ていたため、共通ヘルパ `table_util::standard_table` に
規約を集約し、アプリ内の全 34 表をそこへ寄せた。規約自体は TONMANUAL §6
「テーブル」へ明文化してある。

## 2. 症状の原因

改修前は表の実装が 3 系統に分かれていた。

| 系統 | 実装 | 該当 |
| --- | --- | --- |
| A | `table_util::standard_table`（`resizable`＋全列 `clip`） | 9 箇所 |
| B | `TableBuilder` 直書き（`striped` のみ） | 22 箇所 |
| C | スプレッドシート様式グリッド（`grid/widget.rs`） | 節点・境界条件など |

指摘の 3 点はすべて B 系統で起きていた。

### 2.1 縦線は `resizable(true)` の副産物だった

`egui_extras` は**リサイズ可能な列の境界にリサイズハンドルとして縦線を引く**
（`egui_extras-0.34.3/src/table.rs:906`。色は `noninteractive.bg_stroke`＝gray-200）。
A 系統は `resizable(true)` を呼んでいるためこの線が出ており、B 系統は呼んでいない
ため出ていなかった。「断面の表は読みやすい」という評価はこの線に対するものになる。

### 2.2 ID の折り返しは `clip(false)` と `Column::auto()` の膠着

`egui_extras` は**クリップを有効にした列でのみ**セルの `wrap_mode` を `Truncate` に
する（`layout.rs:225`）。クリップしない列のテキストは折り返すため、`Column::auto()`
と組むと次の膠着に陥る。

1. 列が狭いので「100」が「10 / 0」と 2 行に折り返す
2. 折り返した結果の実測幅は 1 桁分しかない
3. `auto` はその実測幅を列幅に採るので、列は広がらない
4. 1 へ戻る

部材・材料・設計・保有耐力の各表の ID 列がすべて `Column::auto()` だったため、
同じ症状を抱えていた。

### 2.3 列ズレはクリップ無効とウィジェット幅の指定漏れ

クリップしない列は、内容が列幅を超えた行だけ以降のセルが右へ押し出される。
このため内容の広い行が 1 つあるだけで、その行から先の列位置がずれる。

材料の表ではこれに加えて、ウィジェットの幅と列幅が独立に決められていた。
`ComboBox` は `.width()` を指定しないと `Spacing::combo_width`（既定 100 pt）を
使うため、80 pt の列に置くと 20 pt はみ出す。部材の表で「材料」列の内容が見出しから
ずれていたのはこれが原因である。

## 3. 設計判断

### 3.1 縦線は `resizable(true)` で得る（自前で罫線を描かない）

縦線を出す手段は「リサイズ線を使う」か「各セルが自分で罫線を描く」かの 2 つがある。
後者は C 系統（`グリッド操作.md` §6.1 の共有罫線方式）が採っている方式だが、
セル矩形をそのまま使うと罫線が途切れるため `rect.expand2(item_spacing * 0.5)` で
セル間スペーシングを跨ぐ処理が要る（同 §7.5）。

今回は評価された A 系統の見た目をそのまま基準にし、リサイズ線を使う方式を採った。
追加の描画コードが不要で、罫線の跨ぎ処理を新たに抱えずに済む。外枠と横罫線は引かず、
行の区別は従来どおりストライプに任せている。

C 系統を統一の対象に含めなかったのは、あちらが「編集用スプレッドシート」という別の
UI パターンとして仕様書で確定済みであり、かつ指摘の 3 症状がいずれも起きていない
ためである。同じ見た目にすると「ここは直接編集できる表」という手がかりも失われる。

### 3.2 列幅は用途トークンにし、実幅をフォントから導出する

改修前の列幅は `initial(45.0)` から `initial(260.0)` まで 20 種類以上の生値が散在し、
同じ意味の列でも表ごとに違っていた（「階」は断面表 50 pt・数量表 60 pt など）。
これを `ColWidth`（`Id` / `Num` / `WideNum` / `Label` / `Name` / `Text` / `Actions`）の
7 トークンへ寄せた。

実幅は用途ごとの代表文字列（ID なら `"00000"`、名称なら `"STKR400(SRC)"` など）を
Body フォントで実測し、セル余白を足して求める。TONMANUAL §4 が「テキストを内包する
箱の寸法を固定 px で書かない」と定めており、列幅もこれに該当するためである。既定
フォントでの実測値は Id が約 53 pt、Num が約 66 pt、Text が約 174 pt になる。

トークンの幅より見出しのほうが長い列は、見出しが収まる幅まで広げている。クリップを
全列へ広げた以上、見出しが切り詰められると列の意味そのものが読めなくなるためである。

### 3.3 列定義を `Col` にまとめた

改修前の `standard_table` は `columns: &[Column]` と `headers: &[&str]` を別々に
受け取り、数を合わせるのは呼び出し側の責任だった。ここに幅トークンとツールチップが
加わると対応付けのミスが起きやすいため、`Col` 構造体 1 つに畳んでいる。

```rust
table_util::standard_table(
    ui,
    "materials_tbl",
    &[
        Col::id(),
        Col::name("名称"),
        Col::name("区分").hover("S 造 / RC 造の判定に用います。…"),
        Col::num("E [N/mm²]"),
        Col::actions(),
    ],
    n,
    |row| { /* セルを描く */ },
);
```

見出しのツールチップを `Col` が持てるようになったので、材料の表の「区分」「割増」の
ように補足の要る見出しもヘルパへ寄せられた。改修前はこれが直書きを残す理由になって
いた。

### 3.4 セル内の編集ウィジェットは列幅いっぱいに伸ばす

`cell_text_edit` / `cell_combo` / `cell_drag_value` を用意し、いずれも
`ui.available_width()`（＝セル幅）を使う。列はリサイズできるため、ウィジェットが
追従しないと「列を広げても入力欄は広がらない」という不整合が残る。

ウィジェット側に固定幅を書く方式は採らなかった。同じ数値を列定義とウィジェットの
2 箇所に書くことになり、片方だけ直す事故が再発するためである。

### 3.5 ツールチップは文字列セルにのみ付ける

クリップを全列へ広げたことで、内容が列幅を超えるセルは切り詰められるようになった。
そこで `text_cell` を用意し、名称・符号・形状・種別のような文字列セルはホバーで全文を
出している。数値セルは `{:.1}` などで桁数が決まっており、トークン幅を桁数に合わせれば
切り詰まらないため対象外とした。

「実際に切り詰められたときだけホバーを出す」方式も検討したが、切り詰め判定には
`Label` を自前でレイアウトして `Galley` を検査する必要がある。`colored_label` や
`selectable_label` を使うセルが多く例外処理が増えるため、まずは一律付与で運用する。

### 3.6 縦横のスクロールを表の外側へ寄せた

列幅を見出しに合わせて広げたことで、表の総幅が表示幅を超える場面が増える。
そこで `standard_table` が表ごとに `ScrollArea::both` を作り、`TableBuilder` 自身の
縦スクロールは切っている（`vscroll(false)`）。

縦だけを `TableBuilder` に残す案は採らなかった。`egui_extras` は横スクロールを
持たないため外側に `ScrollArea::horizontal` が要るが、そうすると縦スクロールバーが
表の右端――横スクロールで画面外へ流れる位置――に付いてしまう。縦横ともに外側へ
寄せることで、縦スクロールバーはパネルの右端に留まる。

**行の仮想化は失われない**。`TableBody::rows` は自身のスクロール状態ではなく
クリップ矩形と表の先頭位置の差から可視範囲を求めるため（`table.rs:966`）、
外側のスクロール領域でも可視行だけを描く。

横スクロール領域の内側では利用可能幅が無限になるため、表の幅を明示する必要がある。
表の実幅は利用者の列リサイズで変わるので、前フレームの実測値
（`ScrollAreaOutput::content_size`）を temp storage へ持ち越し、次フレームの
`set_max_width` に使う。見積もりと実幅がずれたフレームは横スクロールバーの要否が
変わるため、再描画を要求する。

この設計に伴い `ColWidth::Remainder`（残り幅を埋める列）は廃止した。残り幅を
埋める列があると実測幅が常に「与えた幅」と一致してしまい、上記の実測が機能しない。
横スクロールが入った以上、自由文の列も他の文字列列と同じく切り詰め＋ホバーで扱い、
足りなければ列を広げて横へ送れば読める。

**表を載せるパネル側は横スクロールを持たせない**。下ドックのモデルタブ・荷重タブと
準備計算パネルは `ScrollArea::both` を使っていたが、表側と二重になり、表を横へ
送ったつもりでサブタブ行や追加フォームまで流れてしまうため `ScrollArea::vertical`
へ変えた。

## 4. 対象範囲

`TableBuilder` 直書きの 22 箇所と、表として使っていた `egui::Grid` の 3 箇所
（通り芯一覧・質点系の階データ・質点系時刻歴結果）を移した。既存の
`standard_table` 呼び出し 9 箇所も新 API へ書き換えている。

移していない `egui::Grid` は、準備計算のサマリと設定フォーム、検定比の
ツールチップ、M-N 図の要約である。いずれも表ではなく key-value 形式のフォームや
ツールチップのため、対象外とした。

## 5. テスト

`table_util` に幅の導出と `Col` の構築を検証する単体テストを 6 本追加した。
表の描画そのものは検証していない。

テスト用の `Ui` は自前で用意している。`egui::__run_test_ui` は CPU 時間の節約の
ため `FontDefinitions::empty()` でフォントを読み込まないので（`egui-0.34.3/src/lib.rs:689`）、
そのまま使うと文字幅が常に 0 になり幅の導出を検証できない。テストヘルパでは既定
フォントを読み込み、`theme::apply_theme` でアプリと同じタイポスケールを適用して
から測っている。

## 6. 残課題

- **スナップショットテストがない**。列ズレや切り詰めのような見た目の崩れは、
  現在の単体テストでは検出できない。`egui_kittest` の導入が候補になるが、和文
  フォントのレンダリング差で CI が不安定になるリスクがある。
- **`Col` の見出しは `&str` に限定している**。動的に組み立てる見出しは、呼び出し側で
  `String` を先に束縛してから参照を渡す必要がある（`design_view.rs` の変形角の
  見出しが該当）。
- **表を縦に並べる画面では、表ごとにスクロール領域が分かれる**。通り芯タブの
  ようにグループごとの表を積む画面では、表ごとに横スクロールバーが付く。
  なお内容が収まっている表はホイールを消費しない（egui は実際に動かせるときだけ
  消費する。`scroll_area.rs:1203`）ため、親のスクロールは妨げない。

## 7. 動作確認

Xvfb（1400x900）＋ lavapipe（Mesa の software Vulkan）で GUI を起動し、6×6 スパン
5 階（部材 480・節点 216）のモデルでモデルタブの各表を目視確認した。指摘の 3 点が
解消していることを確認している。

- 部材・材料の表に列区切りの縦線が入る
- 部材の表の 3 桁 ID（168〜186）が折り返さず 1 行で表示される
- 材料の表の列が見出しとそろい、セル内のコンボ・入力欄が列幅いっぱいに収まる
- 断面の表を横へ送ると、表示幅に収まらない列（J・Asy/Asz・削除ボタン）へ到達できる。
  このときサブタブ行・断面作成フォームは動かない
- 480 行の部材の表を縦へ送っても、サブタブ行と追加フォームは固定されたまま
  行だけが送られる

## 8. 追記: 階の定義表の standard_table 化（2026-08-08）

対象: `crates/squid-n-app/src/app/panels.rs`（`stories_section`）
関連: `解析設定パネルのフロー整理_申し送り.md`、`UI導線改善.md`（3.4）

本申し送りの対象外だった解析タブ「階の定義」を `standard_table` へ移し、
統一対象は全 34 表で外れがなくなった。

- 変更前は「見出し行（階名・レベル・削除）+ 下段の横並び（W・種別）」の 2 段構成で、
  行の高さが縦に伸び、列も揃わなかった。独自のドラフトを持ち、行数とストーリ並びの
  同期を手で保つ必要があった（`story_definition_row` ヘルパ、
  `App::story_def_draft` / `story_weight_edit` / `story_weight_active`）。
- 変更後は 1 行 7 列（階名 / レベル [mm] / 節点数 / 構造 / W [kN] / 種別 / 操作）。
  「節点数」「構造」は準備計算の導出値で表示のみ、残りはセル内で直接編集する。
- 行の並びは上階→下階（`model.stories`（下から上）を `.rev()` して表示）。従来と同じ。
- 編集バッファは `App` フィールドをやめ、`ui.data` のセル ID ごとの一時値で持つ。
  ドラッグ中・フォーカス中だけ挿入され、確定時に除去される（§3.4 のウィジェットは
  列幅いっぱいに伸ばす方針を踏襲）。
- 確定は 1 フレーム 1 コマンドで適用。同一フレームで複数セルが確定しても
  破棄せず、`App::pending_story_cmds`（適用待ちキュー）へ積み、以降のフレームで
  1 コマンドずつ確実に反映する。キューへの積み順は「StoryId を変えない操作
  （種別・重量）→ 標高変更を伴う可能性のある階名・レベル → 削除（最後）」。
  適用は `App::ui`（eframe の毎フレーム処理）冒頭で行うため、「階の定義」表を
  持つ右ドックの表示・非表示と無関係に、編集の確定直後のフレームで必ず反映
  される（準備計算の実行や保存が未反映の階編集に基づいて走ることはない）。
- 削除・レベル変更は `StoryId` の並び替え・繰り上げを伴うため、モデルへの
  反映は 1 フレーム 1 コマンドに限定し、描画ループの途中で model を書き換えない
  （行データは `story_rows` に先に複製する）。
- 適用するコマンドがモデルの変更（削除・並べ替え）の後に残った場合の備えとして、
  `SetStoryLevel`・`DeleteStory` に index 範囲外（＝階数が減った）の Noop ガードを
  追加した。ただし `StoryId ＝配列位置`が不変条件のため、**範囲内に残った古い
  index は常に「その位置の階」へ適用される**（ID の一致検査は不変条件上で恒真で、
  Noop にはならない。`tests::test_stale_story_commands_are_noop` にその旨の注記あり）。
  実際の防御線はキューへの積み順（削除を最後に積む）と 1 フレーム 1 コマンドの
  適用であり、編集の確定が同一フレームに並んだときの順序で保護する。
- 既定値は従来どおり（PH の k=0.5、地下の深さ 3.0 m）。ドラッグの刻み・範囲も同じ。
- ヘッドレス UI テストはないため、描画の検証は追加していない（§5 と同様）。
