# クレート横断の重複統合 — 申し送り

機能ごとにクレートを分けた結果、**同一の計算・判定がクレートをまたいで複製されている**
箇所を全クレート横断で洗い出し、機械的に統合できるものを統合した。本書は
「何を統合したか」と「判断が要るため残した重複」をまとめる。

対象コミット:

- `refactor: クレート横断で重複していた幾何判定・部材種別判定を集約する`
- `refactor: 耐力式・断面積分・モデル走査の重複をクレート下層へ集約する`
- `refactor: 危険断面位置と壁四隅の並べ替えの重複を解消する`

## 背景 — なぜ重複が生まれるか

このワークスペースは `xtask check-deps` で層構造を強制している（上位→下位のみ）。

| 層 | クレート |
| --- | --- |
| 0 | core / math / material / ml |
| 1 | section / load / gpu |
| 2 | edit / skeleton |
| 3 | element |
| 4 | solver / io |
| 5 | design-jp |
| 6 | mcp / app |

同じ計算を必要とする 2 クレートが**同層または逆向き**の関係にあると、共有できずに
複製される。実際、複製箇所の多くはコメントで「◯◯に依存できないため複製している」
「private のためここで再計算する」と自認していた。

**この形の重複は過去に実害を出している。** `squid-n-core/src/face_distance.rs` の
モジュール doc に、柱フェース距離の算定が `squid_n_element` の剛域算定の中だけに
あったために固定荷重が 9.6% 過大になった不具合が記録されている。

したがって解は「複製してコメントで断る」ではなく、**共通部分を下層クレートへ出す**
ことである。以下の統合はすべてこの方針で行った。

## 統合したもの

### 3 次元ベクトル演算 → `squid_n_core::geom::vec3`（新設）

内積・外積・ノルム・単位化・2 点間距離・差・中点が、`dot` / `dot3` / `cross` /
`cross3` / `norm` / `unit` / `normalize` / `dist3` / `member_len3` / `sub` / `mid`
という揺れた名前で 8 ファイルに複製されていた（element 2 か所、load 2 か所、
design-jp・solver・io・app 各 1 か所）。

零ベクトル判定の閾値が **1e-9 と 1e-12 で混在**していたため、座標系が mm である
ことに合わせて `ZERO_TOL = 1e-9` に統一した。影響を受けるのは長さが
(1e-12, 1e-9] mm の部材軸・面法線のみで、いずれも幾何的に縮退しており、
統一前後のどちらでも意味のある結果を返さない。

### 45° 余弦基準（0.707）→ `squid_n_core::geom`

`VERTICAL_COS_TOL`（鉛直判定）と `ORTHOGONAL_DOT_MAX`（直交材判定）が既にあったが、
同じ 0.707 がリテラルで散在していた。加えて「X 方向に効く梁」「加力直交方向へ
卓越する部材」のように**鉛直に限らない軸方向の卓越判定**が同じ規則で書かれていた
ため、`axis_dominates(dir, axis)` を追加してこれに従わせた。

`ORTHOGONAL_DOT_MAX` は `face_distance` の private 定数だったため `geom` へ移して公開。

### 部材の単位軸ベクトル → `squid_n_core::geom::element_axis`

`elem_axis` が core（`face_distance`）と element（`rigid_zone`）に同名・ほぼ同一で
存在した。element 側は core 側が private のため複製していた。

### 部材種別（柱 |ez|≥0.8 / 梁 ≤0.2 / 中間ブレース）→ `squid_n_design_jp::MemberKind`

同一実装が 4 か所（app の `app/mod.rs` と `viewer/th_detail.rs`、mcp の
`job/design_check.rs`、design-jp の `ultimate/geometry.rs`）にあり、境界値 0.8 / 0.2 は
`steel/buckling.rs`・`joint_wiring/common.rs` にも直接書かれていた。
`MemberKind::{from_axis, from_ez, of_element}` と `MEMBER_COLUMN_EZ_MIN` /
`MEMBER_BEAM_EZ_MAX` に集約した。

`squid_n_core::geom::is_vertical_axis`（45° の 2 分）とは**別目的の規約**である旨は
core 側 doc が既に明記しており、統合していない（そのままとした）。

### 部材長 → `Model::member_length`

`elem_geometric_length`（app・mcp）と `geometric_length`（design-jp）が同じ計算を
持ち直していた。element 内でも `(dx²+dy²+dz²).sqrt()` の手書きが散在していたため
`geom::vec3::dist` へ寄せた。

### 曲げひび割れモーメント Mc = κ·√Fc·Ze → `squid_n_core::rc_capacity::rc_crack_moment`

同一式が 4 か所に独立実装されていた。同じ骨格曲線を構成する My・αy は既に
`rc_capacity` へ集約済みで、**Mc だけが漏れていた**（非対称な状態）。

My 比によるクランプは用途ごとに異なる（材端バネ `.clamp(my*0.1, my*0.9)`、
ヒンジ閾値 `.min(my)`、design-jp はクランプなし）ため、呼び出し側に残した。

### ファイバー断面の積分公式 → `squid_n_section::fiber::integrate_fibers`

`section_response`（材料の `trial` を毎回呼ぶ経路）と `GaussPoint::refresh_response`
（トライアル状態をキャッシュ済みの経路）が、断面力 N/My/Mz と 3×3 接線剛性の
積分公式をそれぞれ持っていた。後者のコメントは「結果はビット一致」を要求して
おり、公式が分かれたままでは非線形反復の結果が静かに食い違う。

統合後もビット一致であることは、演算順序（`ea = et*a` を経由する形）が
両者で一致するため保たれる。

### モデル走査 → `Model::node(id)` / `Model::element(id)`

ID から実体を引く箇所で `nodes.iter().find(|n| n.id == id)` の線形探索が 24 か所
以上あった。`Model::validate` が `nodes[i].id == NodeId(i)` を不変条件として検証して
いるため添字で引き、不変条件が崩れた場合のみ線形探索へ落とす実装とした。

### 危険断面位置 → `squid_n_design_jp::design_position`（新設）

`design_positions` / `is_near_design_position` が app と mcp に同一実装で存在した。

要素側の内力評価断面（`squid_n_element` の `eval_sections`）はこれに節点芯
（0.0 / 1.0）を加えたものになる。検定は柱フェース位置で行い節点芯の内力は
用いないため、この差は意図的である（モジュール doc に明記した）。

### その他

| 対象 | 重複していた場所 | 統合先 |
| --- | --- | --- |
| 多角形面積（Newell の公式） | load / design-jp に丸ごとコピー | `core::geom::polygon_area_3d` |

| コンクリートのヤング係数 Ec | design-jp に別実装（Fc≤0 のガードがなく NaN になり得た） | `core::section_shape` へ委譲 |

## 判断が要るため残したもの

### 1. `column_axis_shear` が `MuMethod::Aci` を反映しない（実装漏れ・要修正）

`crates/squid-n-design-jp/src/ultimate/rc_strength.rs` の `column_axis_shear` は
`opts: &UltimateShearOptions` を受け取っているのに `opts.mu_method` を見ず、常に
`rc_column_mu_simple`（at 式）を呼ぶ。一方、同ファイルの `column_mu` は
`mu_method` に応じて ACI 平面保持解析（`rc_column_mu_aci`）へ切り替わる。

**その結果、`MuMethod::Aci` を選ぶと強軸の Mu 判定は ACI 式・弱軸の Qmu は常に
at 式、という食い違いが生じる。** これは重複ではなくオプションの実装漏れであり、
数値が変わるため本リファクタリングでは触っていない。

修正は `column_axis_shear` に `opts.mu_method` を渡すだけだが、二軸せん断検定の
結果が変わるため、V&V の突合を伴って行うこと。

### 2. H 形断面の「せん断有効断面積」が要素剛性側と検定側で食い違う

| | ウェブ側 | フランジ側 |
| --- | --- | --- |
| `core::section_shape::builder`（要素剛性 GAs 用） | `height × web_thick`（**全せい**） | `2 × width × flange_thick`（係数なし） |
| `design-jp::steel::shear_area_2d`（許容応力度検定用） | `web_thick × (h − 2·tf)`（**内法せい**） | `2 × b × tf / 1.5`（**1.5 で低減**） |

同じ「H 形のせん断有効断面積」に対する 2 つの独立算定で、フランジ側は 33% 異なる。
用途が違う（公称断面積 vs せん断応力分布を考慮した有効断面積）ため意図的な差の
可能性が高いが、**相互参照するコメントがなく、意図的な差なのか実装の食い違いなのかが
コードから判別できない**。

対応案: どちらかを正として揃えるか、両者の doc に「意図的に異なる（理由）」を
明記する。構造計算上の意味の判断が要るため未着手。

### 3. 鉄骨全塑性モーメント Mp のフォールバックが解析経路間で異なる

`Mp = Zp·σy` 自体は一致するが、**塑性断面係数を持たない断面のフォールバック**が
異なる。

- `solver::pushover::hinge` — `1.12 × Ze`
- `element::factory::springs` — `Ze`

どちらも「ヒンジ閾値の Mp」という同じ目的なので、係数 1.12 の有無は片方の
取りこぼしに見える。また design-jp の `steel_beam_lateral_buckling_ratio`
（横座屈による Mp 低減）は**どちらの解析経路にも反映されていない**。

これらは数値が変わるため未着手。式を core へ寄せるだけなら機械的だが、
フォールバック係数と横座屈低減の要否を決める必要がある。

### 4. RC 柱梁接合部の有効幅 bj

`bi = (柱幅 − 梁幅)/2` は共通だが、`bai` の採り方が

- 許容応力度（`rc/joint.rs`）: `max(bi/2, D/4)` — 原典図が max と明記
- 終局（`joint_wiring/rc_joint.rs`）: `min(bi/2, D/4)` — 靭性保証型指針、min が安全側

と**規準どおり意図的に逆**である。共通化できるのは `(a−b)/2` の 1 行だけで、
ヘルパ化するとかえって意図的な差が見えにくくなるため、そのままとした。
両ファイルのコメントには既に相違理由が明記されている。

### 5. 主筋重心 `first_layer_dt` と `tension_dt` の段数の扱い

接合部検定系は `first_layer_dt`（1 段目重心、段数を考慮しない）を使い、断面算定系は
`tension_dt`（多段配筋の重心を考慮）を使う。**2 段以上の配筋で両者は一致しない。**

接合部検定に段数を反映すべきかは規準の解釈が要るため、統合せず両者を
`rc::section_props` に並べて置き、doc で使い分けを明記するにとどめた。

### 6. CFT 充填コンクリートの断面性能

`core::section_shape::composite::cft_equivalent_props` と
`design-jp::ultimate::cft_check::cft_section_props` が、内法寸法・充填部の A・I を
それぞれ算定している（式は完全一致）。

ただし**退化寸法の扱いが異なる**（core は内法が 0 以下なら `None` を返して鋼管のみへ
フォールバック、design-jp は `.max(0.0)` でクランプして充填 0 として検定を続行）。
共通ヘルパへ機械的に寄せると、どちらかの退化時の挙動が変わる。どちらの扱いが
正しいかの判断が要るため未着手。

### 7. 標準荷重組合せの生成が 2 系統

- `core::model::load::default_combinations()` — 新規モデルの既定（5 ケース固定）
- `load::combo::standard_combinations()` — 令 82 条の一般ロジック（多雪区域・積雪対応）

両者が一致することは `combo.rs` の
`test_default_combinations_matches_auto_combinations` が**手動同期として保証している
だけ**で、コードは共有していない。core（Layer 0）が load（Layer 1）に依存できない
層構造が原因。

対応案は (a) 既定組合せの構築を load 側へ一本化し、モデル新規作成の経路を
`squid-n-edit` 以上の層へ移す、(b) 現状維持でテストによる同期を続ける、のいずれか。
層構造の設計判断のため未着手。

### 8. 表示側の単位換算が集約されていない

`core::units::to_internal` に入力側（外部単位 → 内部 mm/N 系）の変換が集約されて
いるのに対し、**表示側（内部 → kN・m 等）には対になるモジュールがなく**、
`/ 1000.0` の生リテラルが app 中心に 120 か所前後ある。

`units::to_display` を用意して置換するのが筋だが、`/ 1000.0` には N→kN・mm→m・
単位と無関係なものが混在しており、機械的な一括置換は誤変換を生む。1 か所ずつ
意味を確かめる必要があるため未着手。

### 9. mcp と app の解析ジョブ配線

`squid-n-mcp` は `squid-n-app` に依存できないため、解析ジョブの組み立てを複製して
いる（`job/design_check.rs` の検定器への配線、`job/pushover.rs`、
`job/time_history.rs`、`query.rs`）。

本リファクタリングで、**両者が使う算定規則**（部材種別・部材長・危険断面位置）は
下層へ出した。残るのは「解析器を呼び、結果を組み立てる」配線そのもので、これを
共通化するには app の `run_*` / `compute_*` から純粋計算部分を切り出して
design-jp か新クレートへ移す必要がある。app の GUI 状態との分離が要るため未着手。

なお CONTRIBUTING.md が求めるとおり、`App` に解析エントリを追加したら
`crates/squid-n-app/tests/full_model.rs` にもテストを追加すること。mcp 側の
対応するジョブが腐っていないかは `cargo test -p squid-n-mcp --features mcp` で
確認する（既定フィーチャでは検証されない）。

### 10. 各クレートの `Result<T, String>`

`squid-n-solver` / `squid-n-mcp` / `squid-n-app` は thiserror 型を持たず
`Result<T, String>` を直に返している箇所が多い。solver は既に
`squid_n_math::SolveError` を持つため寄せられる余地があるが、mcp/app の String は
利用者向けメッセージが主目的で、型化の設計判断が要る。

### 11. テストのモデル生成ヘルパ

共有のテストユーティリティはなく、`-> Model` を返すローカル関数が 22 ファイルに
点在している。クレート間の循環依存を避けるため各クレートが独自に持つのは妥当だが、
**同一クレート内で複数ファイルにまたがって似た builder がある**箇所
（例: solver の `statics/linear/tests.rs` と `statics/analysis/tests.rs`）は
crate-local な `test_support` モジュールへ寄せられる。テストごとに検証対象が
異なるため機械的な統合はできない。

## 調査の結果、重複ではなかったもの（誤認防止）

以下は「同じ物理量に見えるが別物」であり、統合してはならない。

- **開口低減率**: 剛性用 `r = 1 − 1.25·r0`（RC 規準）と耐力用 `r2`（RC 規準 18 条）は
  準拠規定も目的も異なる。実体は `core::rc_wall_capacity` に一本化済みで、
  design-jp・element は委譲のみ。
- **せん断終局 Qsu**: 許容 QA 式・荒川 mean 式・塑性理論式・靭性指針式は目的が
  排他的で並存が正しい。荒川式の実体は `core::rc_capacity` の 1 か所のみ。
- **パネルゾーン**: κ・Ve といった幾何は `core::panel_zone` に一本化され、剛性側
  （element）と耐力側（design-jp）が同じ実装を参照している。pMy は鋼構造・SRC で
  それぞれ 1 か所のみ。
- **N-M 相関**: 許容応力度の弾性 N-M 曲線・終局の軸力端点・ACI 平面保持解析は
  前提の異なる別モデル。
- **カタログ断面値と形状式算定値**: `squid-n-section` の JIS 規格断面表（フィレット
  半径込みの実測ベース）と `core::section_shape::properties` の閉形式は、同じ呼び名の
  断面でも A/Iy/Iz/J が微妙に異なる。意図的な設計（カタログは JIS 値の精度を優先）
  だが、利用者から見ると「カタログ経由と手入力で数値が違う」ことになるため、
  `docs/` に記載があるか要確認。
- **NewRC 構成則の Ec**: `material::newrc` の `Ec = 4k·(σB/1000)^(1/3)·10⁵·(γ/2.4)²`
  は新 RC プロジェクト式（工学単位系）で、RC 規準式とは別物。
- **ID / DofMap**: `core::ids::id_newtype!` と `core::dof::DofMap` に完全に一本化
  されており、再実装はない。
- **`squid-n-skeleton`**: 非テストコードから参照されないが、これは意図的な V&V
  参照実装（design-jp の dev-dependency として `rc_mu_simple` の突合に使う）。
  クレート doc 自身がそう明記している。削除しないこと。

## 統合の判断基準（今後の指針）

1. **同じ数式・判定規則が 2 か所以上にあれば、下層クレートへ出す。**
   「依存できないから複製する」は解ではない。共通部分だけを下層へ出せば依存の
   向きは崩れない。
2. **用途ごとに異なるのは「クランプ・フォールバック・係数の選択」であることが多い。**
   式そのものを共有し、これらは呼び出し側に残すと、意図的な差が読み取れる形で
   単一情報源にできる（Mc の統合がこの形）。
3. **意図的に異なるものは、両方の doc から相互参照する。** 参照がないと、後から
   読む者には食い違いなのか意図なのかが判別できない（上記「判断が要るもの」の 2 が
   まさにこの状態）。
4. **可視性が理由の複製は、可視性を上げて解消する。** `pub(crate)` へ上げるだけで
   済むことが多い（`rc_dt`・`section_props` がこの形だった）。
