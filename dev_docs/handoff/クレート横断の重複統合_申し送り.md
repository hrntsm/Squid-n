# クレート横断の重複統合 — 申し送り

機能ごとにクレートを分けた結果、**同一の計算・判定がクレートをまたいで複製されている**
箇所を全クレート横断で洗い出し、統合した。本書は「何を統合したか」「判断を要した
項目をどう決めたか」「何が残っているか」をまとめる。

対象コミット:

- `refactor: クレート横断で重複していた幾何判定・部材種別判定を集約する`
- `refactor: 耐力式・断面積分・モデル走査の重複をクレート下層へ集約する`
- `refactor: 危険断面位置と壁四隅の並べ替えの重複を解消する`
- `refactor: 柱 Mu の ACI 規準（平面保持）による算定を削除する`
- `fix: 全鋼断面形状の塑性断面係数 Zp を算定しヒンジ判定と解析の食い違いを解消する`
- `fix: 接合部検定の引張筋重心 dt を多段配筋対応へ揃える`
- `refactor: 標準荷重組合せの生成を squid-n-core へ集約する`
- `refactor: 表示単位の慣例を squid-n-core へ集約し断面性能を cm 系へ揃える`
- `fix: 解析ジョブを squid-n-job へ集約し MCP の前処理欠落を解消する`
- `refactor: CFT 充填コンクリートの断面性能を共通ヘルパへ集約する`

## 背景 — なぜ重複が生まれるか

このワークスペースは `xtask check-deps` で層構造を強制している（上位→下位のみ）。

| 層 | クレート |
| --- | --- |
| 0 | core / math / material / ml |
| 1 | section / load / gpu |
| 2 | edit / skeleton |
| 3 | element |
| 4 | solver / io |
| 5 | design-jp |
| 6 | job |
| 7 | mcp / app |

（`squid-n-job` は本作業で新設した。GUI と MCP サーバの共通下層。）

同じ計算を必要とする 2 クレートが**同層または逆向き**の関係にあると、共有できずに
複製される。実際、複製箇所の多くはコメントで「◯◯に依存できないため複製している」
「private のためここで再計算する」と自認していた。

**この形の重複は過去に実害を出している。** `squid-n-core/src/face_distance.rs` の
モジュール doc に、柱フェース距離の算定が `squid_n_element` の剛域算定の中だけに
あったために固定荷重が 9.6% 過大になった不具合が記録されている。

したがって解は「複製してコメントで断る」ではなく、**共通部分を下層クレートへ出す**
ことである。以下の統合はすべてこの方針で行った。

## 統合したもの

### 3 次元ベクトル演算 → `squid_n_core::geom::vec3`（新設）

内積・外積・ノルム・単位化・2 点間距離・差・中点が、`dot` / `dot3` / `cross` /
`cross3` / `norm` / `unit` / `normalize` / `dist3` / `member_len3` / `sub` / `mid`
という揺れた名前で 8 ファイルに複製されていた（element 2 か所、load 2 か所、
design-jp・solver・io・app 各 1 か所）。

零ベクトル判定の閾値が **1e-9 と 1e-12 で混在**していたため、座標系が mm である
ことに合わせて `ZERO_TOL = 1e-9` に統一した。影響を受けるのは長さが
(1e-12, 1e-9] mm の部材軸・面法線のみで、いずれも幾何的に縮退しており、
統一前後のどちらでも意味のある結果を返さない。

### 45° 余弦基準（0.707）→ `squid_n_core::geom`

`VERTICAL_COS_TOL`（鉛直判定）と `ORTHOGONAL_DOT_MAX`（直交材判定）がすでにあったが、
同じ 0.707 がリテラルで散在していた。加えて「X 方向に効く梁」「加力直交方向へ
卓越する部材」のように**鉛直に限らない軸方向の卓越判定**が同じ規則で書かれていた
ため、`axis_dominates(dir, axis)` を追加してこれに従わせた。

`ORTHOGONAL_DOT_MAX` は `face_distance` の private 定数だったため `geom` へ移して公開。

### 部材の単位軸ベクトル → `squid_n_core::geom::element_axis`

`elem_axis` が core（`face_distance`）と element（`rigid_zone`）に同名・ほぼ同一で
存在した。element 側は core 側が private のため複製していた。

### 部材種別（柱 |ez|≥0.8 / 梁 ≤0.2 / 中間ブレース）→ `squid_n_design_jp::MemberKind`

同一実装が 4 か所（app の `app/mod.rs` と `viewer/th_detail.rs`、mcp の
`job/design_check.rs`、design-jp の `ultimate/geometry.rs`）にあり、境界値 0.8 / 0.2 は
`steel/buckling.rs`・`joint_wiring/common.rs` にも直接書かれていた。
`MemberKind::{from_axis, from_ez, of_element}` と `MEMBER_COLUMN_EZ_MIN` /
`MEMBER_BEAM_EZ_MAX` に集約した。

`squid_n_core::geom::is_vertical_axis`（45° の 2 分）とは**別目的の規約**である旨は
core 側 doc がすでに明記しており、統合していない（そのままとした）。

### 部材長 → `Model::member_length`

`elem_geometric_length`（app・mcp）と `geometric_length`（design-jp）が同じ計算を
持ち直していた。element 内でも `(dx²+dy²+dz²).sqrt()` の手書きが散在していたため
`geom::vec3::dist` へ寄せた。

### 曲げひび割れモーメント Mc = κ·√Fc·Ze → `squid_n_core::rc_capacity::rc_crack_moment`

同一式が 4 か所に独立実装されていた。同じ骨格曲線を構成する My・αy はすでに
`rc_capacity` へ集約済みで、**Mc だけが漏れていた**（非対称な状態）。

My 比によるクランプは用途ごとに異なる（材端バネ `.clamp(my*0.1, my*0.9)`、
ヒンジ閾値 `.min(my)`、design-jp はクランプなし）ため、呼び出し側に残した。

### ファイバー断面の積分公式 → `squid_n_section::fiber::integrate_fibers`

`section_response`（材料の `trial` を毎回呼ぶ経路）と `GaussPoint::refresh_response`
（トライアル状態をキャッシュ済みの経路）が、断面力 N/My/Mz と 3×3 接線剛性の
積分公式をそれぞれ持っていた。後者のコメントは「結果はビット一致」を要求して
おり、公式が分かれたままでは非線形反復の結果が静かに食い違う。

統合後もビット一致であることは、演算順序（`ea = et*a` を経由する形）が
両者で一致するため保たれる。

### モデル走査 → `Model::node(id)` / `Model::element(id)`

ID から実体を引く箇所で `nodes.iter().find(|n| n.id == id)` の線形探索が 24 か所
以上あった。`Model::validate` が `nodes[i].id == NodeId(i)` を不変条件として検証して
いるため添字で引き、不変条件が崩れた場合のみ線形探索へ落とす実装とした。

### 危険断面位置 → `squid_n_design_jp::design_position`（新設）

`design_positions` / `is_near_design_position` が app と mcp に同一実装で存在した。

要素側の内力評価断面（`squid_n_element` の `eval_sections`）はこれに節点芯
（0.0 / 1.0）を加えたものになる。検定は柱フェース位置で行い節点芯の内力は
用いないため、この差は意図的である（モジュール doc に明記した）。

## 判断を要した項目 — 決定と対応（2026-08-12 に深掘りして決着）

以下は当初「判断が要るため残した」項目で、その後の掘り下げで方針を決めて対応した。
**未対応で残っているのは 3・8 の 2 件のみ**（末尾の「残っている課題」参照）。

### 1. 柱 Mu の ACI 規準（平面保持）→ **削除**

`ultimate::rc_strength::column_axis_shear` が `opts.mu_method` を参照せず、
`MuMethod::Aci` を選ぶと 2 軸せん断の強軸だけ ACI・弱軸は at 式という非対称が
生じていた（2 軸曲げは両軸へ伝播していた）。

調査の結果、ACI 実装は **ACI318 の原典を入手できないまま暫定実装**したもので、
`原典照合リスト.md` にも未登録だった。一方 `docs/` は「ACI318-95 に基づき算定
します」と 1 次資料に基づく旨を断言しており、方針違反の状態だった。参照実装
（市販の一貫プログラム）が同じ切替を持つことが導入動機だったが、原典未照合の
分岐を製品に残すほうがリスクが高いと判断し、`MuMethod` ごと削除した。
これにより上記の不整合も消滅した。

再実装の条件は `dev_docs/v_and_v/終局検定_参照実装照合.md` §3-b に記録した。

### 2. 鉄骨全塑性モーメント Mp のフォールバック → **全形状に Zp を実装**

`plastic_modulus_strong` が H 形・箱形・円形鋼管の 3 形状しか Zp を返さず、
残り 7 形状（組立 H 形・T 形・溝形・リップ溝形・山形・平鋼・中実丸鋼）は
フォールバックに落ちていた。その値が解析実体（`σy·Ze`）とヒンジ判定側
（`σy·1.12·Ze`）で **12% 食い違っていた**ため、要素は降伏しているのにヒンジ判定は
未降伏という状態が生じていた。組立 H 形は実務で使う断面であり稀なケースではない。

矩形帯分解から**等面積軸**まわりに積分する汎用ヘルパを追加し、全 7 形状へ実装した。
山形鋼は `calc_iy` と同一の幾何軸（図心を通る脚に平行な軸。主軸ではない）で定義し、
Ze と軸を揃えて形状係数 Zp/Ze が意味を持つようにしている。`1.12·Ze` のフォールバックは
材端曲げバネと同じ `Ze` へ揃えた。

**フォールバックは到達不能ではない。** `structure_kind_of` は材料の区分が鋼なら形状に
よらず `StructureKind::S` を返すため、壁・スラブ断面（`RcWall`/`RcSlab`）へ鋼材料を
割り当てたモデルは Zp を持たないままこの分岐へ来る（`compute_hinge_thresholds` は
全要素を走査しており、壁を除外していない）。したがってフォールバック値を材端曲げバネと
一致させることが必要で、`hinge.rs` のコメントにその旨を明記した。

### 3. H 形断面の「せん断有効断面積」→ **原典照合リストへ登録して保留**

剛性用（`as_y`/`as_z`）と検定用（`Ay`/`Az`）は**別の物理量**（ティモシェンコ梁の
等価せん断面積 vs 最大せん断応力度を出す有効面積）であり、統合しないのが正しい。
当初「食い違い」と記載したのは誤りで、`docs/` の 3.3 と 6.3 から相互参照を張って
利用者が両者を区別できるようにした。

ただし**剛性用の内部で規約が揃っていない**（矩形は κ=1.2 を適用するのに H 形の
フランジは κ=1.0）。鋼構造設計規準のせん断有効断面積の規定を確認しないと決められ
ないため、`原典照合リスト.md` へ登録して保留とした。

### 4. RC 柱梁接合部の有効幅 bj → **対応不要**

`bai` の max/min は規準どおり意図的な相違（許容応力度は原典図が max と明記、終局は
靭性保証型指針で min が安全側）。共通化できるのは `(a−b)/2` の 1 行だけで、
ヘルパ化するとかえって意図的な差が見えにくくなる。両ファイルのコメントに相違理由が
すでに明記されている。

### 5. 主筋重心の段数の扱い → **多段対応へ統一**

接合部検定・SRC パネル・壁脚・PCa 水平接合面が 1 段目重心固定だったのに対し、
断面算定・部材ランクは多段対応で、**同一モデル内で配筋の解釈が割れていた**。
多段対応の `rebar_tension_dt` へ統一した。

SRC パネルの `mCd = 柱幅 − 2·dt` には直接効く（せい 600 の柱で 13% 減、耐力を
過大評価しない側へ動く）。SRC 規準の mCd が原典の図で「最外縁主筋の中心間」と
定義されている場合は 1 段目基準が正しくなるため、原典入手時に再確認すること。

**RC 柱梁接合部の「影響なし」は条件付きだった**（当初の記述を訂正）。`Qdj1 = ΣMy/j`
の d_eff が約分されるのは、**接合部の全梁が同一の dt を持つ場合に限る**。`beam_j` は
先頭梁（`beam0`）のみから決まるのに対し、`ΣMy` は各梁が自身の dt で Mu を算定して
合算するため、十字形接合部で梁ごとに配筋段数が異なると約分しない。

D25・かぶり 40・帯筋 D10・せい 600 の同一断面で、beam0 が 1 段筋・beam1 が 2 段筋の
場合を検算すると、ΣMy は 1075 → 1043.75 となり **Qdj1 が 2.9% 減る**。これは 2 段筋の
梁が実際に伝える曲げが小さいことを反映した結果であり、従来（両梁とも 1 段目基準）は
2 段筋の梁の My を過大評価していた。したがって変更後のほうが正しい。

なお `beam_j` を先頭梁で代表させる簡略化は本変更以前からのもので、新規の問題ではない。

### 6. CFT 充填コンクリートの断面性能 → **共通ヘルパへ統合**

当初「退化寸法の扱いが異なる」と記載したのは誤読だった。両者とも**寸法ごとに
`max(0.0)` / 個別ガード**を掛けているため、退化時はどちらも充填コンクリートの
寄与がゼロになり結果は一致する。

`SectionShape::cft_core_props`（`CftCoreProps`: 内法寸法・A・Iy・Iz・J）へ切り出し、
剛性側（`cft_equivalent_props`）と耐力側（`ultimate::cft_check`）の双方が呼ぶように
した。内法寸法は 0 で下限クランプして返し、**退化時の扱いは呼び出し側が選ぶ**
（剛性側は鋼管のみへフォールバックして `None`、耐力側は充填ゼロのまま検定を続行。
どちらも「充填コンクリートが効かない」という同じ結果になる）。挙動は完全に保存した。

### 7. 標準荷重組合せの 2 系統 → **core へ集約**

`combo.rs` の依存が `squid_n_core` のみで層構造上の障害がなかったため、
`squid-n-core/src/load_combo.rs` へ移し、`default_combinations` を
`standard_combinations` の固定引数版として実装し直した。手動同期テストは不要に
なり、対になる `is_short_term_combo` と `LoadCaseKind::is_long_term` が同じ
クレートに揃った。

### 8. 表示側の単位換算 → **`units::to_display` を新設**

当初「`/1000.0` の重複」と捉えていたが、本質は**「この量をどの単位で見せるか」という
慣例の情報源が散っている**ことだった。実際、同じ断面性能が画面によって別単位で
表示されていた（断面表は cm 系、部材情報パネルは mm 系、準備計算は生係数）。

量ごとの表示単位を `to_display` に集約し、断面性能は JIS 形鋼表の慣例に合わせて
cm 系へ統一した。単位ラベルの表記ゆれ（`kN·m` U+00B7 と `kN・m` U+30FB の混在）も
解消した。値の関数とラベル定数は分離し、小数桁は規約化していない。

**未完**: `to_display` の関数・定数を使う書き換えは、断面性能の 3 箇所と単位ラベルの
正規化までで、力・モーメント・長さの `format!` 内の生リテラル（app 中心に約 60 箇所）は
そのまま残っている。誤変換を避けるため 1 か所ずつ意味を確かめる必要がある。

### 9. mcp と app の解析ジョブ配線 → **`squid-n-job` を新設**

MCP は剛域のみを適用し、**仕口パネルのない剛性**で解いていた（app 側ですでに一度
修正済みの不具合と同型）。加えて `PushoverControl`・靭性算定法・記録フラグを既定値で
ハードコードしており、GUI で選べる解析条件が MCP から使えなかった。

新クレート `squid-n-job`（Layer 6。app・mcp は Layer 7 へ）へ前処理・解析条件
（`AnalysisSettings`）・各解析の純粋計算・エラー型を集約し、両者が同じ実装を通るように
した。結果の整形は各クレートに残している（MCP の JSON スキーマと GUI の表示要件が
結合するのを避けるため）。

### 10. `Result<T, String>` → **`squid-n-job` に `JobError` を定義**

同じ失敗でも入口によって文言が違っていた（app は日本語、mcp は英語）。`JobError`
（thiserror・`Display` は日本語・`kind()` で機械可読な種別コード）へ集約した。

`squid-n-solver` 内部の `Result<_, String>` は増分解析のコールバック（`SolverFn`）を
通るため型化すると非線形反復の実装全体に波及する。`squid-n-job` の境界で変換すれば
app/mcp から見た品質は確保できるため、そのままとした。

### 11. テストのモデル生成ヘルパ → **対応不要**

9 個の `fn node` はシグネチャが全部異なり、各テストが必要な最小限を書いている健全な
状態。共通化すると引数が増えて逆に読めなくなる。クレート横断の共通化は循環依存を
避けるためにも妥当。

## 調査の結果、重複ではなかったもの（誤認防止）

以下は「同じ物理量に見えるが別物」であり、統合してはならない。

- **開口低減率**: 剛性用 `r = 1 − 1.25·r0`（RC 規準）と耐力用 `r2`（RC 規準 18 条）は
  準拠規定も目的も異なる。実体は `core::rc_wall_capacity` に一本化済みで、
  design-jp・element は委譲のみ。
- **せん断終局 Qsu**: 許容 QA 式・荒川 mean 式・塑性理論式・靭性指針式は目的が
  排他的で並存が正しい。荒川式の実体は `core::rc_capacity` の 1 か所のみ。
- **パネルゾーン**: κ・Ve といった幾何は `core::panel_zone` に一本化され、剛性側
  （element）と耐力側（design-jp）が同じ実装を参照している。pMy は鋼構造・SRC で
  それぞれ 1 か所のみ。
- **N-M 相関**: 許容応力度の弾性 N-M 曲線・終局の軸力端点・ACI 平面保持解析は
  前提の異なる別モデル。
- **カタログ断面値と形状式算定値**: `squid-n-section` の JIS 規格断面表（フィレット
  半径込みの実測ベース）と `core::section_shape::properties` の閉形式は、同じ呼び名の
  断面でも A/Iy/Iz/J が微妙に異なる。意図的な設計（カタログは JIS 値の精度を優先）
  だが、利用者から見ると「カタログ経由と手入力で数値が違う」ことになるため、
  `docs/` に記載があるか要確認。
- **NewRC 構成則の Ec**: `material::newrc` の `Ec = 4k·(σB/1000)^(1/3)·10⁵·(γ/2.4)²`
  は新 RC プロジェクト式（工学単位系）で、RC 規準式とは別物。
- **ID / DofMap**: `core::ids::id_newtype!` と `core::dof::DofMap` に完全に一本化
  されており、再実装はない。
- **`squid-n-skeleton`**: 非テストコードから参照されないが、これは意図的な V&V
  参照実装（design-jp の dev-dependency として `rc_mu_simple` の突合に使う）。
  クレート doc 自身がそう明記している。削除しないこと。

## 統合の判断基準（今後の指針）

1. **同じ数式・判定規則が 2 か所以上にあれば、下層クレートへ出す。**
   「依存できないから複製する」は解ではない。共通部分だけを下層へ出せば依存の
   向きは崩れない。
2. **用途ごとに異なるのは「クランプ・フォールバック・係数の選択」であることが多い。**
   式そのものを共有し、これらは呼び出し側に残すと、意図的な差が読み取れる形で
   単一情報源にできる（Mc の統合がこの形）。
3. **意図的に異なるものは、両方の doc から相互参照する。** 参照がないと、後から
   読む者には食い違いなのか意図なのかが判別できない（上記「判断が要るもの」の 2 が
   まさにこの状態）。
4. **可視性が理由の複製は、可視性を上げて解消する。** `pub(crate)` へ上げるだけで
   済むことが多い（`rc_dt`・`section_props` がこの形だった）。
