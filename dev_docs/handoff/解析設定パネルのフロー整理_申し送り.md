# 解析設定パネル（右パネル）のフロー整理

作成日: 2026-07-25
対象ブランチ: `claude/right-panel-flow-organization-gr10yg`
関連文書: `準備計算_申し送り.md`、`UI導線改善.md`、`../specs/UI設計.md`

## 1. 背景（変更前の問題）

解析設定パネルは、実装した機能を追加した順に縦へ並べており、一貫計算の手順とは
一致していなかった。結果として次の混在が生じていた。

| 変更前の状態 | 何が混在していたか |
| --- | --- |
| 「🛠 準備計算 実行」と「🏢 階の自動生成」が別ボタン | 階の定義は準備計算の一部（階高・剛床・地震用重量はほぼ全項目の前提）なのに、利用者が 2 つの実行導線を使い分ける必要があった |
| 階の定義に「構造: RC / S / SRC」の手入力ボタン | 断面形状から決まる情報を利用者に入力させていた（入力とモデルの不整合が起こりうる） |
| 「地震静的 (Ai 分布)」に独立した「▶ 実行」 | 同じ水平力が EX/EY 荷重ケースにも同期されており、荷重組合せ経由でも解かれる。同じ計算に 2 つの入口があった |
| 「風荷重静的」に独立した「▶ 実行」 | 同上。さらに WX/WY の荷重ケースが存在せず、荷重組合せの \\(G+P\pm W\\) は生成されても解けなかった |
| 「Z表CSV読込…」「市町村」参照 | Z は告示別表からの読み取り値 4 種（1.0/0.9/0.8/0.7）であり、CSV ローダ機構は過剰だった |
| 質量方式が「固有値」セクション内 | 実際には階生成時にモデルへ反映される準備計算の入力 |

## 2. 変更後の構成

```
解析設定
  最終実行 / 結果の陳腐化表示
  ① 準備計算
      [🛠 準備計算 実行] [📋 結果を表示] / ステータス
      ▸ 地震力の条件 (Ai 分布)   T算定・Z・地盤種別・C0
      ▸ 風圧力の条件             V0・粗度区分・パラペット
      ▸ 計算条件                 質量方式・並列スレッド数
      ▸ 階の定義                 一覧（W 手入力・階種別のみ編集可）
  ② 解析
      ▸ 荷重ケース（静的）       DL/LL/EX/EY/WX/WY… を選んで実行
      ▸ 荷重組合せ
      ▸ 固有値
      ▸ プッシュオーバー
      ▸ 時刻歴応答（線形）
```

「① で解析入力を確定 → ② で解く」という一貫計算の手順そのものが画面の並びになった。

## 3. 実装した変更

### 3.1 階の定義を準備計算へ統合

- `App::run_preparation` は毎回 `generate_stories_action` を呼ぶ（変更前は階が未定義の
  ときだけ生成し、既存の階は手入力保護のため再生成しなかった）。UI から
  「階の自動生成」ボタンを削除。
- 毎回再生成しても利用者の手入力が消えないよう、`Story` に
  `weight_override: Option<f64>`（地震用重量の手入力値）を追加した。
  `squid_n_load::story_gen::carry_over_manual_story_settings` が、床レベルが一致する
  旧階から `weight_override` と `level_kind`（一般 / PH / 地下。自動判定できない）を
  引き継ぐ。
- 毎回再生成する構成では「押すたびに undo 履歴が積まれ、解析結果が stale になる」
  という副作用が出るため、`generate_stories_action` を冪等にした。
  `story_gen_changes_model` が `ApplyStories` の書き換え対象（階・所属階・剛床拘束の
  並び・剛床代表節点・`generated_masters`・質量方式）を突き合わせ、差分が無ければ
  コマンドを発行せず `mark_edited` も呼ばない。所属階の比較では、`ApplyStories` が
  `node_story` の適用後に `rep_nodes` で節点を丸ごと置換する順序に合わせ、
  剛床代表節点を除外する（代表節点の所属階は `rep_nodes` 側が正）。
- `weight_override` が `Some` のときは `seismic_weight`（実効値）へも反映するため、
  解析・設計側の読み出しは `seismic_weight` のままでよい（変更なし）。
  `squid_n_edit::SetStoryWeight` が両者を更新し、逆操作は新設の `RestoreStoryWeight`。
- 階を生成できないモデル（節点なし・単一レベルのみ）でも `run_preparation` は
  中断しない。生成エラーを `last_error` に残したまま、階を前提としない項目
  （剛域・断面性能・幅厚比・整合性チェック）の集計まで進める。

### 3.2 主要構造種別の自動判定

- `StoryStructure::of_section_shape`（断面形状 1 つ → RC / S / SRC）と
  `StoryStructure::majority`（本数の最多。同数は RC → SRC → S の優先）を `squid-n-core` に追加。
- `story_gen::assign_story_structures` が、各階に属する柱・梁（`ElementKind::Beam` で
  形状定義を持つもの）を数えて `Story.structure` を決める。部材の所属階は
  「材端節点のうち最も高い節点の所属階」とした。
- 同数時に S を採らないのは、S の階が増えるほど略算周期 \\(T\\) が長く \\(R_t\\) が
  小さくなり地震力が下がるため（S を採らない方が安全側）。
- UI からは構造種別の手入力ボタンを削除し、階名の行に判定結果を表示するだけにした。
  `squid_n_edit::SetStoryStructure` は使われなくなったため削除（テストも削除）。

### 3.3 地震静的・風荷重静的を荷重ケース解析へ統合

- 風荷重も EX/EY と同じ扱いにするため、
  `squid_n_solver::analysis::build_wind_load_case_from_model` を新設し、
  `Analysis::wind_static` はこれを解くだけにした（載荷ロジックの一元化）。
- `WX_CASE_NAME` / `WY_CASE_NAME`（"WX" / "WY"）を `squid-n-core` に追加し、
  `App::sync_wind_load_cases_action` が準備計算で WX/WY へ層水平力を同期する
  （`sync_seismic_load_cases_action` と同じ冪等な規約）。
  `sync_auto_load_cases_action` の同期スキップ判定ハッシュに V0・粗度区分・
  パラペット高さを追加した。
- 「地震静的 (Ai 分布)」「風荷重静的」セクションを廃止。実行は「荷重ケース（静的）」に
  一本化し、`App::start_load_case_job` が `App::standard_lateral_case` の判別により
  EX/EY → `start_seismic_job`、WX/WY → `start_wind_job`、それ以外 → `start_linear_static_job`
  へ振り分ける。結果キー（`StaticCaseKey::Seismic` / `Wind`）は変更していないため、
  剛心の精算・保有水平耐力の判定など既存の参照はそのまま動く。
- `auto_generate_combinations_action` は標準ケース名で方向を判別するようにした
  （EX/EY/WX/WY）。従来は種別 `Wind` の先頭 1 件を無条件に `wind_x` としており、
  WY しか無いモデルではそれを WX と誤って扱っていた。標準名のケースが 1 つも無い
  モデルに限り、従来どおり種別の先頭 1 件を X 方向として扱う。
- 空の水平力ケースを参照する組合せのガード（`empty_seismic_case_in_combo`）を
  `empty_lateral_case_in_combo` へ改め、風（kind=Wind）も対象にした。
  \\(G+P\pm W\\) の組合せを実際に生成するようになったため、空の WX/WY を参照した
  まま解いて風の項が黙って 0 になる（長期と同じ応力を短期の検定に使う）ことを防ぐ。

### 3.4 加力方向の選択を設計タブへ移設

`analysis_cfg.seismic_dir` は解析の実行条件ではなく、層指標（層間変形角・剛性率・
偏心率）と必要保有水平耐力の**判定を評価する方向**である。従来は「地震静的」
セクションの方向選択がこの値を兼ねていたため、そのセクションの廃止で操作手段が
無くなってしまう。値を消費している設計タブの層指標セクション先頭へ
「加力方向: X / Y」を置き直した。

### 3.5 Z 表 CSV ローダの廃止

- `squid_n_load::z_table` モジュール、`App::{z_table, z_table_municipality,
  load_z_table_from_csv, apply_z_from_municipality}`、および UI の
  「Z表CSV読込…／市町村／Z参照」を削除。Z は準備計算「地震力の条件」で直接入力する
  （範囲 0.7〜1.0、既定 1.0。既定値は変更前から 1.0 で、変更していない）。

## 4. 影響と非互換

- **モデルスキーマ**: `Story.weight_override` を追加（`#[serde(default)]` のため旧データは
  「手入力なし」として読める）。スキーマ版は上げていないので既存 SCZ の読み込みは通る。
  ただし本変更より前に保存したファイルでは、手入力していた地震用重量も
  「手入力なし」として読まれるため、**最初の準備計算で自動算定値へ戻る**。
  自動算定値と手入力値を事後に区別する手段が無いための割り切りであり、
  該当するモデルは階の定義で入力し直す必要がある。
- **準備計算の副作用**: 実行のたびに階が再生成されるため、階の一覧・剛床代表節点の座標が
  モデルの変更に追従するようになった。手入力の重量・階種別は引き継がれるが、
  それ以外（自動算定の重量・剛床構成）は毎回上書きされる。
- **公開 API の削除**: `squid_n_edit::SetStoryStructure`、`squid_n_load::z_table`、
  `App::{load_z_table_from_csv, apply_z_from_municipality}`。
- `App::{run_seismic, start_seismic_job, run_wind, start_wind_job}` は残している
  （UI の専用導線は無くなったが、荷重ケース実行の振り分け先として使われる）。

## 5. 残課題

- 準備計算が階を毎回再生成するため、階の名称（`1F`・`2F`…）も毎回自動採番になる。
  階名の手入力を許すなら `weight_override` と同じ引き継ぎ機構へ載せる必要がある。
- 主要構造種別の判定は柱・梁の本数の多数決であり、告示の「柱及び梁の大部分が鉄骨造で
  ある階」を本数比で近似している。断面の耐力・剛性で重み付けする方が原典に近い可能性が
  あるため、原典照合リストへの追加を検討する。
- 風荷重の WX/WY は PH 階を負担層から除外している（`wind_precalc_for_model` の既存仕様。
  PH 階への風荷重接続は未対応の残課題）。
- 準備計算は UI スレッドで同期実行する。階の生成と床荷重分配は交差小梁スラブを持つ
  大規模モデルで重くなり得る（`tests/perf_probe.rs` が計測対象にしている）。
  従来から「階の自動生成」ボタンが同じコストだったので新たな悪化ではないが、
  主導線になった以上、解析ジョブと同じくバックグラウンド化する価値がある。
