## 1. 既存設計の何が誤っていたか

### 1.1 「床版は常に存在する」という前提が誤り

PR #218 は床領域を `Slab` そのものとし、`WallRegion` だけを独立した型にした。
根拠は「床版のない床領域は荷重も発生せず、小梁をまとめる意味がない」であった。

**これは誤りである。** 吹抜けに架かる繋ぎ小梁、階段室まわり、デッキを張らない範囲の小梁は、
床版がなくても小梁をまとめる単位として実在する。版なし壁領域を認めながら版なし床領域を認めないのは、
対称性の破れではなく単に前提の誤りである。

### 1.2 「壁版は解析要素である」という前提が誤り

`WallRegion.wall` は `Option<ElemId>` で、`validate` は `ElementKind::Wall` であることを確認している。

**これも誤りである。** 壁面には雑壁・仕上げ材のように解析要素にならない荷重があり、
壁版を解析要素に限ると受け皿がない。実際、現状のコードには次の欠落がある。

| 表現 | 実体 | 荷重の扱い |
|---|---|---|
| `Element`（`Wall`/`Shell`） | 解析要素（耐震壁） | 自重は ρ·t·(A−開口) ＋開口重量のみ。**仕上げ荷重を入れる欄がない** |
| `WallAttr` | 要素に紐づく開口・三方スリット | 自重の開口控除・剛性低減 |
| `MiscWall` | フレーム外雑壁（解析対象外） | `weight_per_area`（仕上げ込み）を 0.5m 分割で節点へ集計 |
| `WallRegion` | PR #218 で追加 | なし |

仕上げ荷重は線材（`MemberWeightCfg.w_f`）とスラブ（`Slab.loads`）にはあるが、壁要素にはない。

### 1.3 領域の粒度が定義されていなかった

最大の見落としはこれである。**領域は、床であれば大梁で囲まれた領域、壁であれば柱と梁で囲まれた領域ごとに 1 つ**でなければならない。
この不変条件がないと、荷重を主架構へ分配する処理が定義できない。

- 領域がパネルより細かい（小梁で切られた小片）と、境界辺の一部が小梁になり、分配先が主架構でなくなる
- 領域がパネルより粗い（複数パネルにまたがる）と、領域の内部に大梁があり、分配先を特定できない

PR #218 の設計にはこの制約がなく、そのため荷重分配の設計を持っていなかった。

## 2. 現状コードの問題点（実測）

`crates/squid-n-app/tests/fixtures/model.stb`（4 層＋PH の S 造。節点 166・解析要素 115・二次部材 56・スラブ 82）で実測した結果を記録する。

### 2.1 小梁設計が別階のスラブを掴んでいる（不具合）

`design_secondary_joist_checks`（`crates/squid-n-app/src/app/actions/design/check.rs:337`）は、
小梁中点が属するスラブを `point_in_slab_boundary` の **XY 平面のみ**で判定し、`find` で最初に見つかったものを採る。
`point_in_slab_boundary`（`crates/squid-n-load/src/floor/geometry.rs:72`）は XY へ投影した判定であり、Z を見ない。

**結果、56 本の小梁のうち 49 本が別レベルのスラブに割り当たっている。**
その小梁は、別階のスラブの板厚から出る固定荷重と、別階のスラブ形状から出る負担幅（`slab_perp_extent`）で設計されている。
なお本フィクスチャは全スラブが `usage = None`（積載荷重 0）のため、積載荷重の取り違えは今回は起きていない。
室用途が設定されたモデルでは、それも取り違える。

レベル一致を条件に加えると、別レベルへの帰属は 0 本になる。**ただしそれでも帰属は一意にならない。**
同一レベル内の該当枚数は次のとおりで、1 枚に決まる小梁は 1 本もない。

| 判定条件（いずれもレベル一致つき） | 該当 0 枚 | 1 枚 | 2 枚 | 3 枚 |
|---|---|---|---|---|
| 厳密内包（辺上を除く） | **56** | 0 | 0 | 0 |
| 内部または辺上（現行 `point_in_slab_boundary`） | 0 | 0 | 46 | 10 |

**小梁は必ずスラブの辺上に載る。** §2.2 のとおりスラブが小梁で分割されているためで、
厳密内包で判定すると 56 本すべてが該当なしになる（＝小梁設計が全滅する）。
複数該当したスラブの断面は 56 本すべてで同一のため、面荷重強度 w は同じで、
差が出るのは負担幅の算定に用いるスラブ形状だけである。

この不具合は移行と切り離し、**先に単独の `fix` PR で直す**（§5 Step 0。実施済み。
記録は [`v_and_v/小梁設計のスラブ帰属_レベル一致_2026-08.md`](../v_and_v/小梁設計のスラブ帰属_レベル一致_2026-08.md)）。
帰属の一意化は Step 0 では解けない。パネル単位の分配（D1・D9）へ移して初めて解ける。

### 2.2 荷重分配が入力データの細分に依存している

`auto_loads.rs:122` は、スラブ境界の辺 `LoadTarget::Edge(k)` について `find_beam(n0, n1)` で大梁要素を探し、
見つからなければ `LoadTarget::Span([n0, n1])` へ落として、最終的に辺の両端節点へ振り分ける。

フィクスチャのスラブ 82 枚の共有辺 55 本の内訳は次のとおりである。

| 共有辺の種別 | 本数 |
|---|---|
| 大梁がある辺 | 14 |
| **小梁がある辺** | **41** |
| 部材のない辺 | 0 |

つまり ST-Bridge のスラブは小梁で細分された小片であり、小片の辺荷重は**小梁の曲げを一切経由せず**
小梁の両端節点へ落ちている。そこから `squid-n-load/src/secondary.rs` の CMQ 経路で大梁の中間集中荷重になるため、
大梁への総和は保たれる。保たれるが、小梁は荷重伝達材として働いておらず、辺荷重を両端へ振る役をしているだけである。
小梁の曲げは分配経路に現れず、`check.rs` が幾何から負担幅を再導出して別計算している（それが §2.1 の不具合）。

**これが成立しているのは、ST-Bridge のスラブが既に小梁で細分された状態で入ってくるからにすぎない。**
パネル内に小梁があるのにスラブが分割されていない入力、および版のないパネルでは、この経路は何も出さない。

### 2.3 パネル単位へ統合できることの確認

大梁が囲むパネル数を、独立した 2 つの方法で求めた。

1. **Euler の公式**: レベルごとの水平大梁を平面グラフとみなし、内部面数 `F = E − V + C` を数える
2. **幾何隣接による統合**: スラブの辺が 100mm 以上重なる隣接を、その重なりを大梁が覆っていない場合に限り結合する（union-find）

| レベル Z [mm] | 水平大梁 V/E | Euler の内部面 | スラブ | 幾何統合後 | 断面混在 | 用途混在 |
|---|---|---|---|---|---|---|
| 200 | 12/17 | 6 | 14 | 6 | 0 | 0 |
| 4700 | 12/17 | 6 | 22 | 6 | 0 | 0 |
| 8700 | 12/17 | 6 | 22 | 6 | 0 | 0 |
| 12700 | 14/20 | 7 | 21 | 7 | 0 | 0 |
| 16500 | 4/4 | 1 | 3 | 1 | 0 | 0 |
| **計** | | **26** | **82** | **26** | **0** | **0** |

**2 つの方法が全レベルで一致し、82 枚 → 26 パネルへ統合できる。統合後に板厚（断面）または室用途が混在するパネルは 0 件である。**
パネル単位の 1 枚の版へ畳んでも情報は失われない。

**注意**: 辺の節点対が完全一致する隣接だけを結合する素朴な union-find では 41 クラスタとなり、真のパネル数と合わない。
大梁が節点で分割されている箇所（T 字取り付き）で辺の節点対が一致せず、同一パネル内が分断されるためである。

### 2.4 `region_gen`（Step 1 実装済み）による確認

面走査の実装（`squid-n-core/src/region_gen.rs`）でパネルを検出したところ、
§2.3 の 2 通りの見積もりと**完全に一致**した（レベル別 6 / 6 / 6 / 7 / 1、計 26）。
パネル面積の合計は各レベルのスラブ面積の合計と一致する（相対差 1e-6 未満）。

この真のパネルに対してスラブ片を割り当て直し、D3・D9 の前提を再測定した。

| 項目 | 結果 |
|---|---|
| パネル数 | 26（すべて版を持つ） |
| どのパネルにも割り当たらなかったスラブ | 0 枚 |
| パネルあたりのスラブ片数 | 1 枚: 3、2 枚: 4、3 枚: 5、4 枚: 14 |
| **断面が混在するパネル** | **0** |
| **室用途が混在するパネル** | **0** |

**パネル単位の 1 枚の版へ畳んでも情報は失われない**という D3・D9 の前提は、真のパネルでも成立する。

この測定は `crates/squid-n-app/tests/full_model.rs` の `slabs_fold_into_panels_without_mixing`
として固定した（判定は `Panel::contains` を用いる。自作の内外判定は辺上の点で誤るため、
実装が使う述語をそのまま用いること）。あわせて、節点を共有せずに交差する大梁が 0 組であること
（面走査が前提とする平面グラフが成り立っていること）も同テストで確認している。

## 3. 決定事項

利用者との設計検討（2026-08-23）で決めた内容を、決定単位で記録する。
D1〜D12 が領域の基本設計、D13〜D23 が主架構に囲まれない領域（片持ち・パラペット等）の扱いである。

### D1. 領域は「大梁で囲まれた領域 / 柱と梁で囲まれた領域」ごとに 1 つ（最重要）

床領域は水平面内で大梁が囲む閉領域（パネル）ごとに 1 つ、壁領域は鉛直構面内で柱と梁が囲む閉領域ごとに 1 つとする。
**これは他のすべての決定の前提であり、`validate` で守る不変条件とする。**
現時点の `validate` は**完全一致の重複だけ**を見る。幾何的な一意性の検査を広げるのは Step 3 であり、今波では `validate` を広げない。

この制約により、荷重分配の規則が幾何から一意に決まる。

- 境界辺は必ず主架構（大梁、または柱・梁）である。**囲まれた領域については** `find_beam` が外れる
  `Span` フォールバックが不要になる（取り付き領域は下記のとおり別途対応が要る）
- 領域内の部材は必ず二次部材である。「境界＝最終の受け手、内部＝中間の受け手」が幾何で確定する
- 版は 1 領域、二次部材も 1 領域にしか属さないため、二重計上が構造的に防げる
  （`specs/床領域と壁領域.md` が残課題に挙げていた「床をまたいだ小梁の重複」の検証は不要になる）

### D2. 版なし領域を認める（床・壁とも）

床領域・壁領域とも版を任意とする。`Slab` を床領域そのものとする設計は破棄する。

### D3. 領域が版の仕様を直接持つ

**⚠ この決定は Step 4 着手時に誤りと判明し、§3.1 のとおり覆っている（床側のみ。壁側の
`WallRegion`/`WallPlate` は本決定のまま Step 7〜9 へ持ち越す）。** 以下は決定当時の記述として残す。

領域は「幾何（境界）＋ 版の仕様（任意）＋ 二次部材」を持つ。
版の仕様には面荷重（自重・仕上げ）・開口・厚さ・材料が入る。

`Model.slabs` は `Model.floor_regions` へ置き換える。`MiscWall` と `WallAttr` は壁領域へ吸収する。
これにより、雑壁は「解析算入しない壁領域」、耐震壁は「解析算入する壁領域」として同じ型に収まる。

版を ID 参照（`Option<SlabId>` / `Option<ElemId>`）にする案は退けた。
スラブは解析要素ではないため 2 リストに分ける必然性がなく、分ければ
「版を消したときの `Option` 戻し・ID 繰り上げ」という `WallRegion.wall` と同じ保守が発生するためである。

### D4. 解析要素は領域から生成する派生物とする

入力の正は領域とし、剛性に算入する領域からは解析要素（`ElementKind::Wall`/`Shell`）を生成する。
領域と要素・断面に幾何と厚さが二重に存在する状態を作らない。

**代償**: 要素 ID が入力ではなく生成物になるため、断面力の表示・保有水平耐力の対象指定・ST-Bridge 出力といった
「要素 ID を参照先にしている経路」を、すべて領域 ID 起点へ張り替える必要がある。
現状の壁要素を直接編集する UI（`tables/wall_attrs.rs`・要素テーブル）は領域編集に置き換わる。

### D5. 生成は準備計算で行い、生成物はモデルに残さない

生成の置き場所は `App::ensure_preparation`（`crates/squid-n-app/src/app/preparation.rs:408`）とする。
既にモデルを触る同期処理（剛域の反映・DL/LL/EX/EY の同期）を冪等に行い、ハッシュでスキップ判定し、
モデル編集で `preparation_stale` が立つ枠組みを持っているためである。
解析入口ごとに書くと静的・固有値・増分・時刻歴で重複する。

生成した要素は `model.elements` へは入れず、展開済みの解析用モデルを派生データとして作る。
`io.rs:254` の「準備計算・解析結果はいずれもモデルから再計算できる派生データ」という既存原則に従う。
保存対象は領域のみで、開き直すと再生成される。生成は決定的（領域の順序で並べる）とし、同じ ID になるようにする。

**条件**: 展開関数は `squid-n-app` ではなく下位クレート（`squid-n-load` か新設）に置き、
GUI の準備計算とヘッドレス実行（`squid-n-job`・`squid-n-mcp`）の両方から同じ関数を呼ぶこと。

### D6. 二次部材の実体は領域が持つ

`Model.secondary_members` の横断リストは廃止し、`FloorRegion.joists: Vec<SecondaryMember>` /
`WallRegion.posts: Vec<SecondaryMember>` として領域が実体を持つ。参照は「領域 ID ＋ 領域内の添字」とする。

所属が構造的に必然になり、`validate` に規則を足さずに済む。
**あわせて、PR #218 で入れた `SecondaryMemberId` の「配列添字と一致」不変条件・`visit_secondary_member_ids`・
`retain_secondary_members` の ID 張り替えは、まるごと不要になる**（§6 参照）。
あの仕組みは横断リストと領域参照が二重に存在することから生じた保守負担であった。

**代償**: 二次部材を走査する箇所がすべて二段ループになる。非テストの走査箇所は §7 のとおり 10 箇所ほどで、
`Model` に「全二次部材を走査する反復子」を 1 本用意すれば多くはそれで置き換えられる。

### D7. 所属は「中点の厳密内包 ＋ Z 一致」で決める

二次部材の所属先は、中点がその**パネル**の内側にあり、**同じレベルにある**ことで決める。
辺上（`point_on_polygon_boundary`）は内包に含めない。含めると、辺を共有する隣接パネルの双方が該当するためである。

**この規則が使えるのはパネルに対してだけである。** 現行の小片スラブに当てはめると、
小梁は必ずスラブの辺上に載るため 56 本すべてが該当なしになる（§2.1）。
パネルの境界は大梁だけであり、小梁はその内部に入るため、厳密内包が成立する。

D1 によりパネルは平面を覆うため、版の有無に関わらず所属先は決まる。
それでも決まらない小梁（建物外周の外など）は診断に出し、黙って別の領域へ寄せない。

### D8. 領域は主架構から生成する

水平面ごとに大梁の閉路（平面グラフの面）を検出して床領域を、
鉛直構面ごとに柱・梁の閉路を検出して壁領域を作る。取り込んだ版は該当パネルへ統合する。

版から組み立てる案（共有辺に大梁がないスラブ片を結合する）は退けた。
版のあるところにしか領域ができず、**版のないパネルが領域として現れない**ためである。

`axis_gen::generate_axes`（柱位置から通り芯を自動生成し、`AxisSource::Auto`/`Manual` で再生成対象を分ける）を前例として、
`region_gen` を同じ位置づけで置く。

**申し送り**: AGENTS.md は「自作実装よりライブラリを優先」とするが、
**平面グラフの面抽出（最小閉路の列挙）を行う保守された Rust クレートは見当たらず、ここは自作になる見込みである。**
アルゴリズムは各節点で出辺を角度順に並べ、進入辺の次の辺を選んで一周する定型手法（面走査）で、実装量は 150 行程度。
外周面を捨てる処理が要る（**符号付き面積が負の面**として判別すること。面積の大小で判別すると、
中庭のある建物で内部面を誤って捨てる。§8.1 参照）。

### D9. 領域内の分配は「小梁で再分割して既存の三角形・台形分配」

**⚠ 「帰結」の一文（`JoistLine` 廃止）は §3.1 の修正で覆っている。`JoistLine` は
`FloorRegion.joists`（交差小梁の格子解析用の手入力）として存続する。** 小片への再分割自体は
D9 のとおり実装した（`squid-n-load::floor::distribute_region`）が、小片の実体は `FloorRegion`
ではなく新設した `Slab`（大梁または小梁で囲まれた版）である。

パネル境界と小梁で平面を再分割して小片を作り、各小片を既存の三角形・台形分配で境界（大梁または小梁）へ配る。
小梁が受けた分は単純梁の反力として境界大梁の中間集中荷重にする。

三角形・台形分配は日本の設計慣行で `docs/` に計算根拠が既にあり、その根拠を変えずに済む。
これは §2.2 でいま入力データが肩代わりしている細分を、プログラム側へ移す変更である。
小片の生成は D8 の面走査に小梁の辺を足すだけで、同じ実装を再利用できる。

負担面積法（`distribute_polygon_supported` のグリッドサンプリング）へ一般化する案は、
結果が変わり計算根拠の記述と検証記録を書き換えることになるため退けた。
床格子サブモデル（grillage）で全床を解く案は、`JoistLine.pinned_onto` を含む格子解析をすべての床に課すことになり、
計算コストと説明の複雑さに見合わないため退けた。格子は交差小梁がある領域に限った上乗せとして現状の位置づけのまま残す。

**帰結**: `JoistLine`（`Slab.joists`）は役目を終える。小梁の実体は領域が持ち（D6）、細分は面走査が行うためである。

### D10. 領域は保存対象とし、再生成は「作り直し」ではなく「入れ直し」

領域を保存対象（利用者入力の持ち主）とし、準備計算で主架構からパネルを再検出して
既存領域と**重心・レベルで対応付け**、版仕様と二次部材を引き継ぐ。

重心とレベルをキーにすると、梁が節点で分割されて境界の節点列が変わっても対応が付く（重心も面積も変わらないため）。
パネルが実際に割れた・融合したときだけ対応が外れる。そのときは利用者入力を引き継げないのが正しい挙動であり、
属性未設定の新規領域として現れ、診断に「引き継げなかった領域が N 件」と出す。

再生成時は全二次部材をいったん回収し、パネルを検出し直し、D7 の規則で入れ直す。二次部材そのものは消えない。

### D11. 領域は表示名を持つ

床領域・壁領域とも `name: String` を持たせる。現状の `Slab` は名前を持たず `SlabId` だけで、
ナビゲータでも番号でしか見えない。意図した版なし領域（「階段室」「吹抜け」）と、
所属を引き継げなかった領域を、フラグを増やさずに名前で区別できる。

### D12. ST-Bridge の持ち方には引きずられない

取り込みは「ST-Bridge の構造を写す」処理ではなく「正しいモデルへ変換する」処理と位置づける。
**結果として ST-Bridge との往復互換性が下がってもよい。**
出力で表現しきれないもの（版なし領域、パネル統合した版）は落ちてよい。

### D13. 領域には「囲まれた領域」と「取り付き領域」の 2 種別がある

床領域・壁領域とも、次の 2 種別を持つ。D1 の「囲まれた領域ごとに 1 つ」は前者にのみ適用する。

| 種別 | 境界の決まり方 | 生成 | 数の制限 |
|---|---|---|---|
| 囲まれた領域 | 主架構の閉路（大梁、または柱と梁） | 準備計算で自動生成（D8） | 1 閉路につき 1 つ（D1） |
| 取り付き領域 | 取付き先 ＋ 利用者が与える張り出し量 | 利用者入力・取り込み時の変換 | なし |

床の片持ちスラブ・バルコニー・出隅と、壁のパラペット・腰壁・垂れ壁・自立壁は、すべて取り付き領域である。
これらは **主架構に囲まれていない**点と、**輪郭が主架構から導けない利用者データである**点が共通しており、
D8 の閉路検出では生成できない。片持ちスラブの跳ね出し長さも、パラペットの立ち上がり高さも、
主架構のどこにも書かれていない。

版の仕様・二次部材・所属・編集コマンド・UI は 2 種別で共有する。違うのは境界の決まり方と荷重の出口だけである。

### D14. 取付き先は「線 / 点 / 床領域」の 3 つを取る

取り付き領域の取付き先は種類つきの値とし、次の 3 つを取る。

| 取付き先 | 内容 | 該当する現行の表現 |
|---|---|---|
| 線 | 節点対 `[NodeId; 2]` ＋ 区間 `[t_i, t_j]`（D22） | 片持ちスラブ（辺 0）、梁に載るパラペット・腰壁 |
| 点 | 節点 1 つ（柱） | 出隅スラブ（`distribute_corner` が `boundary[0]` へ全荷重集中） |
| 床領域 | 床領域の ID | 自立壁（床の上に立つ間仕切り等） |

**節点参照にするのは、節点移動に追随し、大梁を分割しても取り付きが外れないためである。**
現行の片持ちスラブは節点対の完全一致で受け手の大梁を探すため（`auto_loads.rs` の `find_beam`）、
大梁が分割されると一致せず `Span` フォールバックへ落ちる。`MiscWall` は絶対座標だけを持ち、
部材を一切参照しないため、節点を動かしても追随しない。どちらも新しい設計へ持ち込まない。

荷重の受け手は準備計算で幾何的に解決する。`squid-n-load/src/secondary.rs` の
`beam_span_position` / `resolve_nodal_to_primary` が既に「節点共有なしで梁のスパン中間に載る荷重」を
中間集中荷重へ変換しており、同じ経路に載せられる。

### D15. 取り付き領域の輪郭は「取付き線 ＋ 両端の張り出し量」

輪郭は `[d_i, d_j]`（床は跳ね出し長さ、壁は立ち上がり高さ）で持ち、矩形も台形も表せる。
現行の `distribute_cantilever` は先端 2 節点の取付き線からの距離を**平均**して使っており（台形は潰れている）、
`[d_i, d_j]` はそれを上回る情報量である。

輪郭を節点で持たないのは、**要素が接続しない節点をモデルへ増やさない**ためである。
そうした節点は `DofMap::build` が解析自由度から外す一方、モデルの節点一覧には残り続け、
ビューアと節点編集に「触れない節点」として並ぶ。現行の片持ちスラブがその状態にある。

L 形バルコニーのような不整形は、取付き線ごとに領域を分けて表す（取り付き領域に数の制限はない）。

### D16. 伝達規則は取付き先の種類で決まる

| 取付き先 | 荷重の出口 |
|---|---|
| 線 | 「取付き線へ分布」または「取付き線の両端の柱へ集中」（利用者が選ぶ） |
| 点 | その節点（柱）へ集中（一択） |
| 床領域 | その床領域へ渡す（一択。D17） |

出隅スラブの「全荷重を柱へ集中」と、雑壁の柱伝達（`MiscWallTransfer::Column`）は、
規準上の根拠こそ違え荷重の出口としては同じ操作なので、ひとつの規則に統一する。
`MiscWallTransfer::Beam` は「取付き線へ分布」、`SelfStanding` は「床領域へ渡す」に対応する。

### D17. 床領域の上に立つ壁の荷重は等価な面荷重へならす

自立壁（間仕切り等）の総重量は、所属する床領域の面荷重へ等価換算して加え、床の分配にそのまま乗せる。
間仕切り壁の重量を床の固定荷重へ等価等分布として含めるのは実務の慣行であり、`docs/` に計算根拠として書ける。

位置に依存する厳密さが要る壁（パラペット・腰壁・垂れ壁）は D14 の「線」で大梁に取り付くため、
この経路に来るのはパネルの内側に立つ壁だけで、位置の影響は小さい。

**限界として、面荷重へならした時点で壁の位置情報は失われる。** 重い壁がパネル中央にある場合、
近い大梁は過小、遠い大梁は過大になる（総和は保たれる）。この既定は `docs/` の床荷重分配の節に明記し、
厳密に扱いたい場合は壁の直下に小梁を入れて主架構へ取り付ける運用とする。

### D18. `Slab.edge_supported` は廃止し、支持辺は幾何から導く

辺上に主架構の部材（大梁・片持ち梁）または領域が持つ二次部材（先端リブ小梁）が実在すれば支持辺とする。

この欄が担っていた 2 用途は、いずれも新しい設計では構造的に消える。
一般スラブの「開口際で支持されない辺」は D1 で消える（パネルの境界は定義上すべて大梁で、
吹抜けはパネルそのものが版なし領域になる）。片持ちの「片持ち梁・先端リブ小梁の支持辺追加」は
D6 で消える（片持ち梁は実部材、先端リブは領域が持つ二次部材で、実在を見れば決まる）。

なお **`edge_supported` には現状書き手が存在しない**。非テストの出現箇所はすべて `None` の初期化で、
UI・取り込み・編集コマンド・MCP のいずれも値を設定せず、利用者向け `docs/` にも記載がない。

`distribute_polygon_supported`（最近接支持辺の負担面積で分割）は捨てずに残す。
片持ち領域に片持ち梁・先端リブ小梁がある場合の分配経路として必要で、変わるのは支持辺の決め方だけである。

### D19. `SlabKind` は廃止する

`Interior` はパネル領域、`Cantilever` は取付き先が線の取り付き領域、`Corner` は取付き先が点の
取り付き領域に対応するため、種別を表す欄が二重になる。数量積算の「片持ち床」分類
（`quantity/mod.rs:1142`）も「取り付き領域である」ことから導く。

種別を残すと「出隅なのに線へ分布」のような無意味な組み合わせを表現できてしまう点も避けられる。

### D20. 取り込みでパネルに収まらない版は片持ちと自動判定する

ST-Bridge 取り込みは現状 `kind` を常に既定（`Interior`）で入れるため、バルコニーも一般スラブとして
取り込まれ、大梁のない辺へ配られた荷重は `Span` フォールバックで両端節点へ落ちている。

D8 でパネルを検出したうえで、**どのパネルにも収まらず、1 辺が大梁と重なる版は片持ち**として
取り付き領域へ変換する（`[d_i, d_j]` は取付き線からの距離）。判定できなかった版
（どの大梁とも辺を共有しない宙に浮いた版）は診断に出し、黙って落とさない。

落とす・対象外にする案は採らない。**バルコニーの荷重がモデルから消え**、長期荷重にも
地震用重量にも入らなくなるためである。

### D21. 畳んだ結果、参照が 0 になった節点は削除する

D15 で輪郭を `[d_i, d_j]` に畳むと、版の先端節点は誰からも参照されなくなる。
取り込み時にこれを削除する。ただし他の要素・二次部材・支点・領域が参照している節点は残すため、
削除は**参照が 0 になった節点のみ**に限る。

### D22. 部分的な取り付きは区間で表す

取付き線は節点対に加えて区間 `[t_i, t_j]`（取付き線上の無次元位置 0.0〜1.0、既定は全長 `[0.0, 1.0]`）を持つ。
腰壁が開口部で切れる、パラペットが階段室の手前で終わる、バルコニーがスパンの途中までしか出ていない、
といった形は実務で普通に現れる。

無次元にするのは、節点が動いて取付き線が伸縮しても割り付けが相対位置として保たれるためである。
区間の両端が梁のスパン中間に来ても、D14 の幾何解決で中間集中荷重・部分分布荷重として渡せる。

大梁上に節点を追加して表す案は、D15 と同じ理由（解析に不要な節点を増やす）で採らない。

### D23. 地面に直接立つ塀は対象外とする

床領域の上にない自立壁は、建物の架構へ荷重を渡さないため対象外とし、取り込み時に警告して落とす。

## 3.1 Step 4 着手時の設計修正（2026-08-24）

Step 4（D9: 領域内の分配を小梁で再分割）を実装する段階で、D3（領域が版の仕様を直接持つ）が
再び「床版は 1 領域につき 1 枚」という誤った前提に戻っていたことが判明した。

### 何が誤っていたか

D3 は「床領域＝大梁が囲む 1 区画」と「版（面荷重・厚さ・室用途を持つ実体）」を同一の型に
畳んだ。これは Step 2a〜3 の実装（`FloorRegion::plate: Option<SlabPlate>`）ではおおむね
成立していたが、**D9 で「小梁で再分割して既存の三角形・台形分配」を実装しようとすると
破綻する**。区画内が小梁でさらに細かい打設単位（厚さ・室用途が違う版）に分かれている場合、
「区画＝版」では 1 つの `FloorRegion` に複数の版仕様を持たせる場所がない。

加えて、床領域＝区画という決定は、大梁の 1 スパン区画と、その中の小梁・版という
利用者の実際のメンタルモデル（「床領域は大梁の1スパン区画。この中に小梁やスラブがある。
スラブは大梁または小梁で囲まれた領域に定義される」）とも一致しない。

### 修正内容

**`FloorRegion`（床領域）と `Slab`（床板）を再び別の型に分離する。** ただし D3 が退けた
「ID 参照にすると `Option` 戻し・ID 繰り上げの保守が発生する」という懸念は、
`FloorRegion` 側が `Vec<SlabId>` で複数の床板を保持する設計（一方向の参照、`Option` を使わない）
にすることで避ける。

| 型 | 持つもの | 対応する現行実装 |
|---|---|---|
| `FloorRegion` | 名前（D11）・境界（大梁の閉路。D1・D8）・所属する小梁 ID 一覧・所属する `Slab` ID 一覧（`slab_ids: Vec<SlabId>`）・手入力小梁ライン（`joists: Vec<JoistLine>`。交差小梁の格子解析専用） | `crates/squid-n-core/src/model/region.rs` |
| `Slab` | 形（`SlabShape::Enclosed { boundary }` = 大梁または小梁で囲まれた版 / `SlabShape::Attached { anchor, extent }` = 取り付く版）＋ 版の仕様（`SlabPlate`: 断面・仕上荷重・室用途・分配方法・一方向） | `crates/squid-n-core/src/model/slab.rs` |

**1 つの `FloorRegion` は複数の `Slab` を持ちうる**（区画内が小梁でさらに細かい打設単位に
分かれている場合）。取り付く `Slab`（片持ち・バルコニー・出隅）はどの `FloorRegion` からも
参照されない独立した床板として存在する（D13 のとおり）。

`JoistLine`（D9 の「帰結」で廃止予定としていたもの）は **廃止しない**。手入力の交差小梁
格子解析・矩形床板の二段階伝達は `FloorRegion.joists` として存続する。二次部材の実体
（D6）は依然 `Model.secondary_members` の横断リストのままで、D6 は引き続き保留である
（§8.4 に統合。理由は変わらず、`FloorRegion` が複数の `Slab` を持ちうる現状では
「中点の厳密内包」が `Slab` 単位でしか一意にならないため）。

### 荷重分配（D9）の実装

`squid-n-load::floor::distribute_region(model, region, w_of)` を分配の入口とする。

- `region.joist_lines()` が空でなく、代表床板（`region.slab_ids` の先頭）が矩形かつ
  分配法が三角形・台形または一方向なら、既存の `distribute_rect_with_joists`（手入力小梁の
  二段階伝達）を使う
- それ以外は `region.slab_ids` の各 `Slab` を独立に `distribute_slab_w` で分配する
  （`Slab` は大梁または小梁で囲まれた版であり、その境界辺がそのまま分配先になる）
- どの `FloorRegion` からも参照されない `Slab`（取り付く版・浮き床板）は
  `distribute_slab_resolved` で個別に分配する（`squid-n-job::auto_loads::slab_beam_loads_with`
  が `FloorRegion` 経由と `Slab` 直接の 2 経路を統合する）

`LoadTarget::Edge(k)` は `Slab` の文脈で解決する（`resolve_edges_to_span`）。1 つの
`FloorRegion` が複数の `Slab` を束ねるため、辺インデックス `k` は「どの `Slab` の境界か」に
よって別の実節点対を指すことに注意。

### 影響を受けた決定・廃止予定の取り消し

- **D3 は上記のとおり修正。** 「版を ID 参照にする案は退けた」の判断を覆す
  （区画が複数の版を持ちうるため、1 対 1 の畳み込みでは表現できない）
- **D9 の「帰結」（`JoistLine` 廃止）を取り消す。** `FloorRegion.joists` として存続する
- **§6「廃止・削除の対象」の `Model.slabs` / `Slab` 行を取り消す。** `Slab` は名前を変えて
  存続する（区画そのものではなく、区画内の版という意味に変わった）
- D19（`SlabKind` 廃止）・D13〜D18・D20〜D22 は影響を受けない（`Slab` の形・取付き先・
  分配方法として引き続き成立する）

### 用語: 「パネル」の使用禁止

建築構造で「パネル」は柱梁接合部（仕口パネル、`crates/squid-n-element` の `PanelZone` 等）を

## 3.2 壁領域（Step 7 着手前）の設計決定（2026-08-25、dig による合意）

§8.2 の未決事項（斜め構面の検出条件、柱梁に囲まれない雑壁の受け皿、開口モードとの関係）と、
Step 7/8 の段取りについて、利用者との対話（dig スキル）で合意した内容を記録する。
実装はこれから行う（本節は着手前の設計記録）。

### E1. 鉛直面のグルーピングは通り芯（AxisGroup）に依存しない新規の幾何判定とする

床の面走査は「同じレベル Z にある水平大梁だけ」を先に絞り込んでから面走査をかけている
（D8・`region_gen.rs`）。壁でこれに相当する絞り込み（「同一鉛直面に乗る柱・梁だけを集める」）は、
床の「Z が一致するか」ほど自明ではない。面走査アルゴリズム自体が「対象の辺をすべて 1 つの
2D 平面へ投影して角度順にソートする」処理を前提にするため、面を先に固定するステップは省略できない
（1 本の柱には通常 4 方向の梁が取り付き、それぞれ異なる鉛直面に属する。面を固定せずに
「柱・梁が閉じたループになっていれば十分」とすると、同一平面上にない部材どうしでも
グラフ上の閉路として拾ってしまう）。

**グルーピング規則**: 全柱の上下節点ペアから鉛直な芯線候補（XY 平面上の直線）を列挙し、
各芯線上にある柱・梁を [`crate::geom::MEMBER_AXIS_TOL_MM`]（10mm）の許容差で拾う。
直交グリッドか斜めかを問わず同じロジックで扱う。通り芯（`AxisGroup`）とは独立の判定とする
（`AxisGroup` は「構造計算には一切用いない」表示専用のデータであり、利用者が通り芯を
手動編集・削除しても壁領域の検出結果が連動して変わってはならないため）。

**新規実装が必要。** `region_gen.rs` は床（水平面）のみ実装済みで、壁（鉛直面）のグルーピングは
本節が最初の設計決定である。

### E2. 壁領域は「1 閉路＝1 平面」が前提。非平面な壁面は自然に複数領域へ分解される

E1 の帰結として、**壁領域の境界検出は常に厳密な平面（1 つの法線で表せる面）を対象とする**。
これは面走査アルゴリズムの数学的な前提であり、変更できない（床の「対象は水平な大梁のみ」と
同じ制約）。

現実の壁面が鉛直方向に完全な平面でない場合（芯ずれ、途中で折れ曲がる壁列、傾いた壁面など）は、
1 つの `WallRegion` にはならず、**平面ごとに複数の `WallRegion` へ自然に分解される**。
これは床の段差床が「同じ階でも別の平面グラフになる」のと同じ扱いであり、L 形バルコニーが
取付き線ごとに複数の取り付き領域に分かれる D15 の考え方とも一貫する。特別扱いや例外処理を
新設するのではなく、E1 のグルーピング規則がそのまま複数の面走査対象を作ることで実現する。

**この制約を実装時に見失わないこと**（利用者からの明示的な申し送り）。壁領域の設計・実装の
どこかで「1 領域は必ず 1 つの平面上にある」という前提を緩めるような近道（例: 複数面の節点を
まとめて 1 つの `WallRegion` にする）を取らないこと。

### E3. 壁領域の面積・荷重計算は、理想平面への投影を経由せず 3 次元座標から直接求める

E2 のグルーピング許容差（`MEMBER_AXIS_TOL_MM` = 10mm）は、床の `LEVEL_TOL_MM`（1mm）より
1 桁緩い。床は許容差が小さいため「理想平面へ投影した 2D 座標から面積を出す」現行実装
（`RegionBoundary::polygon`／`area`。Z を捨てて XY のシューレース公式）でも実務上誤差は
無視できるが、壁で同じ手法を使うと、芯ずれ・非平面性による誤差（壁スパンによっては
無視できない大きさ）が自重・仕上げ荷重（面積 × w）に混入する。

**壁側の面積・荷重計算は、理想平面へ投影せず、実際の 3 次元節点座標からニューエルの公式
（3D 多角形面積）で直接求める。** 面走査（閉路検出のための角度ソート）は引き続き E1 の近似法線を
使ってよい（トポロジーの決定にのみ用いるため）。用途によって「近似平面でよい処理」と
「実座標が必要な処理」を分けること。

### E4. `MiscWall`（自由座標の雑壁）は節点参照へ完全移行し、自由座標入力は廃止する

現行の `MiscWall` は `start`/`end` の絶対座標のみを持ち、節点・部材への参照が一切ない
（ST-Bridge 取り込み経路には `MiscWall` を生成するコードが存在せず、実フィクスチャにも
`MiscWall` は 0 件。単体テストの合成データのみ）。D14（取付き先は 線／点／床領域 の 3 つで、
節点参照にする）と現行の自由座標入力は直接矛盾する。

AGENTS.md が「後方互換性は維持しない」と明記しており、実データが存在しないため移行ロジック
（既存の自由座標を最近傍アンカーへスナップする処理）は不要と判断し、**新規の壁領域入力
（Step 9 UI・MCP・ST-Bridge 取り込み）は D14 の 3 アンカー（線／点／床領域）を必須とし、
アンカーを持たない自由座標の壁は作れない仕様にする。**

**帰結**: §8.2 の「柱梁に囲まれない雑壁の受け皿」は本決定で自動的に解消する。取付き先が
必ず存在するため、「囲まれない」かつ「取り付き先もない」状態自体が作れなくなる
（地面に直接立つ塀は D23 で対象外と既に決まっている）。

**実装範囲への影響**: `MiscWall`（`start`/`end` の自由座標）を直接構築している非フィクスチャの
単体テストが 3 ファイルにある。E4 着手時はこれらもアンカー付きの新表現へ書き換える対象に含めること。

- `crates/squid-n-load/src/story_gen/tests.rs:1446,1531`
  （`test_misc_wall_beam_transfer_conserves_total_weight`／`test_misc_wall_column_transfer_splits_to_column_ends`。
  `MiscWallTransfer::Beam`／`Column` の 0.5m 分割集計を数値で検証している。D16 のアンカー種別への
  写像後も同じ検証数値が再現できるかを併せて確認すること）
- `crates/squid-n-design-jp/src/secondary/eccentricity/tests.rs:241,250,259`
  （偏心率算定における雑壁剛性寄与のテスト）

### E5. `WallRegion` は複数の `WallPlate` を持ちうる設計とする（D3 の教訓を先取りする）

§3.1 は、床領域を最初「1 区画＝1 版」（D3）と決めたのちに「1 区画は複数の版を持ちうる」
（`Vec<SlabId>`）へ手戻りした経緯を記録している。壁でも同じ状況が起こりうる
（1 つの柱・梁パネル内に、間柱で実際には分割された壁、異なる厚さ・仕様の雑壁が隣接する等）。
ST-Bridge の `StbWall` は親子関係を表すタグを持たず、床のスラブ片と同様に、1 つの
柱・梁パネル内に複数の壁要素が幾何的に収まる入力が普通にありうる。

**同じ手戻りを避けるため、`WallRegion` は最初から `Vec<WallPlateId>`（複数の壁版）を
持てる設計とする。**

### E6. 開口モード（`MultiOpeningMode`）は引き続き `Model` 全体で 1 つのグローバル設定のまま

開口データ（`WallOpening`）の持ち主が `WallAttr` から `WallPlate`（`WallRegion` の一部）へ
移っても、複数開口の取り扱い（`Model.multi_opening_mode`）は建物全体で一律のままでよいと判断した。
壁ごとに評価方式を変えたいという利用者ニーズは想定していない。**帰結**: §8.2 の
「開口モードとの関係」は影響なしと確認でき、`WallPlate` に `MultiOpeningMode` フィールドは追加しない。

### E7. Step 7 と Step 8（D4）は分離せず一括で実施する

当初の Step 表は Step 7（型の作り直し・`MiscWall`/`WallAttr` 吸収。壁要素は
引き続き `Model.elements` に直接入力されたまま）と Step 8（D4: 解析要素を準備計算からの
生成物にする）を分けていた。しかし Step 7 だけで区切ると、`WallPlate` が
「引き続き手入力される `Element::Wall` への一時的なつなぎ（`elem: Option<ElemId>`）」を
一時的に持つことになり、Step 8 でこのつなぎを剥がして生成方式へ切り替える二度手間が生じる。

**利用者の判断により、Step 7・8 は分離せず一括で実装する。** `WallRegion`/`WallPlate` を
入力の正とし、剛性に算入する壁の解析要素は準備計算（D5・`App::ensure_preparation`）で
生成する形を最初から実装する。断面力表示・保有水平耐力の対象指定・ST-Bridge 出力の
参照先の張り替え（§8.4）も同じ波に含む。

### E8. 実装着手前に、壁を含む実フィクスチャを新設し、現行動作の代表スカラをピン止めする

床側 Step 4 は実フィクスチャ（`crates/squid-n-app/tests/fixtures/model.stb`、82 枚のスラブ）の
`snapshot_key_scalars` を安全網として、型再分離が生んだ回帰を含む既存バグ 6 件を検知できた
（§5.4）。**壁側は実フィクスチャに `Element::Wall` が 0 件で、`full_model.rs` に壁の
スナップショットが 1 つもない**（`WallAttr`・`wall_nonlinear`・`joint_wiring` 等の壁関連機能は
すべて単体テストのみで検証されている）。

E7 のとおり Step 7・8 を一括で行うと、断面力表示・保有水平耐力・ST-Bridge 出力の参照先切り替えを
回帰検知網なしで行うことになる。これは `dev_docs/handoff/README.md` が記録する P7・P8 の
「非デフォルト機能が実装済みと申告されながら実際には壊れていた」再発パターンと同じ危険を持つ。

**着手前に、壁を含む最小実フィクスチャを新設し、型変更前の現行動作をピン止めするテストを
追加する。** これを Step 7・8 の Step 0 相当（床の §5 Step 0 に対応）として最初に行う。

**2026-08-25、実施済み。** `crates/squid-n-app/tests/wall_model.rs` を新設した。
`Model.floor_regions`（26 件、`full_model.rs` の既存フィクスチャ）を巻き込まない独立の
最小モデル（柱 4 本・梁 4 本・耐震壁 1 枚〔開口あり〕・フレーム外雑壁 1 本、1 スパン 1 層）を
`App` の全解析入口（`run_preparation`／`run_static_all`／`run_eigen`）に通し、
`insta`（`full_model.rs::snapshot_key_scalars` と同じ仕組み）で代表スカラをスナップショットした
（`snapshot_wall_bay_scalars`。地震用重量・固有周期・耐震壁要素の材端力〔DL・EX 両方〕・
EX 荷重時の柱頭水平変位）。`cargo clippy -p squid-n-app --all-targets --locked -- -D warnings`
を通過済み。

**確認した注意点**: 耐震壁要素の材端力（面内せん断剛性・開口低減の回帰検知に使う想定だった値）は、
DL（対称な架構への鉛直荷重）単体ではほぼゼロになる（この対称形状では壁柱換算の軸力・曲げが
小さいため。固有周期が壁の有無で 0.0797s→0.0522s と動くことから、壁は剛性には確実に効いている。
`test_wall_element_changes_eigen_period` で固定）。壁の面内せん断・開口低減を実際に動かすのは
地震荷重（EX）であり、スナップショットは EX 側の材端力・柱頭水平変位も記録する。
**次にこのフィクスチャへ手を入れる際、「動かない代表値」を回帰検知の根拠に使わないこと**
（値が動かない列は型変更の影響を検知できず、検知網があるという誤った安心感だけを生む）。

**このフィクスチャに含まれないもの（未着手）**: D13〜D16 の取り付き領域（パラペット・腰壁等の
アンカー付き壁）は、現行コードにその型がまだ存在しないため含められない（ベースラインを
ピン止めする対象がまだない）。E1〜E7 の型実装後、取り付き領域を含む代表値を別途追加すること。
また `保有水平耐力`（Qu・τu・Ds 群判定）は現状すべて単体テストのみで検証されており、
このフィクスチャでは通していない（プッシュオーバー・Ds 群判定を最小構成で通す準備には
別途作業が要るため、E8 のスコープからは意図的に外した。Step 8 の参照張り替えで
保有水平耐力の対象指定を壁領域 ID 起点へ切り替える際は、通す作業を先に行うこと）。

## 3.3 用語の改名（2026-08-26）

`dev_docs/specs/用語集.md` の該当項目・関連する他の申し送り（`剛域長の算定を技術基準へ揃える_申し送り.md`

 ├ name:     String

 └ posts:    Vec<SecondaryMember>
```

```
FloorRegion / WallRegion の幾何（D13〜D16・D22）
 └ shape:
     ├ Enclosed { boundary: Vec<NodeId> }              // 閉路から自動生成
     └ Attached {
           anchor: Line { nodes: [NodeId; 2], span: [f64; 2] }  // 区間は無次元 0..1
                 | Point(NodeId)
                 | Floor(FloorRegionId),
           extent: [f64; 2],                            // 両端の張り出し量 d_i, d_j
           transfer: …,                                 // 線のときのみ選択肢を持つ
       }

`SlabPlate` は現行 `Slab` から幾何と所属を除いた残り（断面・仕上荷重・室用途・分配方法）。

### 5.2 Step 2b でやったこと・D6 を Step 3 の後へ回した理由（2026-08-23）

**D6（二次部材の実体を領域が持つ）は、Step 3 のパネル統合より後でなければ成立しない。**
D7 の所属規則は「中点がその領域に厳密内包される」だが、現在の小片スラブ領域では
小梁は必ず辺の上に載るため、内包されるものが 1 本もない。実測は次のとおり。

| 判定対象 | 小梁 56 本の該当数の分布 |
|---|---|
| 現在の小片スラブ領域（辺上を含む） | 2 枚: 46 本、3 枚: 10 本（一意にならない） |
| `region_gen` のパネル（厳密内包） | **1 つ: 56 本（すべて一意）** |

横断リストを先に廃止すると、取り込んだ小梁 56 本の置き場所がなくなる。
そのため Step 2b では D6 を扱わず、D11（領域名）と取り付き領域の入力経路を入れた。

- `SetFloorRegionName` / `AddAttachedFloorRegion` を `squid-n-edit` に追加
  （取付き先が実在しない節点・部分区間は Noop）
- 床タブに「名前」列と「取り付き領域を追加」フォームを追加（取付き先＝大梁の 2 節点
  または柱の 1 節点、張り出し量、荷重の出口）
- 階複製が**領域名を引き継ぐ**ようにした
- `LoadTransfer` を `RegionAnchor::Line` の中へ移した（B1）。点に取り付く領域は
  その節点への集中しかありえないため、値を持たせると無意味な組み合わせを表現できてしまう
- 階複製の `slab_story` が取り付き領域で `None` を返し、**複製の対象からも見送り件数からも
  外れていた**のを修正した（取付き先の節点で階を判定する）。取り付き領域を複製しないこと自体は
  変えていないが、見送った件数として利用者に見えるようになった

Step 0 を分ける理由は三つある。移行は長期になる見込みで、その間ずっと誤った小梁設計が出続けること。
修正は判定条件の差し替えだけで小さく、単独で検証できること。
そして移行の PR で一緒に直すと、分配の作り替えによる結果変化と不具合修正による結果変化が同じ差分に混ざり、
V&V でどちらの影響か切り分けられなくなることである。

**Step 0 自体が 49 本の小梁を別のスラブへ移すため、小梁の検定比と `snapshot_key_scalars` が変わった。**
実測は `design.joist_checks` 28 → 56 件、小梁の最大検定比 0.2049 → 0.3006。
他のスナップショット値（応力・変位・固有周期・保有水平耐力・時刻歴・部材検定比）は不変である。
記録は [`v_and_v/小梁設計のスラブ帰属_レベル一致_2026-08.md`](../v_and_v/小梁設計のスラブ帰属_レベル一致_2026-08.md)。

### 5.5 Step 5 でやったこと・一部にとどめた理由（2026-08-25）

Step 表の「`distribute_region` の出力から導く」を文字どおり実行しようとしたところ、
`distribute_region` の出力（`LoadShape`＋CMQ）は固定端梁前提であり、小梁検定
（`design_joist_simple`/`design_joist_from_forces`）が前提とする単純梁の負担幅モデル
（`w × spacing`）とは基準が異なることが分かった（レビュー指摘）。乗り換えると
`docs/calc_basis/01_荷重/03_床荷重の分配.md` §1.4.2 の計算根拠（負担幅 spacing による
等分布荷重）を書き換えることになり、`FloorRegion.joists` 経路（グリレージ・単純小梁とも
`w × spacing` のまま）とも基準が食い違う。

そのため、**荷重の基準は変えず、`spacing` の求め方だけを直した**。
`squid_n_load::secondary::joist_edge_tributary_width` を新設し、小梁の辺に沿う境界辺を
持つ床板（同じレベルに限る）の幅の合計を半分にして負担幅とするようにした。これにより、
複数の床板の辺に載る小梁の負担幅を「載っている床板の幅の単純平均」としていた既存実装
（T 字取り付き等、3 枚以上に載る場合は近似だった）が、片側が複数枚に割れているときも
正しく扱えるようになった。床板の境界に載らない小梁（内部を通る等）は既存の平行小梁
グループ化へフォールバックする。

**実装中に危険側の不具合を 3 件見つけて直した**（詳細は V&Vレポート）。1 件目は、隣の
床板が T 字取り付きの途中の節点で境界を分割されている場合、節点対の完全一致では反対側を
取りこぼし負担幅が半分程度になる欠陥（コミット前レビューで発見）。2 件目は、幾何判定へ
直した直後に見つかった、レベル一致の絞り込み漏れ（上下階で平面が繰り返される建物では
別階の床板を拾ってしまう。コミット前レビューで発見）。3 件目は、PR 提出後の実装への

### 5.6 取付き線の部分区間対応でやったこと（2026-08-25）

§9 残課題「Step 4 で取付き線の部分区間（`span != [0, 1]`）に対応する」に対応した。
D22 が決めていた「区間の両端が梁のスパン中間に来ても、幾何解決で中間集中荷重・
部分分布荷重として渡せる」を、§8.3 で片持ちスラブの辺荷重向けに実装済みだった
座標ベースの幾何割付（`beam_span_position`／`emit_along_segment`）へそのまま乗せる形で実装した。

- `squid_n_load::floor::LoadTarget::Span([NodeId; 2])` を
  `Span { nodes: [NodeId; 2], t: [f64; 2] }`（既定 `[0.0, 1.0]`）へ拡張した。既存の呼び出し箇所
  （小梁反力・矩形床境界の残り分など）はすべて `t = [0.0, 1.0]` を渡すだけで動作は変わらない
- `resolve_edges_to_span`（`squid-n-load`）が、取り付く床板（`SlabShape::Attached`）の辺 0
  （取付き線）を `Span` へ解決する際、取付き先の `span`（`RegionAnchor::Line::span`）を
  そのまま `t` へ引き継ぐ。囲まれた床板の境界辺は常に `t = [0.0, 1.0]`
- `squid-n-job::auto_loads::slab_load_case_content` の `Span` 解決を、`t == [0.0, 1.0]`
  のときだけ従来の高速経路（`bl.elem` 直接ヒット、`a0 = 0`・`len = 全長`）を使い、
  `t != [0.0, 1.0]`（部分区間）は `nodes` の座標を `t` で線形補間した区間端点
  （実節点ではない）を使って幾何解決へ回す形に分けた。高速経路は要素の局所 x 軸の
  向きを検証せずに使っており（対称形状の `Uniform` は影響しないが一般には潜在リスク）、
  部分区間をそのまま高速経路へ乗せず、既に向きに依らず解決できる幾何経路へ回すことで
  この潜在リスクに触れずに済ませた。件数が少ない（部分区間を使うのは取り付き領域のみ）ため、
  既存の大多数（小梁反力等）が使う高速経路の性能には影響しない
- `Model::validate`（`squid-n-core`）と `squid-n-edit` の `AddAttachedSlab`／`SetAttachedAnchor`
  の「`span != [0, 1]` は弾く」制限を、「`span` が有限かつ `0.0 <= t_i < t_j <= 1.0`」という
  妥当性チェックへ置き換えた
- 床タブの取り付く床板フォーム・一覧表（`squid-n-app::tables::slabs`）に区間 `[t_i, t_j]`
  の入力を追加した。これを追加しない限り、GUI からは `span != [0, 1]` を作る手段がなく
  （ST-Bridge 取り込みも `span = [0, 1]` 固定、MCP にも専用ツールが未整備）、
  データモデルとしては通っても実際には作れない機能になってしまうため

**実装中に見つけて直した既存の潜在的な誤りが 1 件ある**（コミット前レビューで発見）。
`LoadTransfer::Columns`（両端の柱へ集中）は `distribute_attached` が `span` を無視して
常に半分ずつ（0.5 / 0.5）を両端の柱へ振っていた。`span = [0, 1]` の間は区間の中点が
ちょうど中央（`t_mid = 0.5`）に一致するため誤りが表面化しなかったが、部分区間を
弾く制限を外すとこの組み合わせが到達可能になり、位置がずれたまま黙って通ってしまう
状態だった。単純梁の集中荷重反力公式（\\( R_i = W(1-t_{\text{mid}}) \\)、
\\( R_j = W \cdot t_{\text{mid}} \\)、\\( t_{\text{mid}} = (t_i+t_j)/2 \\)）で按分するよう直した
（`squid_n_load::floor::distribute_attached`）。`docs/calc_basis/01_荷重/03_床荷重の分配.md`
に「両端の柱へ集中」の按分規則を追記した。

再発防止・回帰テストを追加した（`crates/squid-n-job/src/auto_loads.rs`）。取付き線の下の
大梁が中間節点で分割されている場合に部分区間が分割点をまたいでも両方の梁へ正しく分割して
載ること（`test_attached_anchor_partial_span_crosses_beam_split`）、区間の始端・終端が
取付き線の実節点にちょうど一致し `beam_span_position` の節点近傍除外を通って幾何割付側へ
落ちても正しく載ること（`test_attached_anchor_partial_span_touches_start_node`／
`test_attached_anchor_partial_span_touches_end_node`）、`LoadTransfer::Columns` が区間の
中点で按分すること（`test_attached_anchor_columns_transfer_partial_span_splits_by_lever_arm`）
を含む。既存フィクスチャは `span != [0, 1]` を使っていないため、代表スカラの変化はない。

**敵対的レビューで見つけて直した点**（コミット後、コードレビュースキルを使わない手動レビュー）:

1. `distribute_to_node`（`cantilever.rs`）・`distribute_slab`／`distribute_attached`
   （`floor/mod.rs`）の rustdoc が、`LoadTransfer::Columns` の按分を「常に半分ずつ」と
   古い記述のまま残っていた。実装（`t_mid` による按分）は直したが、それを説明する
   doc コメントを直し忘れていた。区間中点で按分する旨へ更新した
2. `LoadTransfer::Columns` の `t_mid` 按分は、張り出し量が区間の両端で等しい
   （`extent[0] == extent[1]`）ときに限り厳密である。張り出しが異なる台形の
   footprint（D15）では真の面積重心が区間中点からずれるが、その差は見ていない。
   これは今回の変更が持ち込んだものではなく、`span=[0,1]` 固定だった旧実装の
   半分ずつ按分も同じ近似を持っていた。`distribute_attached` の doc コメントに明記した
3. GUI（`squid-n-app::tables::slabs`）の区間入力の妥当性チェックが、有限性と
   始端 < 終端しか見ておらず、`Model::validate` と同じ範囲（`0.0 <= t_i, t_j <= 1.0`）を
   確認していなかった。`egui::DragValue::range(0.0..=1.0)` の入力側クランプに実質的に
   依存していたため、クランプが効かない経路があると「追加」ボタンが有効に見えたまま
   クリックしても `Noop` で何も起きない、という利用者に見えない失敗になりうる状態
   だった。GUI 側にも同じ範囲チェックを足した
4. 区間の始端が実節点に一致するケース（`t = [0.0, 0.5]`）はテストしていたが、対称の
   終端一致ケース（`t = [0.5, 1.0]`）は未検証だった。テストを追加した
   （`test_attached_anchor_partial_span_touches_end_node`）

### 5.7 壁側 `region_gen`（構面のグルーピングと面走査）の実装（2026-08-26、未結線）

Step 7+8 の最初の一手として、E1〜E3（構面のグルーピング・面走査・面積算定）を
`squid-n-core` に実装した。**`WallRegion`/`WallPlate` 型の作り替え・要素生成（D4）・
モデルとの結線（診断接続を含む）はまだ行っていない。** 本節の実装は、既存モデル・
既存の解析結果を一切変えない（`crates/squid-n-app/tests/wall_model.rs::snapshot_wall_bay_scalars`・
`crates/squid-n-app/tests/full_model.rs::snapshot_key_scalars` とも無変化）。

**モジュール構成**: `crates/squid-n-core/src/region_gen.rs`（1 ファイル）を
`region_gen/{mod,floor,wall}.rs` へ分割した。半辺（有向辺）をたどる面走査エンジン
（`scan_faces`）と、座標系に依存しない 2D 幾何ヘルパー（`signed_area`・
`point_segment_dist`・`polygon_contains_strict`）を `mod.rs` に共有として切り出し、
既存の床専用ロジック（`horizontal_beams_by_level`・`crossing_pairs`・`RegionBoundary` 等）を
`floor.rs` へそのまま移した。外部から見える公開 API（`region_gen::{generate_region_boundaries,
scan_region_boundaries, RegionBoundary, RegionBoundaryScan, crossing_beams,
polygon_contains_strict, BOUNDARY_TOL_MM}`）は変えていない。**回帰の安全網は「分割前の
`region_gen.rs` の全テストが、分割後も変更なしに通ること」とした**（実際に無変更で通過）。

**壁側 `region_gen::wall` の実装内容**（E1〜E3）:

- **構面の検出（E1）**: 全柱（`ElementKind::Beam` のうち `is_vertical_pair` を満たすもの）の
  柱脚位置（XY）を `MEMBER_AXIS_TOL_MM`（10mm）以内で重複排除し、全ペアから直線候補を作る。
  既知の直線と「同一の構面」とみなす判定は、**角度の許容差ではなく、柱位置から直線までの
  実距離 [mm] で行う**（角度の許容差は直線が長いほど遠方でのずれが拡大するため使わない。
  梁の交差診断を同じ理由で `MEMBER_AXIS_TOL_MM` へ統一した経緯（§8.3）と同じ判断）。
  直線の方向は見出し角 `[0, π)` に正規化する（`atan2` の mod 演算による 0°/180° 境界の
  不連続を避けるため、ベクトルの符号反転で正規化する）。
- **面走査（E1・E2）**: 構面ごとに、両端の XY 射影が `MEMBER_AXIS_TOL_MM` 以内にある
  `ElementKind::Beam`（柱・梁の区別、鉛直・水平・斜めの区別は問わない）を辺として集め、
  局所座標 `(s, z)`（s=構面方向の位置、z=グローバル Z）へ射影して床と共通の面走査
  エンジンへ渡す。1 本の構面は建物の全高さを 1 つの平面グラフとして扱うため、
  複数階にまたがる壁面は階ごとの内部面として現れる。外周面の判別（符号付き面積が
  正か負か）は床（グローバル XY・+Z 上が固定の基準）と同じ規則をそのまま使えるかが
  設計時点で未確定だったため、直交（見出し角 0°・90°）と斜め（30°）の 3 通りで
  面数・面積を検証するテストを追加し、いずれも正しく検出できることを確認した。
- **面積算定（E3）**: `WallRegionBoundary::area` はニューエルの公式による 3 次元面積で、
  理想平面への投影を経由しない。トポロジー（面走査）は直線への射影という近似で
  行ってよいが、面積・荷重は実座標から直接求める、という使い分けを型で強制する
  （投影面積を返す公開メソッドは用意していない）。境界節点が理想平面から数 mm
  ずれていても面走査の結果（面の数・境界）は変わらないが、ニューエル面積は
  投影面積から測定可能な差として動くことをテストで確認した。

**計算量について（実測値。当初の見積もりは誤りだった）**: 柱脚位置の全ペアから
直線候補を作るため候補数は柱の本数 N に対し O(N²) だが、**候補ペアごとに「既知の
全直線と実距離で比較する」素朴な実装は O(N²) ではなく O(N²·L)（L=見つかっている
直線の本数）である。** 格子状の柱配置では、軸方向の直線に加えて格子点を結ぶ斜め方向の
直線が候補として大量に残るため、L 自体が N の増加とともに増える。実測
（`crates/squid-n-core/tests/perf_probe.rs`、release ビルド）は次のとおりで、
柱 400 本（20×20 格子）で 840ms、柱 900 本（30×30 格子）で 19.4 秒に達した。
「実建物の柱本数（数百〜数千本程度）では実用上問題にならない」という当初の記述
（実測なしの見積もり）は誤りだった。

| 柱本数 | 素朴な実装 | グリッド索引後 |
|---|---|---|
| 100（10×10） | 8.0ms | 6.0ms |
| 225（15×15） | 101.4ms | 39.5ms |
| 400（20×20） | 840.9ms | 189.5ms |
| 900（30×30） | 19,361.6ms | 1,813.4ms |

対策として、候補直線の重複判定にグリッド索引（`LineIndex`）を導入した。キーは
「直線の見出し角を 2 倍した角度（`2θ`）の単位円上の位置」と「柱脚位置の重心からの
符号なし距離」を `MEMBER_AXIS_TOL_MM` 相当の刻みで量子化したものとし、近傍のバケットだけを
候補として拾ってから実距離で確認する（索引はあくまで性能上の絞り込みで、**同一直線の
最終判定は必ず実距離（`is_same_line`）で行う**ため、索引の取りこぼし・衝突は
正しさを損なわない）。`2θ` を使うのは、直線の向きが持つ ±180° の符号の曖昧さを
素朴な角度（mod π）でバケット化すると 0°/180° の境界で不連続になる
（179.99° と 0.01° はほぼ同じ直線だが、実数直線上のバケットでは両端に離れて割り当たる）
ためで、角度を 2 倍すると `cos 2(θ+π) = cos 2θ` によりこの不連続が生じない。

上の表のとおり、グリッド索引で 30×30 格子は 19.4 秒 → 1.8 秒まで縮んだが、**それでも
超線形の増加が残っている**（400→900 本の柱本数比 2.25 倍に対し、所要時間は約 9.6 倍）。
残りのボトルネックは、直線ごとに全要素を線形走査する `members_on_plane`（O(L·M)、
M=要素数）と見られるが、詳細な切り分けは未実施（残課題）。梁の交差診断
（`region_gen::floor::crossing_beams`）も当初は総当たりで実装し、実測して初めて
走査線法へ最適化した経緯があり（§8.3）、本モジュールも同じ方針
（先に正しさを固め、実測してから最適化する）を踏襲しているが、**今回は 1 段階の
最適化で止めている。実建物（数百〜数千本の柱）でどの程度の時間がかかるかは、
グリッド索引後の値でも未検証（数百本規模の実測データがない）。Step 7+8 の結線時に
`members_on_plane` のボトルネックを切り分け、必要なら追加の最適化を行うこと。**
性能の悪化と下記 4 の退化閉路は、根が同じである（他の部材と接続しない直線候補が
大量に生き残ること）。そのため `wall_planes` の段階で「乗る部材の射影後 `s` の値が
2 種類未満（＝閉じた面を作りえない）の直線候補を捨てる」事前フィルタを入れれば、
L を大きく減らしつつ退化した面をそもそも発生させない、より根本的な対策になる。
面走査の後で面積しきい値によって除外するより望ましい対策であり、
`members_on_plane` のボトルネック切り分けと合わせて検討すること。

**2026-08-26 追記（E4〜E7 着手前に修正済み）**: `WallRegion`/`WallPlate` の型実装

表面化した。柱 0・1（側柱）と大梁 4・8（壁の上下大梁）の材料を RC へ差し替えて是正した
（断面性能は鋼断面の計算値をそのまま流用し材料だけ差し替えている。現実的な RC 断面
形状で改めて算定すると鋼より大幅に剛性が高くなり、壁単体の剛性寄与を示す
`test_wall_element_changes_eigen_period` の判定が意味をなさなくなるほど埋もれたため）。
この材料差し替え（ヤング係数・密度の変化）と基礎大梁の自重により、
`snapshot_wall_bay_scalars` の代表スカラは実測して更新した（総重量・固有周期・
壁材端力・柱頭変位のいずれも変化。値の変化そのものが目的ではなく、型変更前の
現行動作を新たにピン止めし直したという位置づけ）。
`region_gen_finds_wall_bounded_regions` は、55 件・合計面積という単一の観測値の
ピン止めに留まらない。独立の不変条件として、次の 3 つも確認している。境界どうしが
節点集合として重複していないこと（構面の重複統合ミスの検出）、各境界の面積が必ず
正であること（外周面判別の破綻の検出）、そして本フィクスチャが直交グリッドの S 造
建物であるため正の面積を持つ境界の構面がすべて軸方向（X または Y）であること
（`wall_planes` が実際にはつながっていない柱の組を誤って直線候補として拾い、
構造的に無意味な面を検出していないことの確認）である。床側の Euler の公式検算
ほど厳密な独立検算ではないが、最低限の食い違い検出は持たせた。実測では 55 件
すべてが軸方向で、斜め構面に正の面積を持つ境界は 0 件だった。**この面積正値
チェックが、下記 4 の実バグを実際に検出した。**

**敵対的レビューで見つけて直した点、および未対応のまま申し送る点**（2026-08-26）:

1. **計算量の見積もり誤り**: 上記のグリッド索引導入と実測値の記録（既に本節に反映済み）。
2. `column_footprints` の重複排除（[`crate::region_gen::wall`] 内部）は `model.elements`
   の並び順に依存する（先勝ち）。生き残った代表点が候補直線の原点
   （`WallRegionBoundary::plane_origin`）になるため、構面自体・面走査の結果は
   変わらないが、原点の値は並び順の影響を受ける。D5 が「生成は決定的」と求める
   `Model.floor_regions`/将来の `WallRegion` の生成物とは異なり、`plane_origin` は
   `WallRegionBoundary` の内部表現にすぎず利用者に見えないため実害はないが、
   将来 `plane_origin` を何かの ID・キーに使う場合は要注意（コードコメントに記録済み）。
3. **未対応**: `MIN_PROJECTED_EDGE_LEN_MM`（構面上にはあるが射影後の長さがほぼ 0 の
   部材を除外するフィルタ）が実際に効く経路（既存の辺と近い方位角に紛れ込んで
   並べ替えを乱すケース）は、まだテストで再現できていない。角度の近接を意図的に
   作るテストは部材端点の座標を高精度で作り込む必要があり複雑になるため見送った
   （コードコメントに記録済み）。
4. **実データで見つけた実バグ（面積正値チェックで検出）**: `scan_wall_region_boundaries`
   の外周面判別が「射影後の符号付き面積 `> 0.0`」という厳密な不等式だったため、
   浮動小数点の丸め誤差を「正の面積」として誤って拾っていた。建物の柱は複数階に
   わたって節点が分割されるため、同一の柱に属する節点は XY が完全に一致する
   （Z のみ異なる）。この構面上で他のどの部材とも接続しない孤立した柱（行き止まり）
   を面走査がたどると、射影後の座標 `(s, z)` は全節点で `s` が完全に一致し、理論上の
   符号付き面積は厳密に 0 になるはずだが、シューレース公式の丸め誤差が
   `1e-8`〜`1e-7`mm² 程度残り、`> 0.0` の判定を通過して「正の面積を持つ境界」として
   検出されてしまっていた（実測: 実建物データで 12 件、境界数が 67→55 に減った）。
   `MIN_FACE_AREA_MM2`（`MEMBER_AXIS_TOL_MM²` = 100mm²。観測された丸め誤差より
   9 桁以上大きく、実在の壁面積より 4 桁以上小さい）をしきい値とすることで修正した。
   実建物データの座標（柱脚 (1000,1000) と孤立した柱 (13800,7400) の組。方向ベクトル
   `[0.8944271909999159, 0.4472135954999579]`）をそのまま再現した単体テスト
   `region_gen::wall::tests::test_isolated_dangling_column_does_not_create_spurious_boundary`
   を追加した（修正を戻すと実際に失敗することを確認済み。見出し角が軸方向〔0°・90°〕だと
   `s` の計算が単純な代入になり丸め誤差が出ずこのテストでは再現できないため、
   軸方向のテストケースは意図的に避けている）。
   **床側 `region_gen::floor` の外周面判別（`f.signed_area > 0.0`、変更していない）も
   同種の丸め誤差のリスクを理論上は抱えているが、床の実フィクスチャでは複数階の
   節点が同一 XY を持つことがなく現状は再現していない。** 床側でこの種の不具合が
   将来見つかった場合は、同じ `MIN_FACE_AREA_MM2` 相当のしきい値を導入すること。

### 5.8 `RegionAnchor` の床領域アンカー追加と `WallPlate` 型の実装（2026-08-26、未結線）

E4〜E7（`WallRegion`/`WallPlate` の型実装・要素生成・参照張り替え）着手にあたり、
dig で実装順序・PR の切り方（1 PR で一括、E7 の「一括実施」の精神をそのまま適用）・
保有水平耐力の前提作業（`wall_model.rs` へ Ds 群判定のスナップショットを追加してから
参照を張り替える）・`WallPlate` の型構造（`Slab` と同じ独立エンティティ）・
自重の算定方式（`Slab` と同じく必ず断面参照。`OutOfFrameMiscWall` の直接入力は廃止）を
確定した。本節はその最初の一手（型の骨格）を記録する。**`WallRegion` の作り替え・
要素生成・参照張り替えはまだ行っていない。**

**着手前に修正した前提**: `wall_model.rs`（E8 の壁入りフィクスチャ）は柱脚どうしの
梁を持たず `region_gen::wall` の境界検出を一切通らないことが分かっていたため
（§5.7）、柱脚間の梁 4 本を追加し 4 面すべてを閉じた矩形にした。副作用として
耐震壁の四周判定（`wall_is_framed`）が働くようになり、フィクスチャがもともと
抱えていた不正な混合構造（RC 耐震壁に S 造の側柱・大梁）が表面化したため是正した
（詳細・実測値の変化は §3.2 E8 の項を参照）。

**`RegionAnchor::FloorRegion` の追加**: D14 の「取付き先は線／点／床領域の 3 つ」の
うち床領域アンカーが未実装だった。自立壁（床の上に立つ間仕切り等）が使う。
`{ region: FloorRegionId, nodes: [NodeId; 2] }`（dig Q6=B）。`nodes` は壁自体の
平面上の始点・終点（節点参照。線アンカーと同じ理由で節点移動に追随させる）で
自重の算定（面積）に使い、荷重は `nodes` ではなく `region`（所属する床領域）へ渡して
等価な面荷重へならす（D17。位置情報は失われるが長さは失われない）。既存の
`RegionAnchor` の全 match は `_` を使わない網羅的マッチだったため、コンパイラが
影響箇所を全数洗い出した（本番コード 10 箇所、6 クレートにまたがる）。このアンカーは
壁専用（床板 `Slab` の取付き先には使わない）であるため、`Slab` 側の全箇所は
「到達しないが網羅のために必要な受け皿」として `None`/`false`/no-op を返すよう
明示した（`_ =>` のワイルドカードで握りつぶさない。既存の `Slab::edge_nodes` に
1 箇所あった `_ => None` も同じ理由で明示化した）。

**`WallPlate`/`WallPlateShape` の実装**: `Slab`/`SlabShape` と同型（囲まれた領域 /
取り付く領域）の独立エンティティとして実装した（dig Q3=A）。相違点は次の 2 つ。

1. **取付き線アンカーの張り出し方向が異なる。** 床は取付き線の左向き法線方向
   （水平面内）へ張り出すが、壁は鉛直上向き（D15「壁は立ち上がり高さ」）へ
   立ち上げる。`WallPlate::boundary_coords` はこの違いを反映した専用の
   `extrude_up` を使う（`Slab::boundary_coords` の水平張り出しロジックとは別実装）。
2. **自重は必ず断面参照から求める。** `OutOfFrameMiscWall` が持っていた直接入力
   （`weight_per_area`・`thickness`）は廃止した（dig Q5=A。ST-Bridge 取り込みに
   生成コードがなく実データが 0 件だったため、移行対象の実利用がないと判断した）。
   `Model::wall_plate_self_weight` は `Model::slab_self_weight_intensity` と同じ
   規約（断面未割当は `None`。既定厚で補わない）。

参入レベル（4 節点要素を生成する構造壁／n倍法で偏心率にのみ寄与する雑壁剛性／
自重のみ）を区別する列挙型は `WallPlate` に持たせなかった（dig Q4=B）。`section` の
有無と、所属する `WallRegion` の種別（囲まれた領域か取り付き領域か）の組み合わせで、
生成ロジック（Step 8 本体）側が決める設計とした。

`Model` への統合（`wall_plates: Vec<WallPlate>` フィールド、`validate` の境界重複・
陳腐化参照・取付き線区間の検証、節点参照の巡回、`SectionId` 参照の巡回）は `Slab`
と同じ規約で一通り行った。**`WallRegion.wall_plate_ids`（`Slab` の `slab_ids` に相当）
は `WallRegion` の作り替えとあわせて次に実装するため、「複数の壁領域から共有されない」
検証・`visit_wall_plate_ids`/`retain_wall_plates`（`Slab` の同等物）はまだない。**

**副産物（敵対的な自己レビューで発見・修正）**: `region_gen::wall::WallRegionBoundary::area`
が自前実装していたニューエルの公式（`newell_area`）は、`crate::geom::polygon_area_3d`
（壁・シェル要素の自重算定とスラブ・壁の数量拾いが共通で使う既存関数。2026-08-12
導入、region_gen::wall 実装〔前回 PR #224〕より前から存在）と完全に同じ計算だった。
region_gen::wall 実装時に見落として重複させていたため、自前実装を削除し既存関数へ
統合した（数値は完全一致。既存テスト・実フィクスチャのピン止め値で確認済み）。

**未結線であることの明記**: `WallPlate` はまだ `WallRegion`・要素生成・ST-Bridge
入出力・UI のいずれとも結線していない。次の一手は `WallRegion` の作り替え
（`id`・`name`・`boundary`・`wall_plate_ids: Vec<WallPlateId>` へ。現行の
`wall: Option<ElemId>` を廃止）と、`region_gen::wall` の境界から `WallRegion` を
組み立てる `wall_region_rebuild`（`region_rebuild.rs` の壁側版）である。

### 5.9 `WallRegion` を `FloorRegion` と同型へ作り替え（2026-08-26、未結線）

§5.8 の次の一手のうち `WallRegion` の作り替えを実施した。`region_gen::wall` の
境界から `WallRegion` を組み立てる `wall_region_rebuild`・要素生成・ST-Bridge 移行・
参照張り替えはまだ行っていない。

**型の変更**: `WallRegion { wall: Option<ElemId>, post_ids }` を
`WallRegion { id: WallRegionId, name: String, boundary: Vec<NodeId>,
wall_plate_ids: Vec<WallPlateId>, post_ids }` へ作り替えた（`FloorRegion` と同型）。
`model/wall.rs`（壁属性を集めたファイル）から独立した `model/wall_region.rs` へ移した
（`FloorRegion` が `region.rs` に独立しているのと同じ理由。`wall.rs` は
`WallAttr`/`OutOfFrameMiscWall` 等、Step 7+8 で廃止予定の型が主体のため）。

`WallRegion` は**もはや `ElemId` を一切持たない**（D4・D5: 壁の解析要素は準備計算
からの生成物であり、モデルには残さない）。これに伴い、以下の連動処理を削除した
（残すと存在しない不変条件を守ろうとして無意味なコードになる）。

- `Model::visit_elem_ids` の `WallRegion.wall` を辿る分岐
- `DeleteMember`/`InsertMember`（squid-n-edit）の「削除した壁要素を指す壁領域を
  『版なし』へ戻し、undo で復元する」カスケード処理（`wall_region_refs` フィールド）
- `squid-n-edit::secondary` の `AddWallRegion`/`DeleteWallRegion`/`InsertWallRegion`/
  `SetWallRegion`（壁領域を丸ごと追加・削除・全置換する CRUD コマンド）

**壁領域は床領域と同じく「主架構から再構成される派生的な入力の持ち主」（D10）であり、
利用者が任意の境界を与えて追加・削除する対象ではない**（`region_gen::wall`/
`wall_region_rebuild` が組み立てる）。`FloorRegion` に `AddFloorRegion`/
`DeleteFloorRegion` が存在しないのと同じ理由で、上記 CRUD コマンドは削除し、
利用者が変更できる範囲を表示名（`SetWallRegionName`。`SetFloorRegionName` と同型）と
間柱の割当（`SetWallRegionPostIds`。`SetSlabSecondaryJoistIds` と同型）だけに絞った。

**`Model` への統合**: `wall_regions` の `id == index` 検証、境界の陳腐化参照・重複
検証（D1: 同じ境界を持つ壁領域は 2 つ不可）、`wall_plate_ids` の陳腐化参照・重複・
「複数の壁領域から共有されない」検証（床板と同じ規約）、`visit_wall_plate_ids`
（`visit_slab_ids` の壁側版）を追加した。`retain_wall_plates`（`retain_slabs` の
壁側版）は、壁版を間引く経路（UI・ST-Bridge 移行）がまだないため見送った。

### 5.10 `wall_region_rebuild` を実装し、準備計算・取り込みへ結線する（2026-08-26）

§5.9 の次の一手として `crates/squid-n-core/src/wall_region_rebuild.rs` を新設し、
`rebuild_floor_regions`（床側）と同じ 3 箇所（`squid-n-app::app::actions::loads::
sync_auto_load_cases_action`、`squid-n-job::prepare::prepare_model_for_analysis`、
ST-Bridge 取り込み `assemble.rs`）へ `rebuild_wall_regions` を結線した。D5 が求める
「GUI の準備計算とヘッドレス実行の両方から同じ関数を呼ぶ」を壁側でも満たす。

**これは `region_gen::wall`/`RegionAnchor::FloorRegion`/`WallPlate`/`WallRegion` の
中で初めて実データパイプラインへつながったコード**である。ただし壁版
（`WallPlate`）の取り込み・要素生成はまだ行っていないため、`model.wall_regions` は
境界の幾何（`id`・`name`・`boundary`）だけが実際に埋まり、`wall_plate_ids` は常に
空のまま（版なし壁領域と同じ状態）になる。

**アルゴリズム**（`rebuild_floor_regions` との相違点）: 床は「同じレベル Z」で
新旧区画を対応付けるが、壁は構面（直線）ごとに閉領域が現れるため、まず
`WallRegionBoundary::is_same_plane`（候補点が実距離で同じ直線上にあるか。
`region_gen::wall` の直線統合と同じ判断基準）で構面を絞り込んでから、構面の
局所座標 `(s, z)` へ射影した重心で内包判定（`WallRegionBoundary::contains`）を行う。
面積は常に実座標（3 次元）から求める（§3.2 E3 を踏襲。射影はトポロジー判定にのみ使う）。
`WallRegionBoundary` にこの判定用の `contains`/`is_same_plane` を新設した
（`RegionBoundary::contains`/`is_same_level` の壁側版）。

**床側 D20（パネルに収まらない版を取り付き版へ自動変換する）に相当する規則は
壁側でまだ決めていない。** 囲まれた壁版でどの壁領域にも収まらないものは、変換せず
「帰属なし」として件数のみ報告する（残課題。取り付き領域〔パラペット・腰壁・
垂れ壁・自立壁〕の自動判定基準を dig で確定してから実装すること）。

**検証**: 実フィクスチャ（`full_model.rs::import_populates_wall_regions_from_region_gen`）
で、ST-Bridge 取り込みが実際に `model.wall_regions` を 55 件（`region_gen_finds_
wall_bounded_regions` と同じ件数）埋めること、`id == index` が保たれること、
本フィクスチャは壁版を持たないため `wall_plate_ids` が全件空であることを確認した。
`wall_region_rebuild.rs` 自身の単体テスト（4 件: 検出・名前と間柱の引き継ぎ・
壁版の帰属・帰属なしの壁版が残ること）も追加した。**この結線でも
既存の解析結果（`snapshot_key_scalars`・`snapshot_wall_bay_scalars`）は無変化**
（壁領域の追加は純粋に付加的なメタデータで、まだ何の計算にも使われないため）。

### 5.11 §5.10 の結線後レビューで見つかった 2 件の抜けを埋める（2026-08-26）

§5.10 の結線をコミットした直後、実データパイプラインへ初めてつながったことを
理由に改めてレビューし、以下を修正した。

- **`WallPlate` が `WallAttr` の開口関連フィールドを 2 つ引き継いでいなかった。**
  `opening_area`（個別開口 `openings` が空のときのフォールバック用の合計面積）と
  `opening_weight`（開口部・サッシ等の重量。控除後に加算）が抜けており、
  `WallAttr` を「合計面積のみ」で運用している壁を `WallPlate` へ移行すると
  開口控除が一切効かなくなる欠陥だった。dig Q5（自重は断面参照のみで求める）は
  `weight_per_area`/`thickness`（直接入力の面重量・厚さ）の廃止だけを扱っており、
  開口関連フィールドの扱いは合意事項に含まれていなかった。`WallAttr` と同じ
  2 フィールドを追加し、`total_opening_area`・`wall_plate_self_weight` の式を
  `WallAttr`/`enumerate_self_weight` と同じ規約に揃えた。
- **性能の実測が「グリッドの合成データのみ」で、実データでの比率が未確認だった。**
  `wall_region_rebuild` は §5.10 で `sync_auto_load_cases_action`（対話的操作）にも
  結線したため、超線形の絶対時間（残課題一覧参照）だけでなく「準備計算全体に対する
  比率」も見ておく必要があった。実 ST-Bridge フィクスチャで実測したところ
  `scan_wall_region_boundaries` は準備計算全体の 7.4%（0.36ms/4.9ms）で、この
  フィクスチャの規模では無視できる。ただし 900 本規模での絶対時間（1.8 秒）は
  未解消のまま残っており、規模が大きいモデルでは対話的操作のたびに数秒級の
  遅延が起きうる（残課題一覧に追記）。
- ついでに `WallRegion`/`WallPlate` のモジュール doc の「未結線」表記が §5.10 の
  結線前のまま更新されておらず、実態と食い違っていたため書き直した。用語集の
  「壁領域」「壁領域の境界」「壁版」の 3 エントリも同様に更新した。
- `WallRegion` の ID は `region_gen::wall` の走査順（`model.elements` の並び順に
  依存。D10）に頼っているため、「保存 → 読込 → 再度準備計算」を経て走査順が
  ぶれないことを固定する回帰テスト（`full_model.rs::
  wall_regions_survive_save_reopen_reprepare`）を追加した。

**未着手のまま残る指摘**: `WallPlate::area` は境界の生の面積（ニューエルの公式）
であり、既存の `enumerate_self_weight`（`squid-n-load`）が耐震壁の自重に適用して
いる「周辺柱梁の内法寸法」による面積低減（`wall_clear_area_factor`）を持たない。
自重算定を `WallAttr` から `WallPlate` へ移行する際にこの低減をどこへ持たせるかを
先に決めておかないと、型移行のはずが計算根拠まで変わってしまう（残課題一覧参照）。

## 8. 未決事項

### 8.1 床側（Step 1 の着手前に決める）

- **段差床のある階の面走査。** D8 は水平面ごとに閉路を採るが、段差床のある階は同一階に
  複数のレベル面ができ、段差部の梁はどちらの面にも属する。面走査の入力をレベルで切る規則が要る
- **外周面の判別。** D8 に「最も面積の大きい面を捨てる」と書いたが、これは誤り。
  外周面は符号付き面積が負（時計回りに一周する）面として判別すること。
  中庭のある建物では、面積最大の内部面が外周面より大きくなりうる
- **中庭・吹抜けの扱い。** 上記の面走査では中庭も内部面として現れ、版なし床領域になる。
  それが意図どおりか（領域として持つか、除外するか）を決める
- **`Model.slabs` を置き換えるとき、床の面荷重強度が異なる領域が隣り合う場合の小梁の負担。**
  現行は代表スラブの強度を用いており、Step 4 の分配で厳密化する

### 8.2 壁側（Step 7 の着手前に決める）

**2026-08-25、dig により全項目解消（§3.2 の E1〜E8 参照）。**

- ~~鉛直構面の検出条件。斜め構面、節点が同一平面にない構面をどう扱うか~~ → **解消（E1・E2）**。
  通り芯に依存しない新規幾何判定（芯線候補 ＋ `MEMBER_AXIS_TOL_MM`）で直交・斜めを同じロジックで扱う。
  非平面な壁面は複数の `WallRegion` へ自然に分解される
- ~~壁版の開口（`WallOpening`）を領域が持つときの、複数開口モード（`Model.multi_opening_mode`）との関係~~
  → **解消（E6）**。引き続き `Model` 全体で 1 つのグローバル設定のままでよいと確認した
- ~~柱梁に囲まれない雑壁の受け皿~~ → **解消（E4）**。`OutOfFrameMiscWall` は D14 の 3 アンカー（線／点／床領域）を
  必須とする節点参照へ完全移行するため、「囲まれない」状態自体が作れなくなる
  （§2 の残課題一覧に載っていた 3 項目目。本書 §8.2 には当初なかったが同じ dig で解消した）

### 8.3 Step 3 の着手前に必要な対応

- ~~取り付き領域の辺荷重の解決を幾何解決へ寄せる~~ → **対応済み**。線分を覆う梁を幾何で求める
  `beams_along_segment` を新設し、`Span` の解決へ組み込んだ。実建物では 122 件の節点集中荷重が
  梁の分布荷重になった（記録は
  [`v_and_v/床辺荷重の梁への幾何割付_2026-08.md`](../v_and_v/床辺荷重の梁への幾何割付_2026-08.md)）
- ~~`PanelScan::crossings` を `run_diagnostics` へ接続する~~ → **対応済み**。`region_gen::crossing_beams`
  を `precheck::model_issues` へ組み込み、警告として診断・解析前チェックの両方に出るようにした
  （解析自体は通るためエラーにはしない）。判定を 1 か所に置くため、診断と解析前チェックが
  別々の検査を持たない既存の方針に合わせている。
  交差判定は総当たり（梁の本数の 2 乗）だったため、境界矩形の走査線法で絞るようにした
  （release ビルドでの実測: 梁 32,800 本で 532ms → 3.2ms、面走査全体で 530ms → 17ms）

**Step 3 の前提条件はすべて解消した。**

なお、「点が部材の材軸上に載っているとみなす許容差」は `geom::MEMBER_AXIS_TOL_MM`（10mm）へ
一本化した。荷重の割り付け（`secondary::SPAN_TOL_MM`）と交差の診断が別々の基準を持っていると、
「荷重は載るのに診断には出ない」ずれが生じるためである（交差の判定は外積のしきい値を
用いており、長い部材ほど厳しくなっていた）。

### 8.4 横断

- **ST-Bridge 出力と D5 の整合。** 要素をモデルに残さない以上、出力時に展開を走らせないと
  壁が出力から消える。出力経路が展開関数を呼ぶ形にすること（D12 により、出力で表現しきれない
  ものが落ちるのは許容するが、壁が消えるのは別問題）
- **D10 の対応付けキーの弱さ。** 重心とレベルをキーにすると、通り芯を動かすような節点座標の
  編集で全領域の重心が変わり、版仕様も二次部材も引き継げない。境界節点集合や重なり面積率を
  副次キーにする案を検討すること
