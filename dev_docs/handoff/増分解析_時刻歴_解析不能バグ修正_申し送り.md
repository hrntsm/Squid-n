# 増分解析・時刻歴応答解析の解析不能バグ修正 申し送り

作成日: 2026-07-30
対象コード:
`crates/squid-n-math/src/sparse.rs`（`CscAssembler`/`WeightedSumCache`/`scale_csc_into`）、
`crates/squid-n-solver/src/common/csc_cache.rs`（`CscCache`/`WeightedSumGuard`）、
`crates/squid-n-element/src/factory/input_check.rs`、
`crates/squid-n-app/src/app/actions.rs`（解析スレッド panic のメッセージ引き継ぎ）

## 症状（利用者からの報告）

- UI から増分解析を実行すると「増分解析エラー: factor: NotPositiveDefinite」で停止する。
- 時刻歴応答解析を実行すると「解析スレッドが異常終了しました（プログラムの不具合の
  可能性があります）」と表示される（解析スレッド内 panic）。

## 不具合 1: CSC 組立キャッシュのパターン誤判定（NotPositiveDefinite の原因）

### 根本原因

解析高速化・第2〜3波（`時刻歴応答解析高速化_第2波_申し送り.md`・
`解析高速化_第3波_申し送り.md`）で導入した `CscAssembler`／`WeightedSumCache` の
高速パスは「渡された triplet 列（入力行列）の非ゼロ数が前回と一致すればパターン不変」
とみなし、座標・並び順の一致は `debug_assert` でしか検証していなかった。

しかし弾塑性要素の接線剛性は成分が厳密 0.0 を跨いで消えたり現れたりするため、
**「ある成分が消えるのと同時に別の座標の成分が現れ、非ゼロ数はたまたま一致する」**
遷移が起こり得る。このとき release ビルドでは検証なしで前回のスロット写像へ値を
書き込み、**全く別内容の壊れた行列**を組み上げていた。

- 増分解析: `newton_converge`（`pushover/driver.rs`）の
  `assemble_k_cached`／`reduce_k_cached` で壊れた `k_red` が
  `factorize` へ渡り `NotPositiveDefinite`。
- 時刻歴: `K_eff = K_t + c2·C + c1·M`（`WeightedSumGuard`、
  `dynamic/timehistory/nonlinear.rs`）にも同型の欠陥があった。
- debug／test ビルドでは `debug_assert` が先に落ちるため、`cargo test` では
  NotPositiveDefinite の形では決して現れない（UI の release 配布物でのみ発症）。
- 最悪ケースは、壊れた行列がたまたま正定値のまま分解に成功し
  **黙って誤った解析結果を返す**ことで、エラー停止より危険だった。

### 修正

パターン一致判定を**座標・並び順の完全比較（O(nnz) のスライス比較）**へ変更し、
不一致時は release ビルドを含む全ビルドで安全側（パターン作り直し）へフォールバック
するようにした。判定と作り直しは `CscAssembler::assemble_into`／
`WeightedSumCache::combine_into` 自身が行い、呼び出し側（`CscCache`／
`WeightedSumGuard`）は次元 `n` の変化への追従と初回構築のみを担う。

- 結果は従来どおり `assemble_csc`／`weighted_sum_csc` とビット一致
  （フォールバックした回だけ組立コストが非キャッシュ版相当に戻る）。
- 高速パスに O(nnz) の比較コストが加わるが、組立・分解の O(nnz log nnz)〜に比べ軽微。
  `CholeskySolver` の symbolic キャッシュ判定（`SparsityPattern::matches`）と同じ方針。
- `scale_csc_into` の非ゼロ数検証も `debug_assert` から release 有効の `assert` に
  格上げした（現状の呼び出し元は安全だが、将来の誤用で黙って壊れないように）。

### 回帰テスト

- `squid-n-math` `sparse.rs`: `test_csc_assembler_rebuilds_on_same_count_pattern_change`、
  `test_weighted_sum_cache_rebuilds_on_same_nnz_pattern_change`
- `squid-n-solver` `csc_cache.rs`: `test_csc_cache_same_len_different_coords`

## 不具合 2: 非正の材料強度が入力チェックを素通りし解析スレッドが panic

### 根本原因

履歴則2系統化（PR #148）でファイバーの鋼材・主筋は「fy 未設定なら弾性代替」から
「入力チェックで解析前にエラー停止（素通りした場合は `steel_fiber_material` が
panic）」へ変更された。しかし `factory::input_check::member_strength_issue` の
断面形状未設定（`shape: None`）の分岐は `fy.is_none() && fc.is_none()` しか見ておらず、
**`fy: Some(0.0)` のような非正値を「設定済み」として素通し**していた。

- 柱は `ForceRegime::Auto` で常に Fiber レジームへ解決されるため、該当部材があると
  要素生成（`build_gauss_fibers` → `steel_fiber_material`）が解析スレッド内で panic し、
  UI には「解析スレッドが異常終了しました」としか表示されない。
- `fc: Some(0.0)` も同様に素通りし、剛性 0 のコンクリートファイバによる剛性行列の
  特異化を招く。

### 修正

`shape: None` の線材の検査を要素生成と同じ規則
（「Fc があればコンクリート、なければ鋼材で fy 必須」）に揃え、**正の値**であることを
検証するようにした。鋼材断面形状（形鋼・鋼管）の分岐も明示 return に整理
（従来から fy>0 を検証済み。挙動不変）。利用者向けの入力チェック表
（`docs/calc_basis/05_構造解析/07_プッシュオーバー解析.md`）へ現仕様を反映済み。

### 回帰テスト

`factory/input_check/tests.rs`: `test_issue_when_shapeless_member_fy_not_positive`、
`test_issue_when_shapeless_member_fc_not_positive`

## 改善: 解析スレッド panic メッセージの UI 引き継ぎ

従来、解析スレッドの panic は `catch_unwind` で受けて定型文
「解析スレッドが異常終了しました…」だけを表示しており、利用者・開発者とも原因
（入力不備かプログラム不具合か）にたどり着けなかった。`analysis_panic_message`
（`actions.rs`）で panic ペイロード（`String`/`&str`）を定型文の後ろへ付加する
ようにし、全 `start_*_job`（7 箇所）へ適用した。今後同種の panic が発生しても、
ログに実際のメッセージ（例: `steel_fiber_material` の fy 未設定メッセージ）が残る。

## 検証（時刻歴の panic 再現調査）

fc/fy を正しく設定した有効モデル（RC ポータルフレーム＝柱ファイバー
Karsan–Jirsa 型＋Menegotto–Pinto、耐震壁 1 枚＝壁柱ファイバー＋最大点指向型
せん断ばね）に対し、UI と同一経路（`ensure_nonlinear_input` → 固有値 → 減衰 →
`nonlinear_time_history_analysis`、UI 既定値）で大振幅共振正弦波・長期荷重初期
載荷の有無・`dt`（0.01〜0.001）・並列度（Deterministic/Auto）を振って検証したが、
panic は再現しなかった（すべて正常終了または `SolveError` の穏当なエラー終了）。
利用者環境の時刻歴 panic は、不具合 2（入力チェック素通り）または不具合 1 の
壊れた行列の下流影響が原因である可能性が高い。再発時は上記の panic メッセージ
引き継ぎにより実際の発生箇所が特定できる。

## 残課題・申し送り

- 不具合 1 のフォールバックは「同一 Newton 反復列内でパターンが頻繁に揺れる」モデル
  では毎回作り直しになり高速パスが効かない。頻発するようならヒステリシス
  （直近 N 回のパターンを保持）等の検討余地があるが、正しさ優先で現状はシンプルに保つ。
- 未検証パス（低リスクとして留保）:
  `wall_panel.rs` の `restore_state` 内 `deserialize_state(...).expect(...)`
  （時刻歴の長期荷重漸増が非収束のときのスナップショット巻き戻しでのみ到達。
  同一プロセス内の bincode ラウンドトリップのため通常失敗しない）、および
  数百要素規模のモデルでの要素ループ並列（`par_iter_mut`）の実並列実行。
- 耐震壁モデルは終局耐力付近で Newmark の時間刻みに敏感な非収束
  （`SolveError`、panic ではない）を示す。UX 改善（刻み自動細分など）の検討余地。
