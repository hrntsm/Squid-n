# 階と剛床の分離 申し送り

作成日: 2026-08-06
対象コード:
`crates/squid-n-core/src/model/{story.rs,constraint.rs,aggregate.rs}`、
`crates/squid-n-load/src/story_gen/{mod.rs,generate.rs}`、
`crates/squid-n-solver/src/statics/analysis/{seismic.rs,wind.rs,precheck.rs}`、
`crates/squid-n-solver/src/nonlinear/pushover/response.rs`、
`crates/squid-n-element/src/{shell/element.rs,factory/regime.rs}`、
`crates/squid-n-edit/src/story.rs`、`crates/squid-n-app/src/app/{panels.rs,actions.rs}`、
`crates/squid-n-io/src/stbridge/import/assemble.rs`、`crates/squid-n-load/src/ai.rs`、
`docs/preparation/{README.md,01_階の分布.md}`、
`docs/calc_basis/01_荷重/{01_地震力.md,02_風圧力.md,06_地震用重量_層データの生成.md}`、
`dev_docs/specs/{P0_基盤.md,構造計算一貫プログラム_実装設計書.md}`

モデル作成支援機能（軸・階を先に定義してグリッドから部材を作る／階への複製）の
土台として、階と剛床の癒着を解いた第 1 弾。作成ウィザード・3D グリッド・階複製は
本申し送りの範囲外（後続で実装する）。

## 変更前の問題

階は法規上の層（層間変形角・層せん断力・剛性率・偏心率の対象）、剛床は解析上の
面内剛体拘束であり、本来は別物である。ところが実装では次の 4 点で癒着していた。

1. 剛床の情報が `Story.diaphragms`（`DiaphragmDef`）と
   `Constraint::RigidDiaphragm { story, master, slaves }` の**2 か所に重複**していた。
   どちらも story・master・slaves を持ち、どちらが正かの規約がなかった。
2. `story_gen` が階と剛床を同時生成し、階はちょうど 1 つの剛床を持った。剛床のない階を
   作る経路が存在しなかった。
3. 「階に属する」と「剛床に拘束される」が同義だった（`slaves = node_ids.clone()`）。
   このため柱の分割点など**中間高さの節点まで剛床のスレーブ**になり、存在しない
   水平剛性が生じていた。
4. `DiaphragmDef.rigid`（柔床を表す欄）は `false` を作る経路がなく、読まれるのも
   シェルの `membrane_active` 判定 1 箇所だけだった。

加えて階そのものが節点 Z のクラスタリングで毎回作り直される派生物で、階名は `1F`
形式の固定生成、利用者が階名・階レベルを定義する場所がなかった。

## 対応

### 1. 剛床を `Constraint::RigidDiaphragm` へ一本化

`DiaphragmDef` と `Story.diaphragms` を削除し、`weight`・`ci_override` を
`Constraint::RigidDiaphragm` へ移した。**この拘束が存在すること自体が「面内剛体である」
ことを意味する**ため、`rigid: bool` は廃止した（柔床は要件になく、拘束は無条件に
剛体縮約されるので `rigid: false` は自己矛盾する状態だった）。

階から剛床を辿る経路は `Model::diaphragms_of(story) -> impl Iterator<Item = DiaphragmRef>`
に集約した。節点が剛床上にあるかは `Model::node_on_rigid_diaphragm`。

### 2. 帰属規則を階と剛床で分けた

| 対象 | 規則 | 実装 |
| --- | --- | --- |
| 階 | 区間 `(直下階のレベル, 当該階のレベル]`。最下階の下端は基部レベル | `Model::story_spans` / `story_at` / `node_stories` |
| 剛床 | 床面（階のレベル ±`DIAPHRAGM_LEVEL_TOL_MM` = 1mm） | `Model::on_diaphragm_level` |

中間高さの節点は階には属し（重量が階へ算入される）、剛床には入らない。段差床は
区間の規則で同一階に属し、剛床が床レベルごとに分かれる（多剛床は既存機構で扱える）。

基部レベルの定義（剛床代表節点を除く全節点の最小標高）は `Model::base_elevation` へ移し、
solver 側の `analysis::base_elevation` はその薄いラッパーにした。

### 3. 階を利用者定義のデータへ格上げ

`Story` の欄を「利用者が決める（`name`・`elevation`・`level_kind`・`weight_override`）」と
「準備計算が埋める（`node_ids`・`seismic_weight`・`structure`）」に分けて明文化した。
`generate_stories` は `Model.stories` の `elevation` を階レベルの正として使い、階名・階種別・
重量の手入力をそのまま引き継ぐ。Z クラスタリングは**階が 1 つも定義されていないときだけ**の
初期化に降格した（既存モデル・ST-Bridge 取り込みの受け皿）。

これにより `carry_over_manual_story_settings` は不要になったので削除した（生成が引き継ぎを
担うため、app 側での後追い呼び出しも消えた）。

`squid-n-edit` に `AddStory` / `DeleteStory` / `SetStoryLevel`（逆操作は `RestoreStoryDefs`）を
追加し、右パネル「階の定義」で行追加・削除・階名／レベルの編集ができるようにした。
階の追加・削除・レベル変更は `elevation` 昇順と `StoryId` ＝配列位置の 2 つの不変条件を
保つため、`Model::visit_story_ids`（新設）で全参照を振り直す。**階の削除は階定義だけを消し、
節点・部材は残す**（属していた節点は次の階生成で直下階の区間へ吸収される）。

### 4. 剛床のない階への水平力

剛床がない階では載荷先の代表節点が存在しないため、階に属する節点へ質点質量比で分配する
（`distribute_pi_over_story_nodes`）。質量が無い／合計 0 なら等分割。層せん断力の総量は
保たれるが、載荷位置は床面の代表点ではなく個々の節点になる。地震力・風圧力・プッシュオーバー
の 3 経路すべてが同じ規則を通る。

プッシュオーバーの層間変位・頂部変位・制御自由度は `story_reference_node`（剛床マスター、
なければ階の最重量節点）を介するようにした。

## 敵対的レビューで検出・修正した不具合

実装後の自己レビューで 4 件の実バグを検出し、本作業に含めて修正した。

### 1. ST-Bridge の階が標高昇順に並ばない（本作業で顕在化）

取り込みは `StbStory` を `file_id` 順に並べていた（`assemble.rs`）。従来は階生成が Z
クラスタリングで階を作り直していたため実害がなかったが、本作業で「`elevation` 昇順」が
`Model::story_spans` の前提になったため、階が標高順に書かれていないファイルで帰属区間が
反転し、節点が無言で別の階へ入る（またはどの階にも入らない）状態になっていた。

取り込み時に標高昇順（同標高は file id 順）へ並べ替え、`StoryId` をその順で振り直すよう
修正した。節点の所属階の参照も同じ順位表を引く。

### 2. 重量 0 の階で地震力が NaN になり無言で消える

`Ai = 1 + (1/√αi − αi)·2T/(1+3T)` は αi = 0 で発散し、`Qi = Ci·αi·ΣW` が `∞ × 0 = NaN` に
なる。NaN の水平力は載荷側の `!share.is_finite()` で捨てられるため、**地震力が静かに
欠落する**。総重量 0 のモデルでは `0/0` で αi 自体が NaN になる経路もあった。

この欠陥は従来から存在したが、本作業で「利用者が階を先に定義する」導線を入れたことで、
部材のない階（重量 0）が通常の操作で作れるようになり到達しやすくなった。αi ≤ 0 で
Ai を 0 に倒す判定を `ai_of_alpha` へ集約し、`ai_distribution` と
`seismic_shear_distribution`（PH・地下の混在経路。こちらにも同じ発散があった）の
両方が通るようにした。

### 3. 階の代表節点の同点処理が不定

剛床のない階の代表節点は「質点質量が最大の節点」としたが、`Iterator::max_by` は同点で
**最後**の要素を返す。質量未設定の階では全節点が同点になるため、実質「最後の節点」が
選ばれていた（doc コメントには「最初の節点」と書いており記述も誤り）。基準点が不定だと
層間変位と変位制御の基準が入れ替わり、同じモデルでも結果が再現しない。質量が同点なら
節点 ID の最小を採るよう比較を明示した。

### 4. `elevation` 昇順の不変条件が検査されていない

`story_spans` がこの並びに依存するのに、`Model::validate` は `StoryId` ＝配列位置しか
検査していなかった。標高の逆転を検出してエラーにするよう追加した。

なお、`ShellElement::new` の剛床判定は従来「節点の所属階の剛床だけを見る」近道を使って
いたが、剛床の情報源を拘束へ一本化したため全拘束の走査になり、計算量が階数倍になる。
同じ走査は `factory::regime` の `is_on_rigid_diaphragm` が全部材に対して以前から行って
おり（むしろ階と拘束の二重走査だったものを半減させた）、新しい計算量の階層を持ち込んでは
いないと判断してそのままとした。要素生成が重いモデルが出てきたら、剛床節点の集合を
1 回だけ作って要素生成へ渡す形を検討する。

## 検証

- `cargo test --workspace` / `cargo test -p squid-n-app --features gui` 緑
- `cargo clippy --workspace --all-targets --locked -- -D warnings`、gui・mcp フィーチャ版とも緑
- `cargo run -p xtask -- check-deps` 緑（依存方向に変化なし）
- 追加したテスト
  - core: 区間帰属と床面帰属の分離、段差床の多剛床、剛床なしの階、`visit_story_ids` の網羅
  - load: 中間節点が階に属し剛床に入らないこと、階定義が割り付けを支配すること、
    床面に節点がない階が剛床を持たないこと、再生成が利用者定義欄を保つこと
  - edit: 追加・削除・レベル変更の並べ替えと ID 繰り上げ、undo での復元
  - solver: 剛床のない階の水平力が質量比／等分割で分配されること
  - io: `StbStory` が標高順でないファイルでも取り込み後に昇順・ID＝配列位置になること
  - load: 重量 0 の最上階・総重量 0 のモデルで Ai・Qi・Pi が非有限にならないこと
  - core: 標高が逆転した階を `Model::validate` が弾くこと

## 既知の挙動変更（利用者から見えるもの）

- 中間高さの節点が剛床のスレーブから外れる。剛床に不当な節点が入っていたモデルでは
  水平剛性が下がり、応力・変形が変わる（**是正**であり、変更前が誤り）。
- ST-Bridge から取り込んだ階（`StbStory` の `name`・`height`）が準備計算で上書きされなく
  なった。取り込んだ階名がそのまま残る。
- ST-Bridge の階は床レベル基準（`1F` の height が GL）であるのに対し、`story_gen` が
  作る階は層基準（`1F` の elevation が 2FL）で、**両者で階名が 1 つずれる**。どちらも
  内部的には整合しており計算は成立するが、取り込みモデルと新規モデルで階名の意味が
  異なる点は未解決の残課題（下記）。

## 残課題

- **階名の基準の統一**: 上記のとおり ST-Bridge 由来（床基準）と自動生成（層基準）で
  階名が 1 つずれる。どちらへ寄せるかは利用者向けの表記の問題であり、作成ウィザードで
  階名を入力させる設計（後続 PR）と合わせて決めるのがよい。
- **剛床のない階の診断**: 剛床数 0 の階は準備計算の一覧で強調表示されるが、
  `model_issues` の診断項目にはなっていない。意図せず剛床が消えた場合に気づきにくい。
- **後続 PR**: 作成ウィザード（軸・階の入力、柱・大梁・柱脚支点の一括生成）と 3D 立体
  グリッドのスナップ、階への複製機能。設計は本作業前の深掘りで確定済み。
