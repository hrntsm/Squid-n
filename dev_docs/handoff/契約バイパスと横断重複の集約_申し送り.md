# 契約バイパスと横断重複の集約 — 申し送り

作成日: 2026-09-04
対象コード: `squid-n-core`、`squid-n-element`、`squid-n-edit`、`squid-n-solver`、`squid-n-load`、`squid-n-design-jp`、`squid-n-app`、`squid-n-solver/examples`

この申し送りでは、ワークスペース全体を走査して見つけた重複を 5 つのテーマへ分けて集約した経緯を記録します。
5 つのうち 2 つは、**すでに「ここを使う」と決めてある下層のヘルパを、上層が使わずに同じ式を書いていた**ものです。
残る 3 つは、同じものが 2 か所または 3 か所にある単純な重複です。

## 背景 — 決めた契約が守られていない重複

過去の集約（[クレート横断の重複統合](クレート横断の重複統合_申し送り.md)、[2D 多角形の幾何プリミティブ集約](2D多角形の幾何プリミティブ集約_申し送り.md)）は、共通部分を下層クレートへ出す形で重複を解消してきました。
`squid_n_core::geom::vec3` や `Model::member_length` はそのときに作られたもので、doc には「材長が要るところは常にこのメソッドを使う」と単一情報源であることが明記されています。

ですが今回あらためて走査すると、**その契約を通らずに同じ式を書いている箇所が残っていました**。
集約したはずのものが再び複製されていく形で、これは複製の中でもたちが悪いものです。
下層に正しい実装があるぶん、上層の複製は「どうせ同じだろう」と読み飛ばされ、食い違いが生まれても気づかれにくくなります。

実際、今回見つかった複製では退化判定のしきい値が `< 1e-9`・`<= 0.0` と割れていました。
区間の妥当性判定にいたっては、**コメントが「同じ範囲」と書いているのに実際には違う**という状態です。

見つかった重複は次の 5 テーマです。

| テーマ | 箇所 | 性格 |
|---|---|---|
| 材長と 3 次元ベクトル演算 | 材長 4 か所・`squid-n-element` の手書き演算 22 か所・`viewer::solid` の零長判定 1 か所・私的ヘルパ 2 個・無意味なラッパ 1 個 | **契約バイパス**。下層に正がある |
| 取付き線の区間の妥当性判定 | 4 クレート 9 か所 | **契約バイパス**。しかも内容が食い違っていた |
| N-M 相関曲面の 3D 描画 | 2 画面 | doc コメントが重複を自認 |
| ベンチ例題の断面・材料 | 3 本 | バイト単位で一致 |
| 波形読込から地動入力まで | 3 経路 | エラー文言の書き方だけが割れていた |

## 決めたこと

着手前に dig で 5 問を確認し、次の形に決めました。

| 問い | 決定 |
|---|---|
| 対象の範囲 | 上表の 5 テーマすべて |
| ワイヤーフレームの不透明度（180 と 160 の食い違い） | 引数として残し、表示は変えない |
| 区間判定の集約範囲 | 9 か所すべて。**許容つき**（`>= -1e-9` / `<= 1.0 + 1e-9`）を正とする |
| `vec3` 集約の境界 | 当初洗い出した 6 か所に加え、`squid-n-element` の 22 か所すべてを含める |
| コミットの分け方 | テーマごとに 5 コミット + ドキュメント 1 コミット |

不透明度を引数に残したのは、今回が `refactor`（仕様に影響がないコード改善）だからです。
表示値を動かすと差分の性質が変わり、目視確認の負荷も上がります。
不透明度は「その図が何を重ねて見せたいか」に依存する呼び出し側の情報なので、`examples/common/mod.rs` が採った「定型だけ集め、差異は呼び出し側へ残す」判断とも一致します。

## 材長と 3 次元ベクトル演算

`Model::member_length` は doc で単一情報源を宣言しており、テストを除く 16 か所がそれに従っています。
ですが次の 4 か所は、節点座標を自分で引いて材長を手書きで算定していました。

- `solver::common::assemble::member_load_frame`（`< 1e-9` で `None`）
- `solver::nonlinear::pushover::member_response::member_rp_angle`（`<= 0.0` で 0.0）
- `design_jp::rc::horizontal_joint`（`< 1e-9` で `continue`）
- `design_jp::joint_wiring`（`< 1e-9` で `continue`）

同様に `squid_n_core::geom::vec3` があるにもかかわらず、内積・外積・ノルムを手書きしている箇所が `squid-n-element` に 22 件ありました。
とくに `LocalFrame::from_nodes` は、冒頭で `vec3::sub` / `norm` / `scale` を使いながら、続く正規直交化だけ手書きという混在状態です。
同じ関数の中で流儀が割れているのは、読む側にとってもっともわかりにくい形です。

あわせて `squid-n-load` の私的ヘルパ `dist3` を 2 つ（`floor::joist_design` と `cascade`。どちらも `vec3::dist` と同一）と、`Model::member_length` へ委譲するだけの `app::load_editor::elem_length` も削除しました。
同じクレートの `floor::geometry`・`story_gen::geom`・`wall_attached` は、すでに `use squid_n_core::geom::vec3::dist as dist3;` の形で core を参照していました。
つまり**同じクレートの中で、正しい形と私的な実装が同居していた**ことになります。
削除した 2 つもこの流儀へ揃えました。
`cascade` のほうは着手時の走査では見落としており、実装後のレビューで見つけたものです。
`app::viewer::solid` の零長部材の判定も `vec3::dot(d, d)` へ寄せています。
ここは平方根を省くために材長ではなく平方のまま比べており、材長そのものを要しないので `member_length` ではなく `vec3` を使う形が合います。

### 置き換えがビット一致であること

解析結果を変えていないことは、演算順序まで一致させることで保証しています。

`vec3::dot` は `a[0] * b[0] + a[1] * b[1] + a[2] * b[2]` そのもので、`norm` は `dot(a, a).sqrt()`、`cross` も成分の並びが手書き形と同じです。
浮動小数の乗算は交換法則が厳密に成り立つため、`ref_vec[0] - rdot * ex[0]` を `vec3::sub(v, vec3::scale(ex, rdot))` へ置き換えても結果は 1 ビットも動きません。

**正規化の除算だけは `vec3::unit` へ寄せませんでした。**
`unit` の縮退判定は mm 座標を前提とした `ZERO_TOL`（1e-9）ですが、`LocalFrame` や `ShellFrame` が測るのは無次元の残差ベクトルで、そこでの判定値 1e-12 とは意味が違います。
また `x / l` と `x * (1.0 / l)` は IEEE754 では一致しないため、除算の形も元のまま残しました。
判定値はいずれも変えていません。

### `joint_wiring` の鉛直成分

`joint_wiring` は材長のほかに鉛直成分 `ez` も必要とします。
既存の `geom::element_axis` はこれを単位軸ベクトルとして返しますが、**終端に `nodes` の末尾を採る**ため、この走査では使えません。
`joint_wiring` の対象には 4 節点の壁が含まれており、`element_axis` を使うと `nodes[3]` を見て `member_length`（`nodes[1]` を見る）と食い違います。
そのため `ez` だけは材端 2 節点から求め直し、その理由をコメントに残しました。

## 取付き線の区間の妥当性判定

取付き線の無次元区間 `span` は `0.0 <= t_i < t_j <= 1.0` という規約を持ちます。
この判定式が 4 クレート 9 か所へ複製されており、**しかも内容が一致していませんでした**。

| 場所 | 箇所 | 下限 | 上限 |
|---|---|---|---|
| core `model/aggregate.rs`（`Model::validate`） | 2 | `>= -1e-9` | `<= 1.0 + 1e-9` |
| edit `wall_misc.rs` | 3 | `>= -1e-9` | `<= 1.0 + 1e-9` |
| app `tables/slabs.rs`・`tables/wall_plates.rs` | 4 | `>= 0.0` | `<= 1.0` |

app 側の 4 か所はすべて「`Model::validate`（squid-n-core）・… と**同じ範囲**」とコメントしていますが、両端の 1e-9 の許容がなく実際には同じではありません。
これは前掲の申し送りが警告していた「コメントで『◯◯と同じ』と自認した複製が食い違っていく」型そのものです。

`model::span_is_valid` を `RegionAnchor` の隣へ新設し、9 か所すべてを置き換えました。

許容つきを正としたのは、`span` が浮動小数の無次元比だからです。
`1.0` を意図した値が計算経路で `1.0 + ε` になることはありえます。
保存時の最終防衛線である `validate` が許容を持つ以上、**UI だけが厳しいと「保存はできるが GUI で編集し直すと弾かれる」非対称**が生まれます。
逆向きに揃える（全体を厳密版にする）と、この非対称を固定することになるため採りませんでした。

app の受理範囲はわずかに広がりますが、実挙動は変わりません。
区間の入力欄は `DragValue::range(0.0..=1.0)` で丸めるため、境界の 1e-9 差には到達しないためです。

## N-M 相関曲面の 3D 描画

相関曲面を 3D で描く画面は 2 つあります。
断面詳細ビュー（`mn_view`）は 3 つの降伏モデルの曲面を重ねて軸力スライス平面を添え、ヒンジ詳細ウィンドウ（`viewer::hinge`）は 1 つの曲面に増分解析の応答経路を重ねます。

重ねるものは違いますが、曲面そのものの描き方は同じです。
`draw_axes` と `draw_mn_axes` は本体がバイト単位で一致しており、doc コメント自身が「`mn_view.rs::draw_axes` と同じ考え方の自己完結版」と重複を認めていました。
ワイヤーフレームの二重ループ・正規化基準・投影スケール・格子解像度 24/48 も同様に二重化しています。

これらを `viewer::mn_draw` へ集約しました。

`draw_mn_plot_3d` の doc は、共通化しない理由を「用途ごとにデータの正規化基準が異なるため共通化しにくく、重複させた方が安全」と書いていました。
ですが実際には両画面とも `n_comp.abs().max(n_tens).max(1.0)` という同じ式で基準を作っており、**この説明は事実に反していました**。
集約にあわせて書き換えています。

カメラ・スケール・画面中心は常に 3 つ揃って必要になるため、`MnView` にまとめて投影をそのメソッドへ移しました。
きっかけは clippy の引数個数の制限（7 個）を超えたことです。
結果として `draw_slice_plane` と `draw_mn_response_path_3d` も同じ投影を共有する形になりました。

応答経路の正規化だけは曲面と別扱いにしました。
`n_my_mz_response_path_3d` が返す点はすでに `[My, Mz, N]` の順なので、曲面格子のような並べ替え（`to_world`）が要らず、成分ごとに割るだけで済むためです。

## ベンチ例題の断面・材料

`eigen_bench`・`pushover_bench`・`th_bench` は同じ建物を測るため、柱 H-400x400x13x21・大梁 H-400x200x8x13・材料 SN400 の定義が 3 本でバイト単位まで一致していました。
`Section` や `Material` にフィールドが増えるたび 3 本すべてを直す必要があり、`examples/common/mod.rs` が骨組生成の定型を集めたのと同じ理由で複製が続く形です。

`column_beam_sections` と `sn400_steel` を common へ追加して 3 本から参照するようにしました。

`parallel_bench` は共有していません。
単一断面 H-400（`area = 8_400`）の別モデルで、材料も `fy: None`（線形の並列計算を測るため降伏強度を要さない）と異なります。
測っているものが違うので、common の「差異は呼び出し側へ残す」方針に従ってそのまま残しました。

## 波形読込から地動入力まで

波形ライブラリからファイルを読む処理と、その内容から `GroundMotion` を作る処理が 3 経路へ複製されていました。

- `run_time_history_from_library`（波形ライブラリから時刻歴）
- `run_time_history_from_csv`（ファイル選択から時刻歴）
- 質点系の波形ライブラリ実行（`lumped_mass`）

ライブラリの読込（保存先の特定 → 読み出し → それぞれのエラー通知）は 2 経路で一致しており、エラー文言の書き方だけが `{}` と `{e}` に割れていました。
`GroundMotion` の組み立てとエラー通知は 3 経路で一致しています。

前者を `read_wave_library_file`、後者を `ground_motion_or_report` として `App` へ集約しました。

`read_wave_library_file` が保存先ディレクトリも返すのは、呼び出し側が実行時点の SHA-256 を算定するのに同じディレクトリを使うためです。
`ground_motion_or_report` が解析設定を引数で受けるのは、質点系が刻みと方向を専用の設定（`lumped_th_dt`・`lumped_dir`）へ差し替えた写しを渡すためで、この差し替え自体は呼び出し側に残しています。

## 検証

計算根拠と表示を変えていないことを、次の順で確認しました。

- ワークスペース全体のテスト（スナップショットを含む）が全数成功する
- `gui` フィーチャ付きのテストも成功する
- 実モデル統合テスト（`full_model` 27 件・`wall_model` 9 件）が成功し、承認待ちのスナップショットが 1 件も出ない
- 決定性テストが成功する
- clippy 3 条件（ワークスペース `--all-targets`、`gui`、`mcp`）と `cargo fmt --check` が通る
- `xtask check-deps` が通る（50 件の上流チェック）
- ベンチ例題 4 本がビルドできる
- `cargo doc` の警告数が 81 件で変わらない（新規の警告を出していない）

置き換えがビット一致であることは、テストの成否だけに頼らず**直接確かめました**。
置き換え前後の実装を別プログラムへ写し、乱数で生成した入力を突き合わせています。

| 対象 | 件数 | 結果 |
|---|---|---|
| `member_length` の `powi(2)` 版と手書き `dx * dx` 版 | 200 万 | 差 0 |
| `vec3::dist` と手書きの `(b − a)` 版 | 200 万 | 差 0 |
| `LocalFrame::from_nodes` | 100 万 | 差 0 |
| `ShellFrame::from_nodes` | 100 万 | 差 0 |
| `element_area` | 100 万 | 差 0 |

入力の尺度は縮退する 1e-13 から建物規模の 1e5 まで 5 段階を混ぜ、`ref_vector` には既定値（柱の X・梁の Z）のほか材軸と平行になる値と零ベクトルを入れて、正規直交化のフォールバック分岐も踏ませています。
比較は値の差ではなく `to_bits()` の一致で見ました。
テストが通ることは「差が許容内」までしか示しませんが、この確認は「1 ビットも動いていない」ことを示します。

`viewer::mn_draw` には、集約した純粋な部分に単体テストを 4 件新設しました。
正規化基準が圧縮側と引張側の絶対値の大きい方を採ること、耐力が 0 でも下限 1.0 を割らないこと、`to_world` が `[N, My, Mz]` を画面の `[My, Mz, N]` へ並べ替えること、投影スケールが既定ズーム 3.0 で短辺の 0.32 倍になることを押さえています。
描画そのものは `egui::Ui` を要するため自動テストが書けませんが、**値を決める部分はここで固定できます**。

`span_is_valid` には性質テストを 1 件新設しました。
代表的な妥当値のほか、つぶれた区間・逆転した区間・非有限を弾くことを確かめます。
とくに**両端の 1e-9 の許容が効くこと**を、`[-1e-10, 1.0 + 1e-10]` を受理し `[-1e-3, 1.0]` を弾くという形で押さえました。
許容の有無が今回の判断そのものなので、そこを回帰テストで固定しておく意図です。

## 残課題

- `app::viewer::pick` などスクリーン座標（f32）を扱う UI のヒットテストは、今回も対象外です。[2D 多角形の幾何プリミティブ集約](2D多角形の幾何プリミティブ集約_申し送り.md) と同じ理由で、実寸（mm）の幾何とは別物として残しています
- `region_rebuild.rs` と `wall_region_rebuild.rs` は、旧領域との照合・帰属の付け替え・取り付き形への変換という手順が床側と壁側で並行しています。ですが扱う型（`FloorRegion`/`Slab` と `WallRegion`/`WallPlate`）も幾何の意味も違うため、今回は集約していません。寄せるならジェネリクスかトレイトが要り、「同じ手順に見えるものを 1 つにする」ことと「床と壁で違う判断ができる余地を残す」ことのどちらを取るかを先に決める必要があります
- `tables/slabs.rs` と `tables/wall_plates.rs` は、区間の判定を集約したあとも節点選択のコンボボックス対（2 節点から重複しない組を選ぶ処理）が 3 か所に残っています。レイアウトが縦積みと横並びで違い、壁側には伝達規則のコンボボックスと自立壁の分岐が加わるため、今回は判定だけを寄せました
- `squid-n-element` 以外のクレートにも手書きの 3 次元ベクトル演算が残っている可能性があります。今回は `dot`・`cross`・`norm` の典型的な字面で走査しましたが、`for` ループで書かれたものは拾えていません
