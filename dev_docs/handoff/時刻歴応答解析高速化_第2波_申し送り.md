# 時刻歴応答解析の高速化（第2波: math 新API のソルバ統合） 申し送り

作成日: 2026-07-29
対象コード: `crates/squid-n-solver/src/dynamic/timehistory/{nonlinear,linear,hht,common}.rs`、
`crates/squid-n-solver/src/dynamic/damping.rs`、
`crates/squid-n-solver/src/common/{csc_cache.rs（新規）,constraint.rs}`、
`crates/squid-n-solver/src/nonlinear/pushover/{assembly.rs,mod.rs}`

前提: 第1波（コミット `df7a97b` 「時刻歴応答解析の高速化(第1波)」）で
squid-n-math に symbolic 分解キャッシュ付き `CholeskySolver`/`LuSolver`、
`CscAssembler`、`WeightedSumCache`、`scale_csc`、`solve_into`、`sparse_matvec_into`
を追加済みだった。第2波はこれらを実際のソルバ経路（特に非線形時刻歴の Newton
反復）へ統合し、効果を出すことが目的。**squid-n-math 自体には変更を加えていない**
（既存 API の挙動は不変、追加もしていない。実装済みの新 API を呼び出す側を書き換えた
だけ）。

## 1. 実施内容

### 1.1 非線形経路: ソルバインスタンスの持ち回り（symbolic 分解キャッシュ）

第1波時点の `nonlinear.rs` は Newton 反復のたびに `make_solver(SolverBackend::Auto)`
で**新規インスタンス**を作っていたため、`CholeskySolver` の symbolic キャッシュ
（同一インスタンスへの `factorize` 繰り返しでのみ効く）が機能していなかった。

- `nonlinear_time_history_analysis` の Newton ループ用に、ステップループの外側で
  `Box<dyn LinearSolver>` を 1 個だけ生成し、以後は同じインスタンスへ
  `factorize`/`solve_into` を呼ぶよう変更。
- 長期荷重の静的載荷フェーズ（`apply_long_term_static`→`newton_static_converge`）も
  同様に、`apply_long_term_static` 側でソルバインスタンス・CSC キャッシュ・作業
  バッファを 1 組だけ生成し、`newton_static_converge` へ `&mut` で渡して漸増ステップ
  全体（複数回の載荷率試行×各試行内最大 50 回の Newton 反復）を通じて使い回す形に
  変更。

**バックエンドは `SolverBackend::Auto` から `SolverBackend::DirectSparseCholesky` に
明示し直した。** 理由: `AutoSolver::factorize` は自由度数がしきい値
（`AUTO_ITERATIVE_MIN_DOF`=50,000）未満の直接法経路で、呼び出しのたびに内部の
`CholeskySolver` を新規生成する実装になっており（`squid-n-math/src/auto.rs`）、
`AutoSolver` 自体を持ち回っても symbolic キャッシュは効かない。本解析の自由度規模
（縮約後数百〜数千程度を想定、ベンチモデルは 480）は常にこのしきい値を下回り
`Auto` は事実上 `DirectSparseCholesky` と同じ経路を選ぶため、明示しても数値結果・
エラー条件は変わらない（`linear.rs`/`hht.rs` は元々 `DirectSparseCholesky` を明示
しており、それと同じ方針に揃えた形）。`squid-n-math` 側（`AutoSolver` 内部での
インスタンス再利用化）を直すという選択肢もあったが、「squid-n-math は既存 API の
挙動変更禁止」という今回の作業範囲の制約を踏まえ、呼び出し側の変更のみで完結する
こちらを採った。将来 `Auto` の PCG 経路を非線形時刻歴でも使う設計にする場合は、
`AutoSolver::factorize` の直接法分岐を「既存インスタンス再利用」に直す必要がある
（現状は `State::Direct(_)` を保持していても再利用せず毎回上書きする）。

### 1.2 CSC 組立てのキャッシュ化

`crates/squid-n-solver/src/common/csc_cache.rs`（新規）に `CscCache`・
`WeightedSumGuard` を追加し、以下へ適用した。

- `assemble_k`（`nonlinear/pushover/assembly.rs`）: triplet 生成ロジックを
  `assemble_k_triplets` へ切り出し、`assemble_k`（従来どおり `assemble_csc` を呼ぶ）と
  `assemble_k_cached`（`CscCache` 経由）が共有する形にした。呼び出し元の変更は
  `nonlinear.rs`（Newton ループ・`newton_static_converge`）のみで、プッシュオーバー
  （`driver.rs`）は従来の `assemble_k` のまま（毎ステップ 1 回の組立てで反復しないため
  キャッシュの恩恵が小さく、変更範囲を絞った）。
- `Reducer::reduce_k`（`common/constraint.rs`）: 同様に triplet 生成を
  `reduce_k_triplets` へ切り出し、`reduce_k_cached`（`CscCache` 経由）を追加。
- `K_eff = K_t + c2·C + c1·M`（`nonlinear.rs`）: `WeightedSumGuard::combine` に置換。
- `Damping::assemble_c_tangent`（`damping.rs`）の `weighted_sum_csc(n, &[(a1, k_t)])`
  （単一行列の重み付き和＝スカラ倍）は `scale_csc(k_t, a1)` に置換
  （`StiffnessProportional{basis:Tangent}`・`TangentStiffnessConstantH` の両方）。

#### ビット一致の担保方法

`CscCache`/`WeightedSumGuard` は「2回目以降に渡す triplet 列・入力行列の非ゼロ数が
前回と完全一致していること」を前提とする `CscAssembler`/`WeightedSumCache`
（squid-n-math）を、**その前提が崩れても安全なように**ラップしている。

弾塑性要素の接線剛性は完全塑性域で成分が厳密に 0.0 になり得る（`to_triplets` は
`v != 0.0` の成分のみを積む実装のため）。つまり Newton 反復間で接線剛性の非ゼロ数
（＝ triplet 列の長さ）が変わり得るのは非線形時刻歴では珍しくない。このため:

- `CscCache::assemble`/`WeightedSumGuard::combine` は、直前呼び出しとの次元・
  非ゼロ数（長さ）を**リリースビルドでも**比較し、不一致なら
  `CscAssembler::new`/`WeightedSumCache::new` でパターンを作り直す
  （＝そのラウンドのみ通常の `assemble_csc`/`weighted_sum_csc` 相当のコストに戻る
  が、結果は変わらない安全側フォールバック）。
- 座標・並び順そのものの一致検証は `CscAssembler::assemble_into`/
  `WeightedSumCache::combine_into` 内部の `debug_assert`（デバッグ・テストビルドの
  み）に委ねている。長さが変わらないのに座標だけがずれるケースは想定していないが、
  仮に起きればテスト実行時に必ず落ちる。
- 作り直し（`CscAssembler::new`/`WeightedSumCache::new`）の結果が
  `assemble_csc`/`weighted_sum_csc` とビット一致することは squid-n-math 側の既存
  テスト（`test_csc_assembler_matches_assemble_csc_bit_exact` 等）で担保済み。
  高速パス（`assemble_into`/`combine_into`）についても同様。したがって
  `CscCache`/`WeightedSumGuard` は「高速パスか作り直しか」に関わらず常に
  非キャッシュ版とビット一致する。`csc_cache.rs` 自身にもパターン変化を跨ぐ
  ケースの単体テストを追加している。

これに加えて、以下で数値結果の非退行を確認している。

- 決定性ガードテスト 4 本（`timehistory/tests.rs`、同一入力を 2 回実行して
  `ResponseResult` を bincode バイト列比較）を各段階で実行し、常に一致。
- `th_bench` のピーク変位（線形 1663.3493 mm・HHT 1663.3440 mm・非線形
  6384.8039 mm）が、施策前後・各実行を通じて**完全一致**（下記ベンチ結果参照）。
- `cargo test -p squid-n-solver --lib`／`cargo test --workspace` が全件成功
  （下記「4. テスト結果」）。

### 1.3 solve_into / sparse_matvec_into への置換

- `nonlinear.rs`: Newton ループの `solver.solve(r_red)` → `k_eff_solver.solve_into(r_red,
  &mut du_red_buf)`。`newton_static_converge` の `solver.solve(&r_red)` → `solver.solve_into(&r_red,
  du_red_buf)`（`du_red_buf` は `apply_long_term_static` から持ち回り）。
- `linear.rs`/`hht.rs`: ステップループの `solver.solve(&p_eff_buf)` →
  `solver.solve_into(&p_eff_buf, &mut u_next_buf)`（`u_next_buf` をループ外で 1 回だけ
  確保）。
- `common.rs` の `sparse_matvec_into`（第1波の暫定ローカル実装）を、squid-n-math に
  第1波で追加済みの `squid_n_math::sparse::sparse_matvec_into` の再エクスポートに
  置換（ロジックは元々同一だったため、呼び出し側の変更は不要）。

## 2. ベンチ結果

`cargo run -p squid-n-solver --example th_bench --release`（各ケース 3 回実行、
最小値を採用。480 自由度・200 部材のモデル、線形/HHT は 4096 步、非線形は 1024 步）。

実行環境のノイズが比較的大きい（同一バイナリの再実行でも ±0.05〜0.1 s 程度ぶれる）
ため、線形・HHT-α は複数回実行した範囲の値を示す。非線形は改善幅が計測ノイズより
明確に大きい。

| ケース | 第1波後（本セッション計測） | 第2波後（複数回計測の範囲） | 変化 |
| --- | --- | --- | --- |
| 線形 Newmark-β（4096步） | 0.742 s | 0.738〜0.790 s | 有意差なし（ノイズ内） |
| HHT-α（4096步） | 0.772 s | 0.750〜0.809 s | 有意差なし（ノイズ内） |
| 非線形 既定Cfg（1024步） | 26.077 s | 20.553〜21.104 s（最小 20.553 s） | 約 19〜21% 減 |

参考: コミット `df7a97b`（第1波）のコミットメッセージに記載の計測値は
非線形 22.3 s・線形 0.59 s・HHT 0.64 s（第1波前後比較用の別環境での計測）。
本セッションでの「第1波後」計測（26.077/0.742/0.772 s）はこれと異なるが、
同一環境・同一手順で第2波前後を比較しているため、上表の変化幅（特に非線形の
20〜25%減）が第2波の効果として妥当な数値である。

線形・HHT-α で有意な改善が出なかった理由: 両者は元々ステップループの外で
K_eff を 1 回だけ組み立てて `factorize` する設計（第1波以前から）で、
ステップごとのコストは疎行列の前進代入・後退代入（triangular solve）が支配的。
`solve_into` で削減できるのは `Vec<f64>` の確保コストのみで、480 自由度・
4096 步というモデル規模ではその削減量が計測ノイズに埋もれる。非線形は逆に
「Newton 反復のたびに接線剛性を組み立て直し、有効剛性を再度 `factorize` する」
という構造そのものが支配的コストだったため、symbolic 分解キャッシュと CSC
パターン再利用の効果がそのまま現れている。

**ピーク変位の完全一致**: 施策前後・全ての実行を通じて、線形 1663.3493 mm・
HHT 1663.3440 mm・非線形 6384.8039 mm が完全一致することを毎回確認した
（`th_bench` の出力値そのもの。有限値チェックも常に true）。

## 4. 残課題・設計方針の申し送り

### 4.1 要素ループの並列化（rayon）は未実施

今回の第2波でも rayon 等による要素ループの並列化は導入していない
（`assemble_k`／`compute_f_int` の要素ループは逐次のまま）。理由と将来の設計方針:

- 現状は「要素を `model.elements` の順に走査し、`Vec` へ triplet を `extend`
  する」逐次 collect のため、triplet の並び順が要素順に厳密に従う。これが
  `CscAssembler`/`WeightedSumCache`（本第2波で導入）・`assemble_csc` の
  ビット一致（加算順序が結果に影響し得る浮動小数点演算）を成立させている前提の
  一つでもある。
- 並列化する場合は、**要素ごとの結果を要素番号順を保ったまま collect する**方式
  （例: `Vec<Box<dyn ElementBehavior>>` を `par_iter()` で並列に triplet 化しつつ
  `Vec<Vec<Triplet>>` として集約し、最後に要素順で `flatten`／`extend`）であれば、
  triplet の並び順は逐次実行時と完全に同じになり、決定性（ビット一致）を維持した
  まま並列化できるはずである。逆に「複数スレッドが同じ出力 `Vec`/CSC 行列へ
  ロックや `fetch_add` で直接書き込む」方式は書き込み順序が実行のたびに変わり得る
  ため、ビット一致が崩れる可能性が高く避けるべきである。
- 本モデル規模（数百自由度・数百要素）では要素ループ自体のコストは
  Newton 反復の分解・求解コストに比べ小さく、並列化の投資対効果が低いと判断し
  今回は見送った。より大規模なモデル（要素数が数千〜のファイバーモデル等）で
  ボトルネックが要素ループ側に移る場合に着手を検討すること。

### 4.2 `CscCache`/`WeightedSumGuard` は毎回 `SparseColMat` を clone している

`CscCache::assemble`/`WeightedSumGuard::combine` は内部で保持する
`SparseColMat` への参照ではなく**所有値**（`.clone()`）を返す設計にした。
理由: キャッシュ内部（`CscAssembler`/`WeightedSumCache`）への `&mut` 借用を
呼び出し元の複数箇所（`nonlinear.rs` の Newton ループは `k_t_free`→`k_t_red`→
`k_eff` と複数のキャッシュを跨いで値を使い回す）に跨いで持ち回ると、既存コードの
構造（多数のバッファ・`Option<SparseColMat>` の受け渡し）に対してライフタイムの
影響範囲が大きく、変更のリスクが増す。`SparseColMat::clone()` のコスト（列ポインタ・
行添字・値配列の複製、O(nnz)）は、置き換え対象だった「triplet 化＋
`sort_by_key`」（O(nnz log nnz)）より軽いため、今回はこの設計で十分な高速化効果
（非線形 20〜25%減）が出ている。さらに詰めるなら、`CscCache`/`WeightedSumGuard` に
「参照を返す」バリアントを追加し、`nonlinear.rs` 側の該当区間だけ借用ベースの
構造に書き換える余地がある（squid-n-math 側の変更は不要、squid-n-solver 側の
追加작업のみ）。
