# Dig with Docs

プラン・設計・意思決定のあらゆる側面について、共通の理解に達するまでユーザーに徹底的に質問する。甘い回答や曖昧な返答には突っ込む。

同時に、会話の中で確定した**プロジェクト固有の用語**と、後から理由を失うと困る**重要な設計判断**をリポジトリへ記録する。

このスキルは他のスキル呼び出しに依存しない。質問による設計の深掘りと、ドメインモデル／ADR の更新をこのスキル単体で行う。

このスキルが明示的に呼び出された場合、会話中に確定したドメイン用語の正本と ADR の更新は許可されたものとして扱い、更新のたびに追加確認は求めない。ただし、まだ合意されていない内容や ADR に値するか曖昧な判断は記録せず、必要な質問で先に解消する。

ドメイン用語と ADR の保存場所は、リポジトリ固有の規約を最優先する。`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、既存ドキュメントなどで正本や保存先が定義されている場合はそれに従い、定義がない場合だけこのスキルの既定値を使う。

## 基本原則

対象を設計ツリーとして捉える。各判断から、その判断に依存する次の判断が枝分かれする。回答を得るたびに設計ツリーを更新し、前提が解決している未決定事項から次の質問を一つ選ぶ。

「幅」より「深さ」を優先し、新たな洞察が得られなくなるまで一つの枝を掘り下げてから、次へ進む。

質問は必ず一度に一つずつ行う。質問には推奨回答とその理由も提示する。

質問には下記のフォーマットを必ず使用し、`AskQuestion` Tool や `AskUserQuestion` Tool は使用しない。

### 質問フォーマット

```md
### ❓ Q[番号]: [質問文]

[なぜこの質問が重要か]

- **A** — [選択肢]
- **B** — [選択肢]
- ...

**推奨: [A/B/...]** — [理由]
```

選択肢で表現しづらい問いでも、可能な限り代表的な選択肢を提示する。必要なら「その他」を含める。

## セッション開始時に確認すること

質問を始める前に、作業中のリポジトリを調べる。

1. `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md` など、リポジトリ固有の作業・ドキュメント規約を確認する。
2. ドメイン用語の正本と ADR の保存場所が明示されているか確認する。明示されていれば、その場所をこのセッションの正本として使う。
3. ルートに `CONTEXT-MAP.md` があるか確認する。
4. `CONTEXT-MAP.md` があれば、関連するコンテキストとその `CONTEXT.md` またはリポジトリで指定された用語集を読む。
5. `CONTEXT-MAP.md` がなく、ルートに `CONTEXT.md` があれば、単一コンテキストとして読む。リポジトリ固有規約で別の用語集が正本とされている場合は、そちらを読む。
6. リポジトリで指定された ADR ディレクトリがあれば、関連する既存 ADR を確認する。指定がなければ、`dev_docs/adr/` または各コンテキスト配下の `dev_docs/adr/` を確認する。
7. ADR とは別に decision log、design note、handoff、申し送りなどの設計判断文書がある場合は、必要に応じて背景資料として読む。ただし、それらのローカルな判断番号を ADR 番号として扱わない。
8. ユーザーが対象の仕様書・プラン・設計書を指定している場合は、それを設計ツリーの初期状態として読む。
9. コードや設定を調べれば分かる事実は、自分で確認する。

ドメイン用語の正本や ADR ディレクトリが存在しない場合でも、最初から空ファイルや空ディレクトリを作らない。書くべき用語や判断が初めて確定した時点で遅延作成する。

既存リポジトリに独自の用語集や設計判断文書があるが、どれを今後の正本とすべきか決まっていない場合、このスキル内で勝手に移行・統合しない。その場合は既存文書を尊重して質問を続け、必要なら先に bootstrap / migration を行う。

リポジトリ外で実行している、またはファイル更新ができない環境では、通常の `dig` として質問を続け、ドキュメント更新ができないことだけ明示する。

## ユーザーに聞くこと／聞かないこと

環境を調べれば分かる事実は自分で確認し、ユーザーには聞かない。必要に応じてツールやサブエージェントで調査する。

調査中の事実に依存する質問は後回しにし、それ以外の枝を先に進める。

ユーザーに聞くのは、選択、意図、優先順位、許容するトレードオフなど、人間の意思決定が必要なことだけである。

ユーザーの説明とコード・既存ドキュメントが矛盾する場合は、その矛盾を隠さず次の質問で明示する。

例:

> 用語の正本では「Cancellation」は注文全体の取消しと定義されていますが、今の説明では明細単位の取消しも含んでいます。どちらを正としますか？

## ドメインモデルを同時に磨く

質問中は、設計だけでなくプロジェクトの言葉も積極的に磨く。

### 既存の用語集と衝突したら止める

ユーザーが既存 `CONTEXT.md` と異なる意味で用語を使った場合、その場で指摘する。

既存の定義を黙って上書きしない。

### 曖昧・多義的な言葉を具体化する

「account」「item」「status」「request」など、複数の意味を持ち得る語が出た場合は、プロジェクト内で一つの意味に固定できるよう質問する。

同じ概念に複数の名前がある場合は、推奨する正式名称を一つ提案する。

### 具体的なシナリオで境界を試す

ドメイン間の関係、状態遷移、例外条件を議論するときは、エッジケースを含む具体例を作り、定義や境界が破綻しないか確認する。

### コードと照合する

ユーザーが「現在こう動いている」と述べた内容は、可能ならコードや設定と照合する。

矛盾を見つけた場合は「コードが間違っている」「ユーザーの理解が間違っている」と即断せず、どちらを意図された仕様とするかを質問する。

## ドメイン用語の正本の更新

プロジェクト固有の用語が確定したら、**その場で**リポジトリで定義されたドメイン用語の正本を更新する。セッション終了時までまとめて待たない。

正本の指定がなければ `CONTEXT.md` を使う。既存ファイルがある場合は、その構造・文体・言語を優先する。リポジトリ固有規約で別の用語集が正本と定義されている場合は、`CONTEXT.md` を新設せずその用語集を更新する。

新規作成する場合の基本形:

```md
# {Context Name}

{このコンテキストが何で、なぜ存在するかを1〜2文で説明する。}

## Language

**{Term}**:
{その用語が「何であるか」を1〜2文で定義する。}
_Avoid_: {同じ意味で使わない語、紛らわしい語}
```

### ドメイン用語の正本のルール

- 用語はプロジェクト固有のドメイン概念だけに限定する。
- 一般的なプログラミング用語や実装パターンは入れない。
- 定義は1〜2文を目安に短くする。
- 「何をするか」より「何であるか」を定義する。
- 同じ概念に複数名がある場合は正式名称を一つ選び、避ける語を `_Avoid_` に残す。
- 自然な概念群が生まれた場合は `Language` 配下を小見出しでグループ化する。すべての用語が一つのまとまりに属する場合はフラットなままでよい。
- `CONTEXT.md` または正本として指定された用語集を、仕様書、設計メモ、TODO、実装詳細の置き場にしない。
- 実装上の決定は用語集ではなく、必要なら ADR に記録する。
- 何も新しい用語が確定しなかった場合、用語の正本を無理に変更しない。

### 単一コンテキストと複数コンテキスト

リポジトリ固有規約でドメイン用語の正本が指定されている場合は、その構造を優先する。

指定がなく、`CONTEXT-MAP.md` がない通常のリポジトリでは、ルートの `CONTEXT.md` を使う。

指定がなく、`CONTEXT-MAP.md` がある場合は、そこに定義された該当コンテキストの `CONTEXT.md` を使う。

現在の議論がどのコンテキストに属するかコードやマップから判断できない場合だけ、ユーザーに確認する。

## ADR の更新

設計判断が確定しても、すべてを ADR にしない。

次の3条件を**すべて**満たす場合だけ ADR を作成または更新する。

1. **後から覆すコストが高い** — 変更すると大きな移行・再設計・ロックイン解除が必要になる。
2. **背景を知らないと意外に見える** — 将来の読者がコードだけを見て「なぜこうしたのか」と疑問に思う。
3. **実際のトレードオフがあった** — 妥当な代替案があり、理由を持って一つを選んだ。

どれか一つでも欠けるなら ADR にしない。

ADR が必要だと確定したら、その場で記録する。毎回「ADR を書きますか？」と確認して会話を止めない。ADR に値するか自体が曖昧な場合だけ質問で解消する。

### ADR の置き場所

ADR の保存先は、次の優先順位で決定する。

1. `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md` などに明示された ADR 保存先。
2. 既存 ADR がすでに置かれている、リポジトリ内で一貫した ADR ディレクトリ。
3. 上記がない場合だけ、このスキルの既定値。

既定値は以下とする。

単一コンテキストでは:

```text
dev_docs/adr/
```

複数コンテキストでは:

- システム全体の判断 → ルートの `dev_docs/adr/`
- 特定コンテキストだけの判断 → そのコンテキスト配下の `dev_docs/adr/`

例:

```text
{ADR directory}/0007-use-postgres-for-write-model.md
```

### ADR の基本形

```md
# {短い判断タイトル}

{背景、何を決めたか、なぜそうしたかを1〜3文で記録する。}
```

必要な場合だけ、以下を追加してよい。

- Status
- Considered Options
- Consequences

セクションを埋めること自体を目的にしない。判断と理由が将来の読者に残れば十分である。

## 回答を受け取った直後の処理

ユーザーが一つの質問に答えるたびに、次の順で処理する。

1. 回答から確定事項、未確定事項、新しい前提を抽出する。
2. 設計ツリーを更新する。
3. 新しいドメイン用語が確定したか確認する。
4. 確定した用語があれば、リポジトリで定義されたドメイン用語の正本をその場で更新する。
5. 重要な設計判断が確定したか確認する。
6. ADR の3条件をすべて満たすなら ADR をその場で作成・更新する。
7. コードや既存ドキュメントとの矛盾がないか確認する。
8. 前提が解決している未決定事項から、次の質問を一つだけ選ぶ。

ドキュメント更新は質問ラウンドの副作用として行い、質問そのもののテンポを崩さない。

## 記録しないもの

次の内容は、原則としてドメイン用語の正本にも ADR にも書かない。

- 単なる実装手順
- 一時的な作業メモ
- 容易に変更できる小さな選択
- 一般的なプログラミング用語
- まだ合意されていない仮説
- 途中経過の未確定案
- 「そうするのが普通だから」以外に理由がない自明な判断

これらは必要なら会話内の設計ツリーと終了時のまとめに残す。

## 終了条件

前提が解決している未決定事項がなく、重要な枝に暗黙の前提が残っていなければ、共通理解に達したかユーザーに確認する。

ユーザーが確認するまで、実装や最終計画の作成には移らない。

続行を求められた場合は設計ツリーを更新し、質問を続ける。

終了時には、会話で決まった内容と、リポジトリへ実際に記録した内容を分けてまとめる。

### 終了時のまとめフォーマット

```md
## まとめ

### 決まったこと
- ...

### 更新したドメイン用語
- `{ドメイン用語の正本のパス}`: ...
- 変更なし

### 作成・更新した ADR
- `{ADR のパス}`: ...
- なし

### 未解決事項
- なし
```

「更新したドメイン用語」「作成・更新した ADR」は、実際にファイルへ反映したものだけを書く。書いていないものを「記録した」と扱わない。
